# 手搓智能指针：从代码到控制块的逐段解读

> 对应实现：[smart_ptr.hpp](../modules/A2_smart_pointers/include/smart_ptr.hpp)；对应测试：[test_smart_ptr.cpp](../modules/A2_smart_pointers/tests/test_smart_ptr.cpp)。
>
> 阅读目标不是记住 API，而是能回答四件事：**谁拥有对象？计数何时变化？对象何时析构？控制块何时回收？**

## 先建立全局模型

这份实现按难度递进分为三个类型：

| 类型 | 是否拥有对象 | 能否拷贝 | 核心成员 | 解决的问题 |
| --- | --- | --- | --- | --- |
| `UniquePtr<T>` | 独占 | 否，只能移动 | `T* ptr_` | 让一个堆对象只有一个明确主人 |
| `SharedPtr<T>` | 共享 | 是 | `T* ptr_` + `ControlBlock* cb_` | 多个拥有者共同决定对象何时销毁 |
| `WeakPtr<T>` | 不拥有，只观察 | 是 | `T* ptr_` + `ControlBlock* cb_` | 打破共享引用环；安全地尝试取得对象 |

最重要的区分是：`SharedPtr` 管理的不是只有一个“对象”。它实际上有两块独立分配的内存：

```text
SharedPtr / WeakPtr 副本                 堆上
┌───────────────────────┐       ┌───────────────────────────┐
│ ptr_ ─────────────────┼──────▶│ T object                  │
│ cb_  ─────────────────┼──┐    └───────────────────────────┘
└───────────────────────┘  │
                             │    ┌───────────────────────────┐
                             └───▶│ ControlBlock<T>           │
                                  │ strong: SharedPtr 个数    │
                                  │ weak: WeakPtr 个数 + 1*   │
                                  │ ptr: 被管理对象地址       │
                                  └───────────────────────────┘

*当 `strong > 0` 时，所有 SharedPtr 合起来额外贡献 1 个 weak 计数。
```

因此有两个不同的销毁时刻：

1. `strong` 从 1 减到 0：析构/删除 **T 对象**。
2. `weak` 从 1 减到 0：删除 **控制块**。

`WeakPtr` 的存在意味着：对象可能已经没了，但控制块还必须留下，以便 `expired()` 和 `lock()` 能安全检查 `strong`。这就是两个计数不能合并成一个的原因。

# 第一部分：`UniquePtr<T>` —— 先搞懂独占所有权

## 1. 类的最小状态

`UniquePtr` 的全部状态只有一个裸指针：[`ptr_`](../modules/A2_smart_pointers/include/smart_ptr.hpp:121)。这恰好表达了“唯一主人”。它没有控制块、没有计数、没有额外堆分配；本教学实现的大小通常就是一个指针大小。

从裸指针构造的构造函数在[第 47 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:47)：

```cpp
explicit UniquePtr(T* p) noexcept : ptr_(p) {}
```

`explicit` 阻止 `UniquePtr<T> p = raw;` 这类隐式接管行为。接管所有权应该醒目：调用方需要知道从这一行开始，`raw` 不该再被第二次 `delete`。

## 2. 为什么必须禁止拷贝

[第 50–51 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:50)删除了拷贝构造和拷贝赋值：

```cpp
UniquePtr(const UniquePtr&) = delete;
UniquePtr& operator=(const UniquePtr&) = delete;
```

若允许简单拷贝，两个对象会保存同一个 `T*`。两个析构函数随后都会执行 `delete`，第二次释放就是 double free。这里不是“效率问题”，而是所有权语义在编译期就不允许。

## 3. 移动构造：转交钥匙，而非复制对象

[第 58–62 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:58)：

```cpp
UniquePtr(UniquePtr&& other) noexcept {
    ptr_ = other.ptr_;
    other.ptr_ = nullptr;
}
```

这段代码只复制一个地址，**没有移动 `T` 对象本身**。真正的关键是下一行：原主人被置空。这样离开作用域时，`other` 的析构执行 `delete nullptr`，安全无事；新对象才是唯一会删除 `T` 的主人。

为什么是 `noexcept`：`vector<UniquePtr<T>>` 扩容时需要搬迁元素。`UniquePtr` 的移动不抛，容器可安全选择移动而不是拷贝；被指向的 `T` 对象地址本身不会改变。

## 4. 移动赋值：先处理旧资源，再接手新资源

[第 71–80 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:71)的顺序是：

```text
自移动检查 → delete 当前对象 → 取走 other.ptr_ → other 置空 → 返回 *this
```

自移动检查不可省略。假设 `p = std::move(p)`：若先 `delete ptr_`，随后再读取 `other.ptr_`，得到的是已经释放的地址；最终 `p` 会变成悬垂指针。实现通过 `this == &other` 原样返回来维持不变量。

注意这一版本的 `reset(p)` 有一个教学型前提：`p` 不能等于当前 `ptr_`。若调用 `p.reset(p.get())`，它会把同一地址先保存、再 delete，最后仍保存已释放地址。标准库的 `unique_ptr::reset` 也不应传入自己正在管理的同一指针；正确写法通常是不要这样做，或先明确所有权转移关系。

## 5. `release()` 与 `reset()`：最容易误用的两组 API

### `release()`：只交出地址，不销毁对象

[第 101–106 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:101)把 `ptr_` 置空后返回旧地址。此后对象仍活着，但责任落回调用方：

```cpp
T* raw = p.release(); // p 不再管理 raw
// 必须由调用方 delete raw，或立即交给另一个所有者。
```

它适合和要求裸指针所有权的旧 API 互操作，但日常业务中应很少出现。`release()` 后忘记处理返回值就泄漏。

### `reset()`：删除旧对象，接管新对象

[第 113–118 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:113)先把新地址写入 `ptr_`，再删除旧地址：

```cpp
T* old = ptr_;
ptr_ = p;
delete old;
```

它让对象在函数返回前始终处于“要么管理新指针、要么为空”的状态；`delete nullptr` 合法，因此默认参数能直接实现清空。

## 6. `MakeUnique` 怎样体现完美转发

[第 125–128 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:125)中的 `Args&&...` 是转发引用，`std::forward<Args>(args)...` 保留传入实参的左/右值类别。它在堆上直接构造 `T`，再把新对象交给 `UniquePtr`。这里的异常安全来自表达式求值过程：若 `T` 构造抛异常，`new T(...)` 不会返回指针，也就不会有待接管的资源。

# 第二部分：`SharedPtr<T>` —— 控制块与两阶段销毁

## 7. 控制块的三个字段

[`ControlBlock<T>`](../modules/A2_smart_pointers/include/smart_ptr.hpp:137)包含：

```cpp
std::atomic<long> strong; // 活着的 SharedPtr 数
std::atomic<long> weak;   // WeakPtr 数 + SharedPtr 集合的保留位
T* ptr;                   // 被管理对象
```

构造控制块时为 `strong = 1, weak = 1`。第二个 1 不是一个实际 `WeakPtr`，而是“只要对象仍活着，就保留控制块”的锚点。它保证最后一个 `SharedPtr` 销毁对象时，控制块仍在，随后才能安全减少 weak 计数。

为什么计数不放在 `T` 内部？`T` 可能来自第三方、不能修改；更关键的是，T 在 `strong == 0` 时已销毁，仍存活的 `WeakPtr` 还需要读取计数。为什么计数不放在每个 `SharedPtr` 内？多个副本必须观察同一份计数。

## 8. 从裸指针构建：对象和控制块的关系

[第 156–158 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:156)做两件事：保存 `p`，并为非空指针 `new ControlBlock<T>(p)`。

```cpp
SharedPtr<T> s(new T(...));
```

在本教学实现中这是**两次分配**：一次给 T，一次给控制块。它有助于看清生命周期，但与标准 `make_shared` 不同：真正 `std::make_shared` 通常把对象和控制块做成一次合并分配。

还要注意一个生产级缺口：若 `new ControlBlock<T>(p)` 抛异常，构造函数无法完成，`p` 会泄漏。工业实现会在控制块分配失败时删除 p，或优先使用 `make_shared`。这是这份教学代码最值得主动说出的改进点之一。

## 9. 拷贝：复制两根指针，再增加 strong

[第 165–169 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:165)：

```cpp
ptr_ = other.ptr_;
cb_ = other.cb_;
retain_();
```

“共享”不等于复制对象，只是让新 `SharedPtr` 指向同一个对象和同一个控制块。`retain_()` 在[第 240–243 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:240)用 `fetch_add(1, memory_order_relaxed)` 增加强引用。

这里 relaxed 的原因是：此操作只维护“计数不会丢”的原子性，不借它发布/读取 T 的其他数据。**这不意味着 T 的字段自动线程安全**；多个线程写 `*ptr_` 时仍必须自行同步。

## 10. 拷贝赋值：为什么先 `release_()` 仍然安全

[第 178–185 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:178)先释放自己的旧持有，再复制 `other` 并 `retain_()`：

```cpp
if (this == &other) return *this;
release_();
ptr_ = other.ptr_;
cb_ = other.cb_;
retain_();
```

若 `this` 和 `other` 是**同一个 SharedPtr 对象**，自赋值检查阻止它先把自己减到 0。若它们是不同对象、但已经共享同一控制块，先减后加也安全：至少 `other` 仍保有一个强引用，所以 strong 不会被减到 0。

## 11. 移动：为什么不增减任何计数

[移动构造](../modules/A2_smart_pointers/include/smart_ptr.hpp:191)与[移动赋值](../modules/A2_smart_pointers/include/smart_ptr.hpp:205)只是转交 `ptr_` 和 `cb_`，随后清空来源。由于“一个 SharedPtr 包装器消失，另一个出现”，所有者总数没有变，计数无需 `fetch_add/fetch_sub`。这是移动比拷贝便宜的实质原因。

## 12. `release_()`：整份实现的核心

[第 262–272 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:262)可分成两个阶段读：

```cpp
if (cb_->strong.fetch_sub(1, std::memory_order_acq_rel) == 1) {
    delete cb_->ptr;
    cb_->ptr = nullptr;
    if (cb_->weak.fetch_sub(1, std::memory_order_acq_rel) == 1) {
        delete cb_;
    }
}
```

### 阶段一：最后一个强引用销毁对象

`fetch_sub` 返回减法前的值。因此返回 1 的唯一情况是“减完变成 0”，当前析构者就是最后一个拥有者。只有它能 `delete cb_->ptr`，不会发生多个线程重复析构。

此时必须立刻 `cb_->ptr = nullptr`：教学 `WeakPtr` 虽然不会在 `strong == 0` 时 lock 成功，但控制块不应继续保存一个看似可用的已释放地址。

### 阶段二：最后一个弱引用销毁控制块

对象删除后，`SharedPtr` 集合所贡献的那一个 weak 也要减少。若此时没有实际 `WeakPtr`，`weak` 从 1 到 0，控制块立即释放；若仍有观察者，控制块保留到最后一个 `WeakPtr` 析构。

### 一次完整状态变化

```text
初始：SharedPtr s                       strong=1, weak=1,  T 活着
WeakPtr w = s                           strong=1, weak=2,  T 活着
SharedPtr t = s                         strong=2, weak=2,  T 活着
t 析构                                  strong=1, weak=2,  T 活着
s 析构（最后一个强引用）                strong=0, weak=1,  T 已删除
w 析构（最后一个弱引用）                控制块删除
```

`acq_rel` 的目的不是让任意 T 操作线程安全，而是让“最后一次引用释放并销毁对象”的跨线程计数关系具备正确的同步语义。真实标准库实现可能做更细致的内存序优化，不能把这里的内存序当成唯一标准答案。

# 第三部分：`WeakPtr<T>` —— 观察、过期与原子提升

## 13. `WeakPtr` 增加的是 weak，不是 strong

[第 308–312 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:308)从 `SharedPtr` 创建 `WeakPtr` 时，复制 `ptr_` 和 `cb_`，只给 `weak` 加一：

```cpp
ptr_ = sp.ptr_;
cb_ = sp.cb_;
cb_->weak.fetch_add(1, std::memory_order_relaxed);
```

因此 `WeakPtr` 不会影响 `use_count()`，也不能阻止对象销毁。它的职责只是在对象死亡后仍保住控制块，供未来检查。

## 14. `expired()` 为什么不能作为“检查后直接使用”的依据

[第 347–351 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:347)读取 `strong == 0` 判断过期。这个查询本身没问题，但以下写法有竞态：

```cpp
if (!w.expired()) {
    // 另一线程此刻可能刚好销毁最后一个 SharedPtr。
    // 不能据此直接使用 w 保存的裸地址。
}
```

这叫 TOCTOU（check time 与 use time 之间状态改变）。正确方式是调用 `lock()` 并把返回的 `SharedPtr` 保存在局部变量中；局部强引用会在整个使用期间让对象保持存活。

## 15. `lock()` 为什么一定要 CAS 循环

[第 376–385 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:376)的逻辑是：

```text
读当前 strong 为 cur
只要 cur != 0：尝试用 CAS 将 cur 原子改为 cur + 1
  成功：已经“安全续命”，构造 SharedPtr 返回
  失败：cur 被更新为最新值，重试
读到 0：返回空 SharedPtr
```

不能写成 `if (strong > 0) strong++`：检查到自增之间，最后一个 `SharedPtr` 可能把 strong 减到 0 并删除对象；之后再加一就等于“复活一个已死亡对象”。CAS 将“尚存活才加一”合为一个不可分割的动作。

成功后它调用私有构造函数[第 274–276 行](../modules/A2_smart_pointers/include/smart_ptr.hpp:274)。该构造函数**不再增加 strong**，因为 CAS 已经完成那次增加；再加一次会泄漏。

## 16. 最后一个 `WeakPtr` 的职责

[`release_weak_()`](../modules/A2_smart_pointers/include/smart_ptr.hpp:396)只递减 weak；返回旧值为 1 时当前对象是最后一位观察者，负责删除控制块。它绝不能再次删除 `T`：`T` 的唯一销毁位置是最后一个 `SharedPtr` 的 `release_()`。

# 面试时可顺着讲出的 8 个追问

1. **`shared_ptr` 的计数为什么必须在控制块里？** 因为对象可来自不可修改的第三方类型，且对象死后 weak 仍需查看计数；多个包装器也必须共享同一份状态。
2. **`shared_ptr` 线程安全吗？** 不同 `SharedPtr` 副本对控制块计数的增减可并发；被管理对象本身不是线程安全的；并发读写同一个 `SharedPtr` 实例仍需同步（或使用相应原子包装）。
3. **`weak_ptr::expired()` 后能直接访问吗？** 不能；用 `if (auto s = w.lock())`，因为 lock 原子地检查并增加 strong。
4. **为什么循环引用会泄漏？** 环内每个对象至少被对方强持有一次，所有外部强引用消失后 strong 仍不为 0；把非拥有/反向边改为 weak。
5. **`make_shared` 与 `shared_ptr(new T)`？** 常见实现前者合并对象/控制块分配，分配更少且异常安全；但 weak 长存时整块内存通常晚些释放，后者则更易定制删除器。
6. **为什么不让所有对象都用 `shared_ptr`？** 共享所有权会模糊责任、引入控制块与原子计数成本、制造循环引用风险。默认独占，只有真实共享生命周期才使用。
7. **为什么 `shared_ptr<T>(this)` 危险？** 它通常另建一个控制块；原有控制块和新控制块都会以为自己独占删除权，导致 double free。需要 `enable_shared_from_this`。
8. **`unique_ptr` 能放进 `vector` 吗？** 能。它不可拷贝但可 `noexcept` 移动；扩容会移动指针所有权，T 对象地址不变。

# 这份教学实现与生产级 `std` 智能指针的差距

这不是缺点，而是手写题主动说明边界的机会：

| 缺失/简化项 | 本实现的现状 | 生产实现需要考虑 |
| --- | --- | --- |
| 构造异常安全 | `SharedPtr(T*)` 分配控制块失败会泄漏 T | 捕获后 delete T，或使用 `make_shared` |
| 分配次数 | `MakeShared` 仍是对象 + 控制块两次分配 | 合并分配与 allocator 支持 |
| 删除器与数组 | 固定 `delete ptr_` | 自定义 deleter、`T[]` 特化、`get_deleter` |
| 多态转换 | 只支持同类型 `T` | converting ctor、aliasing ctor、cast helpers |
| `enable_shared_from_this` | 未实现 | 防止成员函数中二次建立控制块 |
| 并发接口 | 只保证控制块计数的基本原子性 | `atomic<shared_ptr>`、完整内存序与实现细节 |
| 调试能力 | 无 | owner 比较、调试 hook、泄漏诊断 |

最重要的结论是：**手搓实现的价值是理解所有权与控制块，不是替代标准库。实际项目优先使用 `std::unique_ptr`、`std::shared_ptr` 和 `std::weak_ptr`。**
