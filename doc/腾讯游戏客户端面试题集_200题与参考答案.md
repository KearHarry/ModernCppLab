## 一、C++ 语言、内存与 STL（40 题）

### Q001. 指针和引用有什么区别？参数应该怎样选择？

**定位：** P0 · 补充题。

**参考答案：** 指针是保存地址的对象，可以为空、重新赋值，并在合法范围内做指针运算；引用是对象或函数的别名，必须初始化，绑定后不能改绑。小型廉价类型通常按值传递；只读大对象用 `const T&`；需要表达可选对象时可用指针；明确转移所有权时用值或智能指针表达。引用本身不延长任意被引用对象的生命周期。

**易错点：** “引用一定不占内存”属于实现层面的过度概括；引用也可能悬空。

### Q002. const、constexpr 和 static 分别解决什么问题？

**定位：** P0 · 补充题。

**参考答案：** `const` 限制通过该访问路径修改对象；`constexpr` 变量要求常量表达式初始化，`constexpr` 函数满足条件时可以参与常量求值，但也能运行时执行。`static` 含义依位置变化：局部变量获得静态存储期，类成员由类共享，命名空间级变量或函数通常获得内部链接。`const T*` 限制经指针修改目标，`T* const` 限制指针改指向。

**易错点：** `const` 不等于编译期常量，也不自动提供跨线程同步。

### Q003. new/delete 与 malloc/free 有什么区别？

**定位：** P0 · 面经题意 [M08]。

**参考答案：** `new` 表达式取得存储后进行对象初始化，`delete` 表达式销毁对象并释放存储；`malloc/free` 主要管理原始内存，不自动调用 C++ 构造与析构。普通 `new` 失败通常抛出 `std::bad_alloc`，`malloc` 失败返回空指针。`new[]` 必须与 `delete[]` 配对。还要区分 `new` 表达式与可重载的分配函数 `operator new`。

**易错点：** 不能混用两套释放接口；分配了一块足够大的内存，不代表任意非平凡类型已经完成构造。

### Q004. RAII 是什么？它为什么适合游戏客户端资源管理？

**定位：** P0 · 补充题。

**参考答案：** RAII 将资源所有权绑定到对象生命周期：成功构造后维持有效状态，在析构中释放。资源可以是内存、文件、锁、网络连接或图形资源句柄。作用域退出和异常展开会触发局部对象析构，因此可以用 `unique_ptr`、容器和锁守卫减少遗漏释放。对于 GPU 资源，析构还可能需要把实际释放延迟到对应命令执行完毕。

**易错点：** RAII 解决所有权与清理时机，不意味着所有资源都能在任意线程立即销毁。

### Q005. 深拷贝、浅拷贝、三法则、五法则和零法则是什么？

**定位：** P0 · 补充题。

**参考答案：** 浅拷贝复制成员值，若成员是拥有资源的裸指针，两份对象可能误以为各自拥有同一资源；深拷贝按业务语义复制独立资源。三法则关注析构、拷贝构造和拷贝赋值，五法则再考虑移动构造与移动赋值。零法则推荐把所有权交给容器和 RAII 成员，让编译器生成合适操作；不可复制资源则明确禁用拷贝。

**易错点：** 共享资源有时正是预期语义，不能把所有浅拷贝都判为错误。

### Q006. 左值、右值与移动语义的关系是什么？

**定位：** P0 · 面经题意 [M01]。

**参考答案：** C++ 表达式分为左值、纯右值和将亡值；将亡值与纯右值合称右值。移动语义使类型能从允许转移资源的源对象接管资源，而非昂贵复制。`T&&` 是一种引用类型，但有名字的右值引用变量作为表达式仍是左值。移动后的标准库对象通常保持有效但未指定的状态，具体操作还要满足类型契约。

**易错点：** 不能凭“有没有名字”完整判断值类别，也不能假定移动后所有对象都自动清空。

### Q007. std::move 和 std::forward 会真正搬动数据吗？

**定位：** P0 · 补充题。

**参考答案：** 两者本质上都执行类型转换。`std::move` 把表达式转换为可供移动重载匹配的将亡值；真正转移资源的是随后被选中的移动操作。`std::forward<T>` 根据推导出的 `T` 保留调用方值类别，常用于转发引用。只有特定推导场景中的 `T&&` 才是转发引用，不能把所有双引用符号都这样理解。

**易错点：** `std::move(constObject)` 通常无法匹配需要非 const 源的移动构造，可能仍发生拷贝。

### Q008. 返回局部对象会拷贝吗？noexcept 为什么影响容器扩容？

**定位：** P1 · 补充题。

**参考答案：** C++17 对特定纯右值返回提供保证的拷贝消除；具名局部对象的 NRVO 一般仍是允许的优化，不能混为一谈。直接 `return local;` 通常能利用 NRVO 或适用的移动规则，乱加 `std::move` 反而可能阻止 NRVO。扩容时，容器为了异常保证，可能在移动可抛异常而拷贝可用时选择拷贝。

**易错点：** `noexcept` 是承诺，函数实际抛出并越过该边界会导致终止，不能只为“优化”随意添加。

### Q009. C++ 动态多态如何实现？虚表什么时候产生？

**定位：** P0 · 面经题意 [M01]、[M08]。

**参考答案：** 通过基类指针或引用调用虚函数，语言语义会选择对象相应的最终重写版本。主流 ABI 常用虚表和对象中的虚表指针实现，表数据通常由编译、链接阶段生成，构造过程设置相应指针。多继承可能出现多张表、指针调整和跳板；优化器也可能去虚拟化。标准规定行为，不强制某一种虚表布局。

**易错点：** 不要把“每个对象复制一整张虚表”或“虚表一定在某固定内存区”当成标准结论。

### Q010. 基类析构函数为什么经常要声明为 virtual？

**定位：** P0 · 面经题意 [M09]。

**参考答案：** 当对象需要通过基类指针执行普通多态删除时，基类通常应有虚析构，保证派生部分与基类部分按正确顺序销毁，否则这类删除会产生未定义行为。接口设计常选择“公有虚析构”，或“受保护非虚析构”来禁止经基类删除。析构顺序与构造相反：派生类析构体先执行，再销毁成员和基类子对象。

**易错点：** 不是所有类都必须有虚析构；纯虚析构函数也需要定义。

### Q011. 构造函数中调用虚函数，会调用派生类版本吗？

**定位：** P1 · 面经题意 [M09]。

**参考答案：** 在基类构造或析构期间，对当前对象的虚调用按当前正在构造或析构的类处理，不会进入尚未构造或已经销毁的更派生部分。构造函数不能是虚函数。安全做法是构造阶段只建立本层不变量，需要派生扩展时采用构造完成后的显式初始化或工厂流程。相关规则见 [C++ 构造与析构期间的虚调用][T01]。

**易错点：** 不要从构造函数中依赖纯虚函数的动态调用；这不是实现多态初始化的可靠方法。

### Q012. 重载、重写与名字隐藏有什么不同？

**定位：** P0 · 面经题意 [M01]，补充名字隐藏。

**参考答案：** 重载是在同一查找范围内使用相同函数名和不同参数列表，由重载决议选中；重写是派生类提供匹配基类虚函数的实现；隐藏发生在派生类声明同名成员时，可能使基类的其他重载不可直接找到。使用 `override` 让编译器验证重写，用 `using Base::f` 引入需要的基类重载。

**易错点：** 仅返回类型不同不能构成普通函数重载；参数或成员函数 const 限定不匹配可能没有重写成功。

### Q013. 菱形继承有什么问题？虚继承怎样解决？

**定位：** P1 · 补充题。

**参考答案：** 普通菱形继承可能让最终对象包含两份公共基类子对象，导致状态重复和名字访问歧义。虚继承让经相关路径继承的虚基类子对象共享一份，由最派生类负责初始化。代价包括更复杂的布局、访问调整和构造规则；具体开销取决于 ABI。设计游戏实体时，组件组合常比深层继承更容易扩展。

**易错点：** 虚继承与虚函数是两套机制；虚继承也不能消除所有成员函数重写歧义。

### Q014. struct 与 class 有什么区别？类大小如何估算？

**定位：** P0 · 补充题；对齐主题见 [M06]。

**参考答案：** C++ 中两者的核心区别是默认成员访问权限和默认继承权限，`struct` 默认 public，`class` 默认 private。估算对象大小需要考虑非静态成员、基类子对象、对齐填充，以及实现可能引入的虚表指针；静态成员不逐对象存储。完整空类对象大小至少为 1，但空基类优化等情形不能机械套用。

**易错点：** 不能简单把所有成员大小相加；过度压缩结构体可能带来未对齐访问，且不等于可移植序列化。

### Q015. C++ 四种命名类型转换应该怎样使用？

**定位：** P0 · 补充题。

**参考答案：** `static_cast` 用于有语言规则支持的转换，但向下转型不提供动态类型检查；`dynamic_cast` 可对多态类型执行运行时检查，指针失败返回空，引用失败抛异常；`const_cast` 调整 const/volatile 限定；`reinterpret_cast` 用于低层表示转换。转换后可否合法访问，还受对象生命周期、对齐和别名规则限制。

**易错点：** 去掉 const 后修改原本就是 const 的对象是未定义行为；转换成功不等于解引用安全。

### Q016. Lambda 捕获怎样导致悬空和意外延长生命周期？

**定位：** P0 · 面经题意 [M01]，补充异步场景。

**参考答案：** Lambda 可看作带状态的闭包对象，值捕获保存副本，引用捕获关联外部对象。异步回调可能晚于局部变量销毁，引用捕获因而悬空。捕获 `this` 通常只保存指针，不保活对象；捕获 `shared_ptr` 能保活但可能形成引用环。观察型回调用 `weak_ptr`，执行时 `lock()` 得到强引用并检查有效性。

**易错点：** `[=]` 不意味着异步操作涉及的一切都已经被深拷贝；指针的副本仍指向原对象。

### Q017. 模板为什么通常把实现写在头文件里？

**定位：** P1 · 补充题。

**参考答案：** 模板通常在实例化时需要看到定义，调用处只有声明而无法生成所需实例时，可能在链接时报未定义符号。因此常将定义放在头文件或其包含的实现文件中。若支持的类型集合固定，可以在源文件显式实例化，并配合声明控制生成。模板带来类型安全和静态优化机会，也可能增加编译时间与代码体积。

**易错点：** “模板绝对不能声明与定义分离”太绝对；关键是实例化点的定义可见性或显式实例化安排。

### Q018. inline 与宏有什么区别？inline 一定展开吗？

**定位：** P0 · 面经题意 [M02]、[M07]。

**参考答案：** 宏进行预处理层面的文本替换，缺少普通函数的类型与作用域规则，参数可能被重复求值。内联函数仍是函数，经过类型检查；`inline` 还涉及允许在多个翻译单元中出现满足规则的定义。编译器是否把调用展开由优化决策决定，不保证遵从关键字。展开可能减少调用成本，也可能增加指令缓存压力。

**易错点：** 不要把内联的收益概括为“一定消除所有参数拷贝”。

### Q019. vector 怎样扩容？push_back 为什么是均摊 O(1)？

**定位：** P0 · 面经题意 [M10]。

**参考答案：** `vector` 保持元素连续存储；容量不足时申请更大的存储，将已有元素移动或拷贝过去，再释放旧存储。单次扩容是 O(n)，采用合适的几何增长策略后，连续尾插的总搬迁量与元素数同阶，因此均摊 O(1)。增长倍率由实现决定，标准没有规定必须翻倍。

**易错点：** 不能将 `capacity` 当作已有对象数量，也不能忽略扩容时保存的元素指针失效。

### Q020. reserve、resize、clear 和 shrink_to_fit 有什么区别？

**定位：** P0 · 补充题。

**参考答案：** `reserve(n)` 预留容量，不增加有效元素；`resize(n)` 改变元素数，必要时构造新元素或销毁尾部元素；`clear()` 销毁所有元素但保留容量；`shrink_to_fit()` 请求收缩容量，标准不保证请求必被执行。高频复用的临时数组可预留容量并清空重用，避免反复分配。

**易错点：** `reserve(100)` 后仍不能直接写入 `v[99]`，除非 `size()` 已覆盖该索引。

### Q021. vector 插入和删除后，哪些迭代器会失效？

**定位：** P0 · 补充题。

**参考答案：** 重新分配会使所有元素指针、引用、迭代器以及旧 `end()` 失效。不扩容的插入使插入点及之后的迭代器和引用失效；删除使删除点及之后的迭代器和引用失效。边遍历边删除应接收 `erase` 返回的下一个迭代器，或使用移除后统一擦除的模式。规则见 [vector 修改操作][T02]。

**易错点：** 预留了足够容量也不代表所有修改都安全，尤其是旧 `end()` 和中间插入、删除。

### Q022. vector、list、deque 在游戏中如何选择？

**定位：** P0 · 补充题。

**参考答案：** `vector` 连续、随机访问快，适合大量顺序遍历；`list` 通常是双向链表，已知节点位置时插删成本低，但定位节点、分配和缓存未命中的成本较高；`deque` 通常分段存储，支持 O(1) 随机访问和高效两端操作，但不保证整块连续。游戏实体热数据通常优先考虑数组布局，再依据稳定地址和更新方式选择其他结构。

**易错点：** “链表插入 O(1)”的前提是已经找到位置，不代表整个业务操作 O(1)。

### Q023. map 与 unordered_map 的实现和复杂度有什么差异？

**定位：** P0 · 面经题意 [M06]、[M07]。

**参考答案：** `map` 按比较器保持键的顺序，通常用红黑树实现，查找、插入、按键删除为 O(log n)；`unordered_map` 使用哈希组织，平均查找与更新 O(1)，最坏可能 O(n)。有范围查询、排序遍历或稳定最坏界需求时考虑有序容器；只按键查找可考虑哈希容器，同时关注内存、负载因子和哈希质量。

**易错点：** 红黑树是常见实现，不是标准强制的唯一实现；哈希容器不是永远 O(1)。

### Q024. 哈希冲突怎样解决？rehash 有什么代价？

**定位：** P0 · 面经题意 [M09]，补充 rehash。

**参考答案：** 常见方法有链式处理和开放寻址，后者需要探测序列与删除标记。哈希函数应分布均匀，并满足相等键具有相同哈希值。负载因子过高会拉长查找路径，rehash 通过重建桶分布改善性能，但会造成一次性搬运或重链接。`unordered_map` rehash 会使迭代器失效，但不因此使已有元素的指针和引用失效。

**易错点：** 桶数取质数只是某些策略的一部分，不能解决差哈希函数的全部问题。

### Q025. 红黑树和 AVL 树有什么区别？

**定位：** P1 · 面经题意 [M09]。

**参考答案：** 两者都是维持 O(log n) 高度的平衡搜索树。AVL 严格限制左右子树高度差，查找路径通常更短，但更新时可能需要较多平衡维护。红黑树通过颜色与黑高规则保持较宽松的平衡，适用于读写混合场景。具体性能仍受节点布局、分配器、缓存和数据分布影响。

**易错点：** 不能简单断言“红黑树在所有插入删除中旋转都更少，所以一定更快”。

### Q026. unique_ptr、shared_ptr、weak_ptr 应怎样选择？

**定位：** P0 · 面经题意 [M06]。

**参考答案：** 默认优先明确唯一所有权，使用 `unique_ptr`，需要转移时移动它。确有多个独立所有者共同决定生命周期时使用 `shared_ptr`；仅观察一个共享对象而不保活时使用 `weak_ptr`，访问前调用 `lock()`。智能指针是所有权表达，不应把所有借用参数都改成共享所有权。观察同步调用中的对象时，裸指针或引用仍然合理。

**易错点：** 同一个裸指针分别构造两个独立 `shared_ptr` 会形成两份控制块，可能重复删除。

### Q027. shared_ptr 的线程安全到底保证到哪里？

**定位：** P0 · 补充题。

**参考答案：** 不同 `shared_ptr` 实例共享同一控制块时，可以在不同线程独立拷贝、销毁，控制块的共享所有权维护受到保护。但对同一个 `shared_ptr` 变量的并发非 const 访问需要同步，可使用锁或 C++20 `atomic<shared_ptr<T>>`。被管理的 `T` 对象也不因此线程安全，仍需自己的同步方案。参见 [shared_ptr 标准条款][T03]。

**易错点：** `use_count()==1` 不是并发场景下可无锁修改对象的普遍证明。

### Q028. weak_ptr 如何解决循环引用？对象和控制块何时销毁？

**定位：** P1 · 补充题。

**参考答案：** 若 A 与 B 互持强引用，外部所有者释放后强计数仍不归零。把非所有权方向改为弱引用，便可打破环。最后一个强所有者释放时销毁被管理对象；控制块还需供弱引用查询，等相关弱引用也不再需要时才能释放。`weak_ptr::lock()` 以安全方式尝试获得强所有权，失败返回空共享指针。

**易错点：** 先 `expired()` 再另行取得对象会留下竞态窗口，应直接使用 `lock()` 的结果。

### Q029. make_shared 有什么优点和取舍？

**定位：** P1 · 补充题。

**参考答案：** 主流实现通常把对象与控制块合并分配，减少分配次数并改善局部性，同时避免直接暴露裸所有权。代价是对象析构后，如果弱引用仍存活，合并分配的整块存储可能继续保留；它也不像某些 `shared_ptr` 构造方式那样直接接受自定义删除器。大对象、特殊分配器和资源销毁线程要求都应单独考虑。

**易错点：** “对象已析构”和“承载对象的分配块已归还”不是同一回事。

### Q030. placement new、内存池与对象池有什么关系？

**定位：** P1 · 面经题意 [M08] 的内存池主题，补充对象生命周期。

**参考答案：** 内存池预先管理存储块，减少通用分配器开销与某些碎片；placement new 在已有且正确对齐的存储中构造对象，不负责再申请普通堆内存。对象池可进一步复用已经创建的对象，但必须重新建立业务状态。释放时分清“调用析构”和“把存储还给池”，按类型与池的契约执行。

**易错点：** 对使用 placement new 构造在池内存中的对象，不能随意用普通 `delete` 释放。

### Q031. 悬空指针、内存泄漏、重复释放怎样定位？

**定位：** P0 · 补充题。

**参考答案：** 悬空是对象生命周期结束后仍保留可访问路径；泄漏是资源不再有用途却无法回收；重复释放是同一所有权被多次执行清理。先记录创建、所有权转移与释放路径，使用可用平台上的地址检查器、泄漏检查器、调试堆和崩溃栈定位首次错误，再通过 RAII、代际句柄或明确的观察关系修复根因。

**易错点：** 释放后把某个指针设为空，只清理该变量，其他别名仍可能悬空。

### Q032. C++ 异常安全有哪些级别？

**定位：** P1 · 补充题。

**参考答案：** 常见分为不抛异常保证、强保证和基本保证：分别表示操作不抛出、失败时状态回滚到调用前、失败后仍保持不变量且不泄漏。可以先在临时对象上完成可能失败的工作，再用不抛异常的交换提交。析构通常不应让异常逸出，尤其在异常展开期间再次抛出会导致终止。

**易错点：** 捕获所有异常却留下半更新状态，并不等于实现异常安全。

### Q033. C++ 从源代码到程序执行经历哪些步骤？

**定位：** P0 · 补充题；相近编译主题见 [M07]。

**参考答案：** 预处理展开包含和宏；编译进行语法、语义分析并生成目标表示；汇编生成目标文件；链接解析符号、重定位并组合所需代码与数据。启动程序时，加载器映射可执行文件和依赖库，运行必要初始化，再进入入口逻辑。编译失败看类型与声明，链接失败重点看定义、链接配置和 ABI。

**易错点：** 头文件通常通过包含参与翻译单元处理，不是默认单独编译后自动链接。

### Q034. ODR、声明与定义、extern "C" 分别是什么？

**定位：** P1 · 补充题。

**参考答案：** 声明告诉编译器名字及类型，定义提供函数体或相应实体。ODR 规定实体在不同场景下能有多少定义以及一致性要求，头文件中的非 inline 普通函数定义容易造成重复定义。`extern "C"` 指定语言链接，常用于 C 接口互操作与抑制 C++ 名字改编；它不会把函数体自动转换为 C 代码，也不能让任意 C++ 类型成为跨语言 ABI。

**易错点：** “声明可以无限重复”也要满足一致性规则；模板与 inline 的多定义有严格条件。

### Q035. 静态库、动态库和 ABI 兼容应注意什么？

**定位：** P1 · 补充题。

**参考答案：** 静态链接通常把需要的目标代码并入结果；动态链接通过共享库在装载或运行时解析接口。ABI 包括调用约定、名字改编、类型布局、异常和运行库约定。插件边界宜使用明确版本、稳定布局的接口，并让分配与释放在兼容的所有权边界中配对。修改结构体布局或混用不兼容运行库都可能破坏二进制兼容。

**易错点：** 能成功链接不代表生命周期、异常传播和跨模块释放都安全。

### Q036. auto、decltype 和 decltype(auto) 有什么区别？

**定位：** P1 · 补充题。

**参考答案：** 普通按值 `auto` 推导通常移除顶层 const 与引用，而 `auto&`、`auto&&` 会表达不同绑定方式。`decltype` 按表达式规则推导；对未加括号的变量名通常得到声明类型，对一般左值表达式得到引用类型。`decltype(auto)` 沿用这些规则，能保留返回引用，也更容易不小心返回悬空引用。

**易错点：** `decltype(x)` 与 `decltype((x))` 可能不同；括号会改变推导语义。

### Q037. std::function、函数指针与模板回调如何取舍？

**定位：** P1 · 补充题。

**参考答案：** 函数指针轻量，但不能直接携带任意捕获状态；模板接收可调用对象时有利于静态优化，但可能增加实例化数量；`std::function` 以类型擦除提供统一接口，可能发生分配和间接调用。热路径可优先具体可调用类型，跨模块或异构回调集合则权衡类型擦除的便利与代价。

**易错点：** 小对象优化是否发生及容量大小由实现决定，不能承诺 `std::function` 从不分配。

### Q038. string_view 和 span 为什么快，又为什么危险？

**定位：** P1 · 补充题。

**参考答案：** 它们是不拥有底层数据的视图，通常保存地址与长度，便于传递子串或连续数组而不复制。速度收益来自减少分配和复制，但视图不会保活源数据，源对象销毁、容器扩容或缓冲区复用都可能使其失效。`string_view` 表示的片段也不保证以零字符结尾。

**易错点：** 不要返回指向局部字符串的视图，也不要直接把任意 `string_view::data()` 当成 C 字符串。

### Q039. 为什么不能对所有 C++ 对象使用 memcpy 或 memset？

**定位：** P0 · 补充题。

**参考答案：** 字节复制不执行类型的拷贝语义，对拥有资源、含虚机制或其他非平凡状态的对象可能破坏不变量。平凡可复制类型在满足对象与存储条件时可进行相应字节复制，但跨平台序列化仍需处理填充、字节序和版本。`memset(0)` 也不等于按类型规则初始化，不能普遍替代构造。

**易错点：** 标准不普遍保证全零字节就表示所有指针类型的空指针，不能据常见机器经验推广。

### Q040. C++20 协程是不是线程？协程帧由谁管理？

**定位：** P2 · 补充题。

**参考答案：** C++20 协程是可挂起和恢复的函数机制，编译器保存跨挂起点需要的状态形成协程帧；调度到哪个线程由使用的库和执行器决定。返回对象、promise 与句柄共同构成生命周期协议，必须明确谁恢复、取消和销毁帧。协程可能申请帧存储，部分场景能被优化消除。

**易错点：** 把局部引用传入会挂起的协程并不自动保活被引用对象；重复恢复或过早销毁句柄可能出错。

## 二、C# 与 .NET 基础（25 题）

### Q041. 值类型与引用类型的本质区别是什么？

**定位：** P0 · 补充题。

**参考答案：** 值类型变量直接包含相应值，默认赋值或传参复制这个值；引用类型变量保存对象引用，复制引用后两个变量可访问同一对象。值类型不等于“必在栈上”：它可以作为类字段、数组元素或装箱值存在于托管堆中。结构体含引用字段时，复制结构体只复制该引用，不递归复制目标。参见 [C# 值类型][T04]。

**易错点：** 区分类别的关键是语义，不能只背“值类型栈、引用类型堆”。

### Q042. 什么是装箱和拆箱？怎样减少它们？

**定位：** P0 · 补充题。

**参考答案：** 将值类型转换成 `object` 或某些接口表示会发生装箱，概念上产生保存值副本的托管对象；拆箱检查实际类型并取出值。`List<int>` 通常比 `ArrayList` 更能避免元素装箱，泛型约束也有机会避免经接口装箱。是否发生分配需结合生成代码和运行时优化检查。参见 [装箱与拆箱][T05]。

**易错点：** 对装箱的 `int` 直接做 `(long)obj` 不是先拆成 int 再数值转换；应明确分成两步。

### Q043. C# struct 与 class 应如何选择？

**定位：** P0 · 补充题。

**参考答案：** 适合独立值语义、体积较小、最好不可变的数据，可考虑 struct，例如坐标与配置键；需要共享身份、继承和复杂生命周期的对象通常用 class。大结构体按值传递和复制可能昂贵，结构体中的引用成员也仍需理解共享关系。不能把所有 class 都改成 struct 作为通用 GC 优化。

**易错点：** 从属性或集合索引取得结构体时常得到副本，修改副本未必更新原容器里的值。

### Q044. ref、out、in 与普通传参有什么不同？

**定位：** P0 · 补充题。

**参考答案：** 普通传参复制参数值，对引用类型则复制对象引用。`ref` 把变量按引用传递，调用方先初始化，方法可读写；`out` 要求方法正常返回前赋值，调用前不要求有值；`in` 提供只读引用传参，可减少大值类型的复制，但编译器某些情况下会创建临时值或防御性副本。

**易错点：** 把 class 作为普通参数传入可以修改对象，却不能仅靠给参数重新赋值来替换调用方变量。

### Q045. const、readonly、static readonly 应怎样选？

**定位：** P0 · 补充题。

**参考答案：** `const` 是编译期常量，值可能被嵌入使用它的程序集；`readonly` 字段可在声明或相应构造阶段赋值；`static readonly` 是类型共享、运行时初始化后不再改写的字段。跨程序集会变化的配置不适合随意暴露为 public const，否则只替换库可能无法更新消费者已编译的常量。

**易错点：** readonly 引用不能改指向，不代表被引用对象的内部状态不可修改。

### Q046. string 为什么不可变？StringBuilder 是否永远更快？

**定位：** P0 · 补充题。

**参考答案：** 字符串内容在对象创建后不再被正常 API 修改，因此可安全共享，拼接等操作通常生成新结果。循环进行大量逐步追加时，可预估容量并使用 `StringBuilder`，减少中间字符串；少量固定拼接可能被编译器和运行库高效处理，没有必要机械替换。热路径还可避免每帧重复格式化相同 UI 文本。

**易错点：** `StringBuilder.ToString()` 仍需形成结果字符串；缓存构建器也要控制容量，避免长期保留巨型缓冲区。

### Q047. ==、Equals、ReferenceEquals 和 GetHashCode 有什么关系？

**定位：** P0 · 补充题。

**参考答案：** `ReferenceEquals` 检查是否同一对象引用；`==` 可以被重载，其含义与静态类型和运算符定义有关；`Equals` 用于类型定义的相等语义。若两个值按相等比较器相等，必须得到相同哈希值；哈希相同不保证相等。自定义字典键应一致实现相等和哈希，并避免插入后改变参与比较的字段。

**易错点：** 普通 C# 规则不能直接替代 UnityEngine.Object 的特殊空值比较，后者见 Q117。

### Q048. 委托和事件有什么区别？

**定位：** P0 · 补充题。

**参考答案：** 委托是类型安全的可调用对象，可保存方法与目标对象，多播委托维护调用列表。`event` 在委托机制上限制外部操作：使用者通常只能订阅、退订，不能随意覆盖或触发发布者的事件。事件适合通知“发生了什么”，返回业务结果的请求更适合显式方法或服务接口。

**易错点：** 多播委托调用中某处理器抛异常，若发布者不隔离，后续处理器可能不会执行。

### Q049. 事件为什么会造成托管内存泄漏？

**定位：** P0 · 补充题。

**参考答案：** 发布者的委托列表通常保留订阅对象的强引用。如果全局服务比界面活得更久，而界面关闭后没有退订，界面仍从 GC 根可达，不能被回收。应按设计在退出、禁用或销毁阶段解除订阅；使用匿名函数时保存可退订的委托实例，或采用生命周期绑定的订阅令牌。参见 [事件订阅与退订][T06]。

**易错点：** 再写一个外观相同的捕获 Lambda 进行 `-=`，不一定能移除原来的处理器。

### Q050. 闭包捕获的是当时的值还是变量？

**定位：** P0 · 补充题。

**参考答案：** C# 闭包捕获变量，其存储可被提升到闭包对象中，后续修改会影响回调读取的结果。`for` 循环共用一个迭代变量时，延迟回调可能都看到循环结束值；需要每轮独立局部变量时应明确复制。现代 C# 的 foreach 迭代变量捕获规则与早期版本不同，不能照搬旧结论。参见 [Lambda 与捕获][T07]。

**易错点：** 闭包还可能延长整个对象图的生命周期，尤其是无意捕获 `this` 的长期回调。

### Q051. 泛型解决什么问题？where 约束有什么意义？

**定位：** P0 · 补充题。

**参考答案：** 泛型在复用代码的同时保持类型信息，使容器和算法不必普遍退化成 object，减少显式转换及某些装箱。约束说明类型必须满足的能力，例如接口、基类或构造要求，便于编译器验证可用操作。不同运行时对泛型代码共享与实例化的实现不同，在 Unity AOT 环境还要关注泛型实例生成和裁剪。

**易错点：** C# 泛型与 C++ 模板不是同一实现机制，不能照搬“所有类型都生成一整份代码”的结论。

### Q052. Array、List<T>、LinkedList<T> 和 Dictionary 如何选择？

**定位：** P0 · 补充题。

**参考答案：** Array 长度固定且索引访问直接；`List<T>` 提供动态数组，尾部添加均摊高效但扩容要复制元素；`LinkedList<T>` 在已有节点位置时便于插删，却增加节点分配和间接访问；Dictionary 适合按键平均常数时间查询。游戏热数据优先考虑连续布局，并根据预估数量设置初始容量。

**易错点：** 即使某运行时看起来按插入顺序遍历 Dictionary，也不应把未由接口契约承诺的顺序作为玩法逻辑依赖。

### Q053. foreach 一定比 for 慢、一定产生 GC 吗？

**定位：** P0 · 补充题。

**参考答案：** 不一定。数组遍历和具体 `List<T>` 的结构体枚举器常可避免枚举器堆分配；转成接口枚举、使用迭代器或自定义枚举实现则可能产生分配或装箱。性能取决于静态类型、枚举器、循环体和运行时优化，应在实际 Unity 后端测量。优先保证逻辑清晰，只优化证实的热点。

**易错点：** 性能问题可能来自循环体中的字符串、闭包和查询，不能看到 foreach 就直接归因。

### Q054. IEnumerable、IEnumerator 和 yield return 分别是什么？

**定位：** P0 · 补充题。

**参考答案：** IEnumerable 表达“可获得枚举器的序列”，IEnumerator 表达一次遍历的状态，通过 `MoveNext` 前进并读取 `Current`。`yield return` 让编译器生成保存执行位置与局部状态的迭代器，按需产出元素。Unity 协程使用相近的迭代器机制，但还由引擎解释 yield 的对象和调度时机。

**易错点：** 返回 IEnumerable 不等于数据已经计算完成；重复遍历可能再次执行查询和副作用。

### Q055. LINQ 的延迟执行会带来哪些问题？

**定位：** P1 · 补充题。

**参考答案：** 许多 LINQ 操作描述查询，直到枚举才执行；源数据改变、捕获变量改变或重复遍历，都可能改变结果与成本。`ToList()` 等物化操作固定当时的结果，但需要分配和存储。复杂链式查询也可能创建迭代器、闭包或中间结构。一般业务代码可重可读性，帧循环中的热点应测量后选用复用缓冲区或直接循环。

**易错点：** 延迟执行不是免费执行，也不能把所有 LINQ 操作都认为是延迟的。

### Q056. 普通 .NET 的 GC 怎样判断对象可以回收？

**定位：** P0 · 补充题。

**参考答案：** GC 从线程栈中的活跃引用、静态字段、运行时句柄等根出发遍历对象图，不再可达的对象才具备回收条件。典型 .NET GC 按代组织对象，基于多数对象寿命短的观察减少部分扫描工作，也有大对象堆和不同回收模式。具体暂停、压缩与并发行为依运行时配置而定。参见 [.NET GC 基础][T08]。

**易错点：** “离开作用域立即释放”不适用于普通托管对象；此题不能直接作为 Unity GC 的答案，见 Q119。

### Q057. 有 GC 为什么还会内存泄漏？终结器能解决吗？

**定位：** P0 · 补充题。

**参考答案：** GC 回收不可达对象，不知道业务是否还需要对象。无上限缓存、静态集合、事件订阅和未结束任务都可能让无用对象继续可达。托管包装持有的原生资源也可能需要显式释放。终结器执行时机不确定，会增加生命周期管理成本，不能代替及时释放；进程退出等情况下也不能依赖它必然完成关键业务。

**易错点：** 手工 `GC.Collect()` 无法回收仍被强引用的对象，也不是常规修复泄漏的方法。

### Q058. IDisposable、using 与终结器是什么关系？

**定位：** P0 · 补充题。

**参考答案：** `IDisposable` 定义显式清理协议，`using` 会在离开相应作用域时通过类似 try/finally 的机制调用 Dispose。Dispose 通常释放文件、原生缓冲区等资源，不等于立即回收托管对象内存。拥有非托管资源时应优先使用合适的安全句柄；必要终结器只是后备清理，并与显式清理协调。参见 [using 语句][T09]。

**易错点：** 对象被提前 return 或发生异常时仍需清理，这正是 using 的价值；清理实现要考虑重复调用。

### Q059. async/await 如何工作？await 会阻塞当前线程吗？

**定位：** P0 · 补充题。

**参考答案：** 编译器把 async 方法转成状态机，保存跨等待点需要的状态。方法通常先在调用线程执行，遇到尚未完成的 awaitable 时注册后续逻辑并返回，完成后再恢复；已完成的等待可以同步继续。await 一般不会像 `.Wait()` 那样阻塞线程，恢复线程由上下文和调度规则决定。参见 [C# 异步编程][T10]。

**易错点：** async 不自动创建后台线程；await 前的重计算仍可能卡住 Unity 主线程。

### Q060. Task、Thread 与 Unity 协程如何选择？

**定位：** P0 · 补充题。

**参考答案：** Thread 是执行线程；Task 表达异步操作的完成与结果，不保证独占线程；Unity 协程由 PlayerLoop 在指定阶段推进。等待网络或文件应优先适用的异步 I/O；纯 CPU 工作可考虑线程池或 Job；分帧流程可用协程。涉及 Unity 对象的操作仍必须遵循相应 API 的线程约束。

**易错点：** 把耗时循环放进协程但不分段 yield，仍会阻塞执行它的主线程。

### Q061. 为什么慎用 async void？取消和异常怎样处理？

**定位：** P1 · 补充题。

**参考答案：** `async void` 缺少可被调用方 await 的任务结果，异常和完成状态更难组合处理，通常仅用于必须返回 void 的事件入口。业务异步方法优先返回 Task 或相应 awaitable，并在调用链明确观察异常。取消是协作协议，应检查令牌、清理资源，并确认底层操作是否真正支持取消。

**易错点：** “请求取消”不等于任务已经停止；界面销毁后还需防止完成回调使用失效对象。

### Q062. C# 的 lock、Interlocked 与 volatile 有什么区别？

**定位：** P0 · 补充题。

**参考答案：** lock 用于保护一段需要保持整体不变量的临界区；Interlocked 提供特定原子读改写操作，例如递增与比较交换；volatile 对支持类型的读写施加相应可见性与顺序规则，但不让多个步骤成为一个原子事务。计数器递增可用 Interlocked；余额扣减加库存更新等组合逻辑通常需要更完整的同步。

**易错点：** `volatile int` 的 `x++` 仍不是整体原子操作。参见 [C# volatile 说明][T11]。

### Q063. 反射与 Attribute 有什么用途？在 Unity 中有什么风险？

**定位：** P1 · 补充题。

**参考答案：** 反射在运行时查询类型、成员和元数据，也能动态调用；Attribute 把声明式元数据附加到代码上，本身不会自动执行业务。它们适合编辑器、序列化和注册系统，但频繁查找和调用可能有成本。Unity 的 AOT、托管裁剪可能使仅经反射访问的代码未保留，需要明确保留规则或生成代码，详见 Q145。

**易错点：** 不能说 IL2CPP 完全不支持反射；问题通常是动态代码生成限制、裁剪或所需实例缺失。

### Q064. Span<T>、Memory<T> 与普通数组有什么不同？

**定位：** P2 · 补充题。

**参考答案：** Span 表达连续内存的临时视图，可以减少切片复制；它是受引用安全规则限制的 ref struct，不能作为普通类字段长期保存，也不能任意跨挂起点存活。Memory 可作为更长生命周期或异步流程中的内存视图，再按需取得 Span。两者通常不拥有底层存储，池化缓冲区归还后视图也可能失效。

**易错点：** Unity 中可用的 API 与语言能力依版本和兼容级别而异，不能把最新 .NET 支持直接假定为项目支持。

### Q065. 接口和抽象类如何选择？

**定位：** P0 · 补充题。

**参考答案：** 接口适合表达能力契约，让彼此无继承关系的类型被统一使用；抽象类适合共享身份、状态和部分实现。类只能继承一个直接基类，但能实现多个接口。游戏中可用 `IDamageable` 表达可受伤能力，用抽象角色基类共享确实稳定的逻辑；优先避免把不相关功能塞进庞大基类。

**易错点：** 新版 C# 有默认接口实现等能力，不能永远概括为“接口绝对不能有实现”，还要核对目标运行时支持。

## 三、操作系统与并发（15 题）

### Q066. 进程、线程、协程有哪些本质区别？

**定位：** P0 · 面经题意 [M05]。

**参考答案：** 进程提供地址空间与资源隔离边界；线程是操作系统调度的执行流，同进程线程共享大部分进程资源；协程保存用户态执行状态并按运行时规则协作切换。进程隔离较强但通信更复杂，线程共享方便但需同步，协程适合组织大量等待流程。是否并行取决于实际执行线程与处理器资源。

**易错点：** “协程比线程快”不是完整答案，应说明切换、等待方式、调度与负载条件。

### Q067. 同一进程中的线程共享哪些资源？

**定位：** P0 · 面经题意 [M01]。

**参考答案：** 通常共享代码、全局数据、堆和已映射资源；各自有寄存器状态、执行栈和线程局部存储。线程栈各有自己的使用范围，但仍处于同一进程地址空间，若把某栈变量地址传给其他线程，其他线程在生命周期和同步都合法时可以访问它。线程结束后该栈上的对象不能继续被使用。

**易错点：** “栈独立”不等于有进程级访问保护，更不等于栈对象天然线程安全。

### Q068. 上下文切换为什么有成本？线程越多越快吗？

**定位：** P0 · 补充题。

**参考答案：** 切换需要保存和恢复执行状态，调度还可能破坏缓存、分支预测与地址转换缓存的局部性。线程过多会增加竞争、栈占用与切换，CPU 密集工作不一定获益。客户端应先区分计算和等待，把任务组织成合适粒度，限制并发并避免主线程等待后台形成串行瓶颈。

**易错点：** 线程数量、逻辑核心数与最佳并发数不是简单恒等关系。

### Q069. 虚拟内存为什么存在？它只是为了扩大内存吗？

**定位：** P0 · 面经题意 [M03]、[M08]。

**参考答案：** 虚拟内存为进程提供独立地址空间，借助页表把虚拟地址映射到物理页，并实施读写执行权限。它支持隔离、按需分配、共享映射和文件映射等能力，交换到磁盘只是可能的机制之一。保留虚拟地址、提交内存与页面真正驻留物理内存也不等价。

**易错点：** 虚拟地址连续不要求物理页连续；64 位地址空间很大不意味着物理内存无限。

### Q070. 页表、TLB 与缺页异常分别是什么？

**定位：** P0 · 面经题意 [M05] 的分页主题，补充地址转换细节。

**参考答案：** 页表记录映射与权限，TLB 缓存近期地址转换以减少页表遍历。访问未建立映射、未驻留或权限不允许的页面可能触发缺页异常，由系统检查是否合法；合法情况可按需分配或载入数据后继续，非法情况则报告访问错误。第一次使用大缓冲区可能因页面实际分配而比后续慢。

**易错点：** TLB 未命中不等于缺页，缺页也不一定需要磁盘 I/O。

### Q071. 堆与栈的分配方式、容量和性能有什么区别？

**定位：** P0 · 面经题意 [M06]。

**参考答案：** 线程栈通常按调用关系管理自动对象与执行状态，分配常是调整栈指针；动态分配区需要分配器维护空闲块与生命周期，适合大小或存活时间不服从调用栈的数据。栈空间通常受较小限额约束，深递归和大型局部数组可能耗尽它。访问性能取决于布局和局部性，不是数据放在栈上就一定更快。

**易错点：** 要分开讨论“分配成本”和“读取同一缓存状态的数据成本”。

### Q072. 内部碎片与外部碎片有什么区别？如何缓解？

**定位：** P0 · 面经题意 [M03]，补充分配策略。

**参考答案：** 内部碎片是已分配块中未实际使用的空间，如尺寸分级与对齐浪费；外部碎片是空闲空间分散，难以满足所需连续块。可按尺寸或生命周期分组，采用池、页式分配和帧分配器，减少随机大小、随机寿命的混合。可移动对象还可通过句柄与整理压缩改善布局，但需要移动成本和引用修复机制。

**易错点：** 池也会预留过多空间或产生内部浪费，不是消除所有碎片的万能方案。

### Q073. 缓存局部性、缓存行和伪共享是什么？

**定位：** P0 · 面经题意 [M01] 的缓存主题，补充伪共享。

**参考答案：** 时间局部性是近期访问的数据可能再用，空间局部性是相邻数据可能一起访问。CPU 按缓存行搬运和维护一致性，连续遍历和紧凑热数据能减少缺失。多个线程写不同变量却落在同一缓存行时，可能反复使对方缓存失效，称为伪共享。可通过分片、适当填充和减少共享写改善。

**易错点：** 缓存行长度依平台而定；盲目填充所有对象会增加内存与带宽负担。

### Q074. 死锁的必要条件有哪些？工程上怎样避免？

**定位：** P0 · 补充题。

**参考答案：** 经典条件是互斥、占有并等待、不可强制剥夺和循环等待。常见治理包括统一锁顺序、缩小临界区、避免持锁调用未知回调、一次协调获取多个锁，或用消息传递减少共享状态。超时可帮助检测和恢复，但必须处理半完成事务，不能只在日志中提示后继续使用不一致状态。

**易错点：** 可重入锁只能解决某些同线程重入问题，不能解决任意多锁死锁。

### Q075. C++ 数据竞争、atomic 和 volatile 有什么关系？

**定位：** P0 · 补充题。

**参考答案：** 不同线程对同一内存位置发生冲突访问、至少一个非原子且缺少适当 happens-before 关系时，可能形成数据竞争，导致未定义行为。atomic 保证相应操作的原子语义，配合内存序表达同步。C++ volatile 用于特定可观察访问场景，不能代替原子或锁。语言规则见 [C++ 数据竞争][T12]。

**易错点：** 单个对齐整数在硬件上“一条指令能读写”，不等于 C++ 程序不存在数据竞争。

### Q076. relaxed、release/acquire 与 seq_cst 有什么不同？

**定位：** P2 · 补充题。

**参考答案：** relaxed 提供该原子对象操作的原子性和修改顺序，但不建立一般的跨对象发布关系。一个线程先写数据再 release 发布标志，另一个线程通过 acquire 读到相应发布值后，可以按同步关系观察此前的数据写入。seq_cst 还为相应原子操作提供统一顺序约束，较容易推理。细节见 [C++ 内存模型][T12]。

**易错点：** 只给两边操作写上 acquire/release 单词不够，必须证明读取关系、生命周期和其他访问也正确。

### Q077. 自旋锁、互斥锁与读写锁如何选择？

**定位：** P1 · 补充题。

**参考答案：** 自旋锁等待时占用 CPU，适合可证明非常短且持锁者能及时运行的临界区；互斥锁可进入阻塞，适合等待时间更长的场景，具体实现也可能先短暂自旋。读写锁允许多个读者，但维护与公平性也有成本，只在合适读写比例和临界区长度下获益。实时主线程应尤其避免不可控等待。

**易错点：** 在持锁者被抢占或核心紧张时，自旋可能拖慢持锁者，让问题更严重。

### Q078. 条件变量为什么要配合谓词循环等待？

**定位：** P0 · 补充题。

**参考答案：** 条件变量不是保存业务条件的队列，线程醒来可能是虚假唤醒，也可能条件已被其他线程消费。应在同一互斥保护下检查共享状态，条件不满足时释放锁并等待，醒来重新持锁检查；例如 `cv.wait(lock, [&]{ return stopped || !queue.empty(); });`。生产者修改受保护状态后再通知。

**易错点：** 只写一次 `if` 后无条件取队列元素，可能读空；只通知却没正确同步状态也会遗漏唤醒。

### Q079. 线程池怎样设计才能安全关闭？

**定位：** P1 · 补充题。

**参考答案：** 明确任务提交、运行、取消和停止状态，任务队列应有容量或背压策略。关闭时先拒绝新任务，再按契约选择排空队列或取消未开始任务，唤醒所有等待线程，最后等待工作线程结束。任务异常需要转交给结果对象或日志，不能让工作线程静默消失；回调引用的资源也必须活到任务结束。

**易错点：** 析构时简单设置一个布尔量而不唤醒、不 join，可能死等或让线程继续访问已销毁对象。

### Q080. 客户端偶现崩溃应该怎样排查？

**定位：** P1 · 补充题。

**参考答案：** 先保存版本、符号、平台、线程栈、关键日志和崩溃上下文，将问题按签名聚类。判断异常访问、栈溢出、主动断言、OOM 或驱动相关路径，再重建生命周期与线程时序。优先找到首次非法写入或状态破坏，使用复现条件、内存检测和最小场景验证修复，并比较修复前后的崩溃率。

**易错点：** 崩溃栈顶常只是受害位置，不能看到某个函数崩溃就直接认定该函数是根因。

## 四、网络与游戏同步（15 题）

### Q081. TCP 与 UDP 有什么区别？游戏为什么不能只比较快慢？

**定位：** P0 · 补充题。

**参考答案：** TCP 提供可靠有序字节流，包含重传、流控和拥塞控制；UDP 保留报文边界，但自身不保证到达、顺序或去重。实时位置更新往往更重视新鲜度，账号、结算等更重视完整性。可按消息语义使用不同通道，在 UDP 上对必要消息增加可靠机制；选型还要考虑网络环境、平台和实现成本。

**易错点：** UDP 不自动低延迟，拥塞和应用层重传同样会造成延迟；TCP 也不是不能做实时游戏。

### Q082. TCP 为什么要三次握手？

**定位：** P0 · 面经题意 [M02]。

**参考答案：** 主动端发送 SYN 和初始序号，对端以 SYN+ACK 返回自己的序号并确认，主动端再 ACK。这个交换同步双方初始序号并确认双向通信状态，有助于防止旧连接报文被误认为新连接。它不验证玩家身份，应用仍需认证。协议细节参见 [TCP 规范 RFC 9293][T13]。

**易错点：** “验证收发能力”只是直观说法，还要能解释序号、确认和旧报文问题。

### Q083. TCP 为什么常说四次挥手？TIME_WAIT 有什么用？

**定位：** P0 · 面经题意 [M02]。

**参考答案：** TCP 是全双工，两个方向分别结束发送，FIN 各自需要确认，所以常见过程是 FIN、ACK、FIN、ACK。若接收端也准备关闭，ACK 与 FIN 可以合并，并非永远四个独立报文。TIME_WAIT 支持重发最后确认，并让旧连接报文在重用连接标识前消退；典型主动关闭方进入该状态。

**易错点：** 收到 FIN 表示对方结束这个方向的发送，不等于本端必须立即丢弃尚未发送的数据。

### Q084. TCP 的可靠性、流量控制和拥塞控制怎样区分？

**定位：** P0 · 面经题意 [M02] 的拥塞控制主题。

**参考答案：** 序号、确认与重传支撑可靠交付；流量控制避免发送方超过接收方可用缓冲能力；拥塞控制根据网络反馈约束注入流量，避免压垮路径。实际发送量同时受接收窗口、拥塞窗口及其他因素限制。可靠有序也意味着缺失的一段数据可能阻止后续数据交给应用，形成交付上的队头阻塞。

**易错点：** 重传解决丢失，不保证业务请求只执行一次；业务仍需去重和幂等设计。

### Q085. “粘包、半包”怎样处理？

**定位：** P0 · 补充题。

**参考答案：** TCP 提供字节流，单次 write 与单次 read 没有一一对应关系。应用应定义消息边界，如固定头部携带消息长度，先累计完整头，再验证长度并累计正文，一次读入可能解析出零条、一条或多条消息。需限制最大包长、检查整数溢出、字节序与协议版本，保留尚不完整的尾部。

**易错点：** 分隔符协议必须处理转义；不能信任对端长度字段直接申请任意大内存。

### Q086. 如何在 UDP 上实现需要的可靠性？

**定位：** P1 · 补充题。

**参考答案：** 为消息或包添加序号、确认与去重，使用 RTT 估计设置重传，必要时采用选择性确认、分片重组和拥塞控制。不同业务可使用可靠有序、可靠无序和不可靠有序等语义，过期位置包可以丢弃。需要限制重组缓存、重试次数和队列长度，以免恶劣网络把旧消息越堆越多。

**易错点：** 给每个丢失包无限重传不等于成熟可靠协议，也会破坏实时性。

### Q087. 帧同步与状态同步有什么区别？

**定位：** P0 · 面经题意 [M04]。

**参考答案：** 帧同步通常交换按逻辑帧组织的输入，让各端执行相同模拟，因此要求初始状态、输入顺序和逻辑具有足够确定性。状态同步交换权威端计算的结果，客户端通过插值、预测改善表现，更容易集中裁决，但可能增加状态带宽。商业系统可以混合使用，不能只根据游戏品类断言具体实现。

**易错点：** 输入可能编码为移动方向或操作指令，关键在于传的是驱动模拟的输入还是模拟结果。

### Q088. 相同输入为什么仍可能造成帧同步不同步？

**定位：** P1 · 补充题。

**参考答案：** 原因包括浮点运算差异、非确定物理、无序容器遍历、随机数调用次数不同、多线程更新顺序以及读入系统时间。应统一逻辑步长、状态初始化、随机种子和调用顺序，选用可控数值方案，将表现与确定逻辑分离；通过逐帧状态摘要和输入录像定位首次分叉。

**易错点：** 统一随机种子或把 float 全改定点数，都不能单独保证整个系统确定。

### Q089. 插值、外推与插值缓冲如何改善远端角色移动？

**定位：** P0 · 补充题。

**参考答案：** 插值在两个已知快照之间计算显示状态，通常让显示时间落后服务器时间一点，以容纳抖动；外推用最近速度等信息预测未来，消息缺失时仍能前进，但可能错判碰撞和转向。工程上优先平稳插值，对短暂缺包有限外推，超时后限制移动，并在恢复数据时平滑纠正。

**易错点：** 增大缓冲会更平滑，却增加看到他人动作的延迟，需要按网络质量取舍。

### Q090. 本地预测与服务器校正的完整流程是什么？

**定位：** P1 · 补充题。

**参考答案：** 客户端给输入编号并立即模拟，保存未确认输入；服务器按输入计算权威状态，回传状态与最后处理的输入编号。客户端收到后以权威状态为起点，重放尚未确认输入，再让显示模型适度平滑过渡。这样输入立即有反馈，但最终状态由服务器决定。

**易错点：** 只把画面位置慢慢拉回而不重放未确认输入，会不断与正在进行的操作冲突。

### Q091. 回滚同步需要保存什么？哪些副作用不能重复播放？

**定位：** P1 · 补充题。

**参考答案：** 为有限时间窗口保存可恢复的模拟状态和输入历史，对尚未收到的输入先预测；真实输入不同时恢复到分叉前，再重演到当前帧。逻辑必须可重放，随机、实体创建与事件顺序要确定。声音、成就、结算等副作用应延迟确认、按事件 ID 去重或设计撤销机制，表现状态可独立平滑。

**易错点：** 只保存角色坐标通常不够，技能计时、随机状态和已产生实体也会影响重演。

### Q092. 射击游戏中的延迟补偿怎样做？

**定位：** P1 · 补充题。

**参考答案：** 权威服务器保存短时间内目标碰撞状态，处理射击请求时根据可信的时间估计，在受限历史窗口中检测射线与当时目标的位置。它可以补偿玩家看到的历史画面，但也会出现受击方已躲进掩体仍被命中的体验。必须限制回溯窗口、验证射速和时序，并处理动态遮挡物与插值延迟。

**易错点：** 不能无条件信任客户端上报的射击时间，也不应把服务器整个世界无限回滚。

### Q093. 断线重连怎样避免重复结算和状态错乱？

**定位：** P1 · 补充题。

**参考答案：** 重连先恢复或重新验证会话，再通过版本化快照与必要增量同步权威状态，明确旧连接和旧请求是否仍有效。请求带业务唯一 ID，重要操作由服务器记录处理结果以支持幂等重试；客户端恢复 UI、输入状态和订阅时也需去重。重连失败、比赛已结束、资源版本变化都应有分支处理。

**易错点：** “重新登录后把断线前的请求全部重发”可能重复购买、释放技能或领取奖励。

### Q094. 心跳、超时和客户端时间应该怎样设计？

**定位：** P1 · 补充题。

**参考答案：** 心跳检测连接和应用是否仍有响应，也可辅助 RTT 估计；超时需要容忍抖动，结合最近实际业务包更新活跃时间。耗时测量使用单调时钟，客户端与服务器时间通过往返样本估计偏移并平滑调整。后台挂起、弱网和时钟跳变应与普通延迟区分。

**易错点：** 系统墙上时间可能被校时或用户修改，不能直接用来计算可靠的技能冷却与网络间隔。

### Q095. 客户端同步带宽如何优化？

**定位：** P1 · 补充题。

**参考答案：** 先测各类消息大小、频率和对象数，再用兴趣管理减少无关对象，按优先级调整发送频率，对可容忍误差的数据量化，使用差量和位打包，并合并过小消息。差量编码要明确基线版本和丢包后的恢复方式；突发生成大量对象时安排预算与补发策略。

**易错点：** 压缩每个小包可能得不偿失，降低发送频率也可能提高预测误差与纠正成本。

## 五、数据结构与算法（15 题）

### Q096. 如何写不容易出边界错误的二分查找？

**定位：** P0 · 补充题。

**参考答案：** 先规定搜索区间和返回语义。例如寻找第一个不小于 target 的位置，维护左闭右开区间 `[l,r)`，初始 `l=0,r=n`；若 `a[mid]<target`，令 `l=mid+1`，否则 `r=mid`，直到 `l==r`。结果可以等于 n，若要判断是否存在还需检查范围和相等。时间 O(log n)，额外空间 O(1)。

**易错点：** 空数组、重复值、全部小于目标必须覆盖；`mid=l+(r-l)/2` 可避免不必要的加法溢出。

### Q097. 如何原地反转单链表？

**定位：** P0 · 面经题意 [M08]。

**参考答案：** 保存 `prev`、`cur`，每轮先保存 `next=cur->next`，再让 `cur->next=prev`，最后整体前进。循环结束时 prev 是新头。每个节点处理一次，时间 O(n)，额外空间 O(1)。输入应为普通无环单链表，空链表和单节点无需特殊复杂处理。

```text
prev = null
cur = head
while cur != null:
    next = cur.next
    cur.next = prev
    prev = cur
    cur = next
return prev
```

**易错点：** 修改 next 之前必须保存后继，否则会丢失尚未处理的链段。

### Q098. 如何找到链表环入口，并反转入口之前的部分？

**定位：** P1 · 面经题意 [M10]。

**参考答案：** 快慢指针分别每次走两步和一步，相遇后让一指针回到头部，两指针再同速前进，相遇点就是入口：第一次相遇时慢指针走过的步数是环长的整数倍。随后只反转 `[head,entry)`，保留原 head，并把它的新 next 接到 entry，环内连接不变。返回反转后的前缀头；若头就是入口，则无需反转。

**易错点：** 先处理无环情况，不要让反转循环进入环。总时间 O(n)，额外空间 O(1)。

### Q099. 单链表怎样排序？为什么常选归并排序？

**定位：** P0 · 面经题意 [M07]。

**参考答案：** 用快慢指针拆为两半，递归排序，再按值合并两个有序链表。归并不依赖随机访问，可通过重连指针完成，时间 O(n log n)，递归栈 O(log n)。若要求 O(1) 辅助空间，可用从长度 1 开始逐倍增加的自底向上归并。相等时优先取左段元素可以保持稳定性。

**易错点：** 拆分时要真正断开两段；遗漏断链可能导致无限递归或形成错误链路。

### Q100. 已知前序与中序遍历，如何重建二叉树？

**定位：** P0 · 面经题意 [M08]。

**参考答案：** 在节点标识唯一且序列合法时，前序首元素是根，在中序中找到根即可得到左右子树长度，再划分对应前序区间递归重建。预先建立值到中序下标的映射，避免每层线性查找，平均时间 O(n)，映射 O(n)，递归深度最坏 O(n)。应传索引范围而非反复复制子数组。

**易错点：** 存在重复值且没有唯一标识时，结果通常不唯一；需要先确认题目约束。

### Q101. 海量数据中的 Top K 怎么做？

**定位：** P0 · 补充题；相近删除最大 N 个元素题见 [M07]。

**参考答案：** 求最大 K 个，维护容量 K 的小根堆，超过堆顶才替换，时间 O(n log K)、额外空间 O(K)，适合流式数据。内存内数组可用快速选择，平均 O(n)，普通实现最坏 O(n²)；若结果需要排序，再排序选出的 K 个。K 接近 n 或数据已有结构时，可重新评估整体排序。

**易错点：** 最大 K 个配小根堆；明确重复值是否计数，以及 K 为零或超过元素数的规则。

### Q102. 快排、归并排序、堆排序怎样比较？

**定位：** P0 · 面经题意 [M01] 的排序比较主题。

**参考答案：** 快排平均 O(n log n)，枢轴不佳可退化到 O(n²)，通常不稳定；归并排序最坏 O(n log n)，可稳定，数组版本通常需要 O(n) 辅助存储；堆排序最坏 O(n log n)，可原地但不稳定，访存模式也影响实际速度。比较排序一般模型下有 Ω(n log n) 下界，特定整数约束可用计数或基数方法。

**易错点：** 不存在脱离数据类型、分布、缓存和稳定性要求的“永远最快排序”。

### Q103. 如何实现平均 O(1) 的 LRU 缓存？

**定位：** P0 · 补充题。

**参考答案：** 哈希表映射 key 到双向链表节点，链表头表示最近使用，尾表示最久未使用。get 命中后把节点移到头部；put 更新已有节点或插入新节点，容量超限则删尾，并同步删除哈希项。查询和节点重连平均 O(1)，空间 O(capacity)。缓存资源还需考虑淘汰时仍有使用者的情况。

**易错点：** 容量为零、重复写键、删除节点后哈希迭代器失效，以及并发访问都要处理。

### Q104. 最长无重复字符子串如何求？

**定位：** P0 · 面经题意 [M09]。

**参考答案：** 用滑动窗口与字符最近出现位置。扫描右端 r，若字符上次位置在当前窗口内，将左端更新为 `max(l,last[c]+1)`，记录本次位置并更新最大长度。每个元素处理一次，时间 O(n)，空间 O(min(n,字符集大小))。若输入是 Unicode，先确认题目按字节、码点还是用户可见字符计数。

**易错点：** 左边界不能倒退，例如处理 `abba` 时直接赋旧位置会得到错误结果。

### Q105. 最大连续子数组和怎样求？

**定位：** P0 · 面经题意 [M07]。

**参考答案：** 对非空数组定义 `ending` 为“必须在当前位置结束的最大和”，转移为 `ending=max(x,ending+x)`，并用 best 维护全局最大。两者都从首元素初始化，可正确处理全负数组。时间 O(n)，额外空间 O(1)；需要区间时同时维护当前起点与最佳区间。

**易错点：** 若题目不允许空子数组，不能把答案初始化成零；求和可能需要更宽整数类型。

### Q106. 不调用 sqrt，如何求非负整数的向下取整平方根？

**定位：** P0 · 面经题意 [M05]，明确为整数版本。

**参考答案：** 利用 `x²≤n` 的单调性二分最后一个满足条件的整数。将搜索下界设为 1 并先处理 n<2，可用 `mid≤n/mid` 避免乘法溢出和除零。时间 O(log n)，额外空间 O(1)。下面是处理无符号 64 位输入的实现；浮点版本应另行定义误差和停止条件。

```cpp
#include <cstdint>
std::uint64_t integer_sqrt(std::uint64_t n) {
    if (n < 2) return n;
    std::uint64_t lo = 1, hi = n / 2 + 1, answer = 1;
    while (lo <= hi) {
        const auto mid = lo + (hi - lo) / 2;
        if (mid <= n / mid) {
            answer = mid;
            lo = mid + 1;
        } else {
            hi = mid - 1;
        }
    }
    return answer;
}
```

**易错点：** 必测 0、1、完全平方数、相邻非平方数与最大输入；乘法溢出会破坏二分的判断。

### Q107. A* 怎样工作？什么时候能保证最短路径？

**定位：** P0 · 面经题意 [M04]、[M07]。

**参考答案：** A* 按 `f(n)=g(n)+h(n)` 选择待扩展节点，g 是已知起点到 n 的代价，h 是剩余代价估计，并维护前驱与更优路径更新。在常见非负边权条件下，可采纳启发式不高估真实剩余代价；图搜索若不重新打开已关闭节点，通常要求一致性。若只有可采纳性，需要正确处理更优路径下的重新打开。

**易错点：** 允许低成本斜走时，曼哈顿距离可能高估；启发式应匹配移动规则和边权。

### Q108. BFS、DFS、Dijkstra 分别适合什么问题？

**定位：** P0 · 面经题意 [M02] 的遍历主题，补充最短路比较。

**参考答案：** BFS 按层扩展，适合无权或等权图最短路；DFS 适合连通性、回溯和结构遍历，本身不保证最短路；Dijkstra 每次确定当前最小暂定距离，适用于非负边权图。邻接表 BFS/DFS 是 O(V+E)，二叉堆实现 Dijkstra 常写为 O((V+E) log V)。

**易错点：** 存在负边时不能直接套 Dijkstra 的正确性证明；大图递归 DFS 还可能栈溢出。

### Q109. 二叉堆怎样实现？建堆为什么是 O(n)？

**定位：** P0 · 面经题意 [M08] 的最小堆主题。

**参考答案：** 用数组表示完全二叉树，父子索引可直接计算，插入时上浮，删除根时将末尾放到根再下沉，二者为 O(log n)，读堆顶 O(1)。自底向上对非叶子节点下沉建堆时，多数节点位于低层、下沉距离很短，各层工作量相加为 O(n)。

**易错点：** 从空堆逐个插入的建堆方式通常是 O(n log n)，要和自底向上建堆区分。

### Q110. 0/1 背包与完全背包为什么遍历顺序不同？

**定位：** P1 · 补充题；动态规划主题见 [M01]。

**参考答案：** 定义 `dp[c]` 为容量不超过 c 的最大收益。0/1 背包每件物品只能使用一次，按容量从大到小更新，保证读取的是该物品处理前的状态；完全背包允许重复使用，容量从小到大更新可引用本轮已更新状态。时间通常 O(物品数×容量)，空间 O(容量)。

**易错点：** “恰好装满”与“不超过容量”需要不同初始化，无法达到的状态不能默认当作零收益。

## 六、Unity 引擎与性能（35 题）

### Q111. Awake、OnEnable、Start、OnDisable、OnDestroy 怎样分工？

**定位：** P0 · 面经题意 [M05]。

**参考答案：** Awake 适合本对象初始化，OnEnable 适合每次激活时建立订阅，Start 在首次启用更新前执行一次，可处理适合此时建立的依赖，OnDisable 解除本轮激活的关系，OnDestroy 清理最终拥有的资源。非激活对象、运行时实例化和场景加载会影响调用时机，不能依赖不同对象同名回调的偶然顺序。参见 [执行顺序][T14]。

**易错点：** 跨对象 OnEnable 不应假定其他所有对象的 Awake 都已经完成。

### Q112. Update、FixedUpdate、LateUpdate 有什么区别？

**定位：** P0 · 面经题意 [M05]。

**参考答案：** Update 跟随显示帧处理常规逻辑，FixedUpdate 按固定游戏时间步推进，通常用于对接默认物理模拟，LateUpdate 在 Update 后执行，适合依赖移动结果的相机。单个显示帧可能对应零次或多次 FixedUpdate。手工积分位移仍需乘相应时间步；物理 API 是否已按时间积分要按其单位和参数模式判断。

**易错点：** FixedUpdate 不是另一个线程，也不是“每个屏幕帧必执行一次”。执行顺序见 [Unity 文档][T14]。

### Q113. timeScale 为零后，哪些逻辑仍然运行？

**定位：** P0 · 补充题。

**参考答案：** 常规 Update 仍可被调用，但缩放后的 deltaTime 为零；默认 FixedUpdate 和基于缩放时间的 WaitForSeconds 不再按普通方式推进。暂停菜单动画、超时提示等可使用 unscaledDeltaTime 或 WaitForSecondsRealtime。物理、Animator、粒子和第三方计时系统是否暂停还取决于各自更新设置。参见 [timeScale][T16]。

**易错点：** 暂停不是让整个应用停止执行，网络线程与使用真实时间的任务可能继续运行。

### Q114. Unity 协程在什么时候执行？怎样停止？

**定位：** P0 · 面经题意 [M05]。

**参考答案：** StartCoroutine 启动时先执行到首次挂起，之后由引擎按 yield 对象在相应 PlayerLoop 时机恢复。`yield return null`、WaitForFixedUpdate 和 WaitForEndOfFrame 对应不同等待条件，不可都概括为“下一帧 Update”。保存返回的 Coroutine 或一致使用约定方式停止，并在生命周期结束时整理关联状态。参见 [协程说明][T15]。

**易错点：** 协程通常在主线程推进，有状态机分配与被捕获对象的存活成本，不是免费后台任务。

### Q115. SetActive(false)、enabled=false、关闭 Renderer 有什么区别？

**定位：** P0 · 面经题意 [M04]，补充协程边界。

**参考答案：** 停用 GameObject 会让其相关组件退出正常激活流程，并停止附着在其 MonoBehaviour 上的协程；单独禁用 MonoBehaviour 会停止相应更新回调，但不会因此自动停止已有协程；仅关闭 Renderer 主要改变渲染，不等价于禁用脚本和碰撞。activeSelf 是本地设置，activeInHierarchy 还受父对象影响。协程边界见 [官方说明][T15]。

**易错点：** 哪种方式更省开销取决于对象组件与业务意图，不能只比较一次赋值的成本。

### Q116. Destroy 和 DestroyImmediate 有什么区别？

**定位：** P0 · 补充题。

**参考答案：** Destroy 安排对象在引擎安全时机销毁，适合普通运行时流程；DestroyImmediate 立即执行销毁，主要用于受控编辑器操作，不适合替代运行时 Destroy。销毁组件只移除相应组件，销毁 GameObject 则连同其组件和子层级处理。自建的材质、网格和外部资源仍需明确各自所有权与清理方式。

**易错点：** 调用 Destroy 后不应继续把对象当作正常存活对象安排新异步操作，也不要在遍历中随意立即销毁集合内容。

### Q117. 为什么 Unity 对象“== null”，ReferenceEquals 却为 false？

**定位：** P0 · 补充题。

**参考答案：** UnityEngine.Object 有托管包装与引擎原生对象的关联。原生对象被销毁后，托管包装可能尚未回收；Unity 重载的等号把这种分离状态视作空，而 ReferenceEquals 仍看到真实托管引用。`?.` 和 `??` 不调用这套重载，不能代替 Unity 存活检查。参见 [Unity Object 的空值语义][T17]。

**易错点：** 变量被当作普通 object 或接口处理时，检查语义可能不同；需要根据静态类型判断实际用到的操作。

### Q118. Unity 内存为什么不能只看 Managed Heap？

**定位：** P0 · 补充题。

**参考答案：** 客户端还包含引擎原生对象、纹理、网格、音频、驱动与 GPU 相关分配，以及各类缓存。GC 主要处理托管对象，不自动等价回收所有引擎和显存资源。应结合内存快照、资源计数和平台工具区分“仍被引用的资源”“分配器保留容量”和“真实泄漏”，并做重复进出场景的对比。

**易错点：** 托管 GC 后进程占用未明显下降，不足以单独证明泄漏；GPU 与系统内存的统计还可能重叠。

### Q119. Unity GC 与普通 .NET 分代 GC 有什么不同？增量 GC 有什么用？

**定位：** P0 · 补充题。

**参考答案：** 本文讨论的传统 Unity Mono/IL2CPP 托管堆采用 Boehm 系列回收器，不能套用普通 .NET 的分代压缩模型。增量模式把回收工作分散到多帧，目标是减少长暂停，并不保证总工作量更少，也不是零暂停。可用性与行为还需核对平台，例如 Web 有额外限制。参见 [Unity GC][T18] 与 [托管堆机制][T18B]。

**易错点：** IL2CPP 把代码转成原生执行，并不取消托管对象的垃圾回收。

### Q120. 每帧 GC.Alloc 怎么排查和优化？

**定位：** P0 · 补充题。

**参考答案：** 在目标设备的构建中定位分配调用栈，区分初始化分配和稳定运行期分配，重点检查字符串、装箱、闭包、临时集合、返回新数组的 API 与过度协程创建。可缓存不变结果、复用有上限的缓冲区、预留容量和使用合适的 NonAlloc API。优化后同时检查帧时间和长期内存。

**易错点：** 为追求某一帧零分配而永久缓存大量对象，可能把暂停问题换成内存峰值与更大扫描成本。

### Q121. Unity 对象池除了 SetActive，还要管理哪些状态？

**定位：** P0 · 面经题意 [M04]。

**参考答案：** 借出时初始化变换、所属者、伤害和计时，归还时取消订阅、计时器、协程和异步回调，清理粒子、轨迹、物理速度及目标引用。需要防重复归还、使用代次校验旧回调、控制容量和预热峰值，并明确池销毁时如何释放资源。对象被禁用不表示其所有 C# 引用与外部任务自动解除。

**易错点：** 旧子弹的延迟回调可能误操作已经复用成“新子弹”的同一对象。

### Q122. Resources、AssetBundle 和 Addressables 如何取舍？

**定位：** P0 · 补充题。

**参考答案：** Resources 接入简单，但大量依赖放入其中会使打包与管理粗放；AssetBundle 提供可独立构建、加载的资源包，需要自己处理依赖与生命周期；Addressables 在资源地址、异步操作、依赖与引用管理上提供更高层抽象。应根据项目规模、远程内容、包体更新和诊断需求选择，而不是只比较一行加载 API。

**易错点：** Addressables 不自动替你解决所有内容分组、包依赖和业务所有权问题。

### Q123. AssetBundle.Unload(false) 与 Unload(true) 有何区别？

**定位：** P0 · 补充题。

**参考答案：** false 释放包自身相关数据，但保留已经加载的对象；true 还会销毁从包中加载的对象，场景中仍使用这些资源的引用可能变成缺失。两者之后都不能继续从该包加载，除非重新加载包。false 后重新加载还可能形成重复资源，必须统一跟踪依赖与使用者。参见 [AssetBundle.Unload][T19]。

**易错点：** 销毁一个 Prefab 实例不等于其纹理和材质已卸载；正在被其他包使用的依赖不能随意单独卸载。

### Q124. Addressables 的加载、实例化与释放怎样配对？

**定位：** P0 · 补充题。

**参考答案：** 显式获取的加载句柄应有对应释放责任；通过 InstantiateAsync 创建的实例按其跟踪方式使用 ReleaseInstance 等配对清理。若先 LoadAssetAsync 得到 Prefab 再用普通 Instantiate，Addressables 不会自动为每个普通克隆增加加载引用，必须让资源句柄活到这些克隆不再使用资源。引用归零也不代表所属包立即可卸载。参见 [内存管理][T20]。

**易错点：** 复制句柄结构体不是自动新增一次拥有关系；重复 Release 与遗漏 Release 都是错误。

### Q125. 异步加载场景为什么仍会卡顿？

**定位：** P1 · 补充题。

**参考答案：** 异步通常只把可异步的 I/O 或准备步骤移出阻塞路径，反序列化、对象激活、Awake/OnEnable、Shader 首次使用、GPU 上传等仍可能占用主线程或造成等待。应分阶段记录时间，预加载依赖，控制激活时机，对自有生成逻辑分帧，并限制旧场景与新场景叠加的内存峰值。

**易错点：** 进度条接近完成不等于所有激活工作结束；把整个流程标记为 async 不能保证每帧稳定。

### Q126. Unity 序列化有哪些限制？ScriptableObject 适合什么？

**定位：** P0 · 补充题。

**参考答案：** 常规 Unity 序列化主要面向符合规则的字段，公共字段或标注 SerializeField 的字段仍需类型受支持，普通属性和许多容器不能直接套用。需要多态托管引用时可按版本使用 SerializeReference 等机制。ScriptableObject 适合共享配置和可编辑资产，但运行时状态最好与配置分离，避免多个使用者意外互相修改。

**易错点：** 构建后的游戏修改 ScriptableObject，不代表变化自动永久保存到项目资产；持久化要另设计。

### Q127. Prefab、Prefab Variant 与场景实例如何组织？

**定位：** P1 · 补充题。

**参考答案：** Prefab 保存可复用对象结构，Variant 基于基础 Prefab 记录差异，场景实例还能有自己的覆盖。适合将公共结构留在基础层，把型号差异放在变体或配置中，避免复制大量几乎相同的资产。团队应限制层级过深与无意覆盖，明确 Apply/Revert 的目标，并把运行时修改与资产编辑区分开。

**易错点：** 场景实例看似正确，可能靠意外覆盖掩盖基础资产问题，后续同步时才暴露。

### Q128. Transform 的 localPosition、position 与坐标变换怎样理解？

**定位：** P0 · 补充题。

**参考答案：** localPosition 相对父级坐标系，position 是世界空间位置；父级的旋转和缩放会影响子对象。转换位置时包含平移，转换方向时通常不应包含平移，方向和向量是否受缩放影响还要看具体 API。层级中出现非均匀缩放与旋转组合时，不能简单逐分量相乘解释所有世界变换。

**易错点：** 给角色局部前方偏移，不能总是直接加世界坐标的 `(0,0,d)`。

### Q129. Rigidbody、CharacterController 与直接改 Transform 如何选择？

**定位：** P0 · 补充题。

**参考答案：** 动态 Rigidbody 适合需要物理求解、力和碰撞响应的物体；CharacterController 提供面向角色的受约束移动，但重力和许多运动规则要由业务实现；直接改 Transform 适合不依赖动态刚体求解的对象。驱动物理对象应遵循对应刚体与步进规则，运动学刚体也有适用的移动接口。

**易错点：** 对动态刚体一边让物理更新、一边每帧强改 Transform，可能造成抖动和碰撞表现异常。

### Q130. Collider 与 Trigger 的区别是什么？碰撞回调为何不触发？

**定位：** P0 · 补充题。

**参考答案：** Collider 描述形状；作为普通碰撞体时参与接触与相应响应，启用 Trigger 后主要报告进入、停留、离开等重叠事件，不产生普通实体碰撞阻挡。排查回调要检查物理系统是 2D 还是 3D、组件是否启用、层碰撞矩阵、刚体及运动学组合和回调签名，并对照相应版本的碰撞消息条件。

**易错点：** 3D Collider 与 Collider2D 属于不同系统；“只加两个碰撞器就必然触发所有回调”是错误的。

### Q131. 高速子弹为什么穿墙？怎样解决？

**定位：** P0 · 补充题。

**参考答案：** 离散检测只观察相邻物理步中的位置，子弹可能从墙的一侧直接到另一侧而没有离散重叠。可以使用合适的连续碰撞检测模式，或对上一位置到新位置做射线、球体扫掠等检测；命中扫描武器可直接查询射线。缩短固定时间步也能降低风险，但会提高物理计算量。

**易错点：** CCD 支持的形状和运动组合有限，也不是所有旋转穿透都能自动解决。

### Q132. Animator 状态机、Blend Tree 与 Root Motion 分别负责什么？

**定位：** P0 · 补充题。

**参考答案：** Animator 状态机决定动作状态与转换，Blend Tree 根据速度等参数连续混合动作，Root Motion 从动画提取根位移或旋转驱动角色。逻辑移动驱动与动画驱动应有明确主导方，避免二者同时修改位置。状态切换需要检查条件、过渡时间、退出时间与中断规则。

**易错点：** 动画播放完成不必然等于服务器确认技能完成；关键玩法结算不宜只依赖展示层事件。

### Q133. 怎样实现上半身射击、下半身移动与脚部贴地？

**定位：** P1 · 面经题意 [M04] 的分部位动画主题，补充 IK。

**参考答案：** 用动画层与 Avatar Mask 限制上层只影响上半身，下层保留移动；根据动作性质使用覆盖混合或基于参考姿态的加法混合。脚部贴地可用地面探测和 IK 调整目标与权重，同时限制腿长和髋部偏移。瞄准、换弹和受击之间需要定义优先级与中断关系。

**易错点：** 加法动画的参考姿态错误会导致叠加变形，不能把所有动作都当作可加性偏移。

### Q134. NavMesh 和 A* 有什么关系？动态障碍怎样处理？

**定位：** P0 · 面经题意 [M04]。

**参考答案：** NavMesh 是可行走区域及邻接关系的表示，A* 是可在相应图上搜索路线的算法；得到多边形路径后还需提取平滑拐点并执行移动。动态避让处理短期局部冲突，导航切割或重建处理拓扑变化，跨越断层可使用导航连接。大量单位应控制重寻路频率和每帧预算。

**易错点：** 本地避让不会自动发现被彻底封路后的全局替代路线，也不保证永远无死锁。

### Q135. UGUI 为什么会发生布局和网格重建？

**定位：** P0 · 补充题。

**参考答案：** 文本、尺寸、布局或材质等变化可能把元素标脏，引发相关布局计算、几何更新或 Canvas 批次重新分析；不是每次修改都以同样范围重建一切。可按刷新频率拆分适度的 Canvas，避免反复修改不变值，减少深层 LayoutGroup，并关闭非交互元素的 Raycast Target。参见 [Unity UI 优化][T25]。

**易错点：** 拆得越细不一定越快，Canvas 之间不能任意合批，需要同时衡量重建成本和绘制成本。

### Q136. 一万个背包格子或排行榜条目怎样显示？

**定位：** P0 · 面经题意 [M03]。

**参考答案：** 保存完整数据，但只创建可见区域加少量缓冲的视图，滚动时复用格子并绑定新数据。等高条目可由滚动偏移直接计算索引，变高条目可维护累计高度辅助定位。图标异步加载需要校验绑定版本，防止旧回调覆盖已复用的格子；选中状态、排序与服务器数据应属于数据层。

**易错点：** 仅把屏幕外一万个对象隐藏仍可能保留大量层级、布局和资源成本，关键是减少实际视图数量。

### Q137. UGUI 为什么相同图集仍无法合批？

**定位：** P1 · 补充题。

**参考答案：** 合批还受材质、Shader、纹理绑定、裁剪或模板状态、Canvas 边界以及绘制顺序约束。透明 UI 的前后关系必须保持，夹在两组元素之间的不兼容绘制可能打断批次。应通过 Frame Debugger 找到实际拆批原因，再调整层级、图集或遮罩，而不是只合并图片文件。

**易错点：** 为合批随意调整重叠 UI 的顺序可能改变画面；图集过大还会增加加载与驻留内存。

### Q138. material、sharedMaterial 与 MaterialPropertyBlock 怎样使用？

**定位：** P0 · 面经题意 [M02]，补充属性块。

**参考答案：** material 可能实例化独立材质，需要管理创建后的生命周期；sharedMaterial 访问共享材质，改其内容会影响其他使用者。MaterialPropertyBlock 可为渲染器覆盖部分参数，避免仅为颜色差异创建大量材质，但它与 SRP Batcher 的兼容存在约束，必须按目标管线验证。参见 [材质实例][T21]、[SRP 兼容条件][T26]。

**易错点：** 不要把“用属性块”当作所有管线下无条件更快的方案。

### Q139. 静态合批、动态合批、SRP Batcher 有何区别？

**定位：** P0 · 面经题意 [M02] 的合批主题，补充 SRP。

**参考答案：** 静态合批为符合条件的静态几何建立组合数据，可能增加内存；动态合批在 CPU 侧处理合格小网格，有变换与限制成本；SRP Batcher 主要复用材质常量数据和兼容提交路径，降低 Draw Call 之间的 CPU 状态设置开销，不等于把所有网格变成一次绘制。参见 [SRP Batcher][T22]。

**易错点：** 不要死背某旧版本顶点阈值，也不要只凭 Draw Call 数量判断优化成败。

### Q140. GPU Instancing 在什么情况下有用？

**定位：** P1 · 补充题。

**参考答案：** 当大量对象共享网格与兼容材质，却有不同变换或实例参数时，可把这些实例一起提交，让 GPU 根据实例 ID 读取各自数据。它减少提交开销，但不会消除所有实例的顶点、像素和阴影成本。需要关注剔除粒度、实例数据上传以及 Shader 是否支持相应实例化方式。

**易错点：** 一次提交一大片不可见实例可能抵消收益；和 SRP Batcher、静态合批的路径选择需实际检查。

### Q141. 如何判断卡顿来自 CPU、GPU、GC 还是等待？

**定位：** P0 · 补充题。

**参考答案：** 在目标设备固定场景下查看每帧时间线，区分主线程、渲染线程、GPU、I/O、GC 和同步点；观察长耗时究竟是做计算还是等待其他环节。降低分辨率可作为像素负载的诊断实验，减少脚本工作可测试 CPU 假设。确认瓶颈后一次改一个变量，用一致条件对比。

**易错点：** Profiler 中等待标记可能反映 GPU、垂直同步或队列节流，不能把它全部计为 CPU 业务开销。

### Q142. Profiler、Frame Debugger、RenderDoc 和 Memory Profiler 各看什么？

**定位：** P1 · 补充题。

**参考答案：** Profiler 看线程与系统耗时和分配；Frame Debugger 看一帧的绘制顺序、状态和拆批；RenderDoc 等图形抓帧工具查看支持平台上的 GPU 资源、管线状态与绘制结果；Memory Profiler 对比对象和资源快照。先用宏观时间线定位类别，再用专门工具深入，避免一开始收集过重数据干扰现场。

**易错点：** 编辑器数据与目标设备不同，Deep Profiling、抓帧和调试构建也会改变性能。

### Q143. Job System、Burst 与 NativeArray 分别解决什么问题？

**定位：** P1 · 补充题。

**参考答案：** Job System 按依赖调度任务，Burst 编译兼容的数据处理代码以提升执行效率，NativeArray 提供可由受控作业访问的原生连续存储。应明确读写声明与依赖，在主线程读取结果或释放存储前确保相关任务完成。复制 NativeArray 结构体通常共享底层缓冲区，不等于深拷贝。参见 [NativeContainer 与作业安全][T23]。

**易错点：** NativeArray 不会因有安全系统就允许任意并发写；频繁立即 Complete 会把工作重新串行化。

### Q144. ECS 与传统面向对象组件设计有什么差异？

**定位：** P1 · 面经题意 [M07]、[M10]。

**参考答案：** ECS 把实体身份、组件数据和系统处理分开，常把相同布局的数据集中存储，便于连续遍历、批处理和并行。传统对象方式把数据与行为绑定，组织直观但热路径可能出现大量间接访问。ECS 的结构变化、组件组合数量、依赖和调试同样有成本，适合按性能与团队需求逐步采用。

**易错点：** ECS 是设计范式，Unity Entities 是具体实现；“用了 struct 和数组”不代表已经解决系统依赖。

### Q145. Mono、IL2CPP、AOT 和代码裁剪有什么关系？

**定位：** P1 · 补充题。

**参考答案：** Mono 与 IL2CPP 是脚本后端选择，能力受平台限制；IL2CPP 将托管中间代码转换为 C++，再由原生工具链提前编译。AOT 平台限制部分动态代码生成，裁剪还可能移除静态分析看不到的代码。经反射和泛型间接访问的类型需使用保留规则、显式引用或代码生成，并在真实构建中验证。参见 [IL2CPP 限制][T24]。

**易错点：** “编辑器能跑”不能证明 IL2CPP 构建正确；IL2CPP 仍有托管语义与 GC，并非把业务变成手动内存管理。

## 七、游戏数学与几何（10 题）

### Q146. 点积与叉积在游戏中怎么用？

**定位：** P0 · 面经题意 [M01]。

**参考答案：** 点积 `a·b=|a||b|cosθ`，可判断朝向夹角、做投影与光照；单位前方向与目标方向点积大于 `cos(半视角)` 可判断目标在视锥角范围内。三维叉积给出垂直方向，其模是平行四边形面积，可求法线与转向关系。二维常用标量叉积 `ax*by-ay*bx` 判断左右侧。

**易错点：** 角度判断前处理零长度向量；叉积符号依坐标约定，不能脱离左右手系死背方向。

### Q147. TRS、MVP 与矩阵乘法顺序怎样理解？

**定位：** P0 · 面经题意 [M02] 的空间变换主题。

**参考答案：** 以列向量约定为例，先缩放再旋转再平移可写 `M=T*R*S`，顶点到裁剪空间为 `p_clip=P*V*M*p_local`，右侧变换先作用。点的齐次分量通常为 1，方向为 0，因此平移只影响点。纯正交旋转矩阵有 `R⁻¹=Rᵀ`；含非均匀缩放的完整矩阵不能直接转置求逆。

**易错点：** 行向量约定的乘法顺序不同；矩阵内存行主序或列主序与数学上采用行向量或列向量不是同一概念。

### Q148. 透视投影、正交投影与狙击镜效果如何理解？

**定位：** P0 · 面经题意 [M02] 的投影主题、[M10] 的狙击开镜主题。

**参考答案：** 透视投影经过齐次除法产生近大远小，正交投影中物体投影尺寸不因相机距离直接变化。全屏开镜可减小透视相机 FOV；若只让镜内放大、镜外正常，可增加相机将较小 FOV 画面渲染到纹理，再用镜片区域合成，同时处理遮罩、视差和性能预算。FOV 改变还需配合灵敏度与动画设计。

**易错点：** 缩小 FOV 与把相机前移并不等价，后者会改变遮挡和透视关系。

### Q149. 欧拉角、四元数、Lerp 与 Slerp 怎样选择？

**定位：** P0 · 补充题。

**参考答案：** 欧拉角直观但依旋转顺序，存在万向节锁和角度跳变；单位四元数适合组合与插值旋转，q 与 -q 表示同一旋转。Slerp 沿四维单位球面插值旋转，可提供相应恒定角速率；归一化线性插值较便宜但角速度通常不均匀。选短路径时先根据点积调整四元数符号。

**易错点：** 不要逐分量插值欧拉角而忽略 359° 到 1° 的跨界，也不要长期不归一化四元数。

### Q150. 如何判断二维点在三角形内部？

**定位：** P0 · 补充题。

**参考答案：** 对按同一绕序排列的 A、B、C，计算点 P 相对三条有向边的叉积，同号或在允许边界范围内则位于内部或边上。也可求重心坐标 `P=uA+vB+wC`，检查 `u+v+w=1` 且各分量非负。先判断三角形是否退化，并明确边界是否算命中；三维问题还需要共面或投影处理。

**易错点：** 浮点误差容限应考虑坐标尺度，面积法也会有舍入和退化问题。

### Q151. 如何判断二维两条线段是否相交？

**定位：** P0 · 面经题意 [M07]。

**参考答案：** 先做包围盒排斥，再用方向叉积判断两端点是否位于另一线段的两侧。严格异侧时可确认普通相交，叉积为零时需额外判断点是否位于线段范围，处理共线重叠和端点接触。整数坐标需选择足够宽的类型计算叉积，浮点输入需明确误差策略。

**易错点：** 只检查两个叉积乘积小于零会漏掉端点与共线情况；乘积本身还可能溢出。

### Q152. 如何判断二维圆与填充三角形相交？

**定位：** P1 · 补充题。

**参考答案：** 若圆心在三角形内，已经相交；否则计算圆心到三条边线段的最近距离，任一距离不超过半径就相交。这也覆盖顶点被圆包含的情况。点 C 到线段 AB 的最近点可由 `t=clamp(dot(C-A,B-A)/|B-A|²,0,1)` 求得，再比较距离平方与 r²。

**易错点：** 必须区分填充区域与仅边界相交；退化线段要单独处理，避免除零。

### Q153. 射线与平面、球体怎样求交？

**定位：** P1 · 补充题。

**参考答案：** 写射线为 `P(t)=O+tD,t≥0`。平面 `N·P+d=0` 给出 `t=-(N·O+d)/(N·D)`，分母接近零时判断平行或共面。球体代入 `|O+tD-C|²=r²` 得到二次方程，判别式决定交点数量，再选符合范围的最近 t。D 不必单位化，但方程系数必须保留 `D·D`。

**易错点：** 直线有交点不代表射线有正向交点；射线起点在球内时最近有效解通常是出射点。

### Q154. 如何在圆盘或圆锥内均匀随机采样？

**定位：** P1 · 补充题。

**参考答案：** 圆盘面积均匀采样可令 `r=R*sqrt(u)`、`φ=2πv`，u、v 独立均匀分布于 `[0,1)`；直接均匀取半径会使中心过密。圆锥方向按立体角均匀采样，应均匀取 `cosθ` 于 `[cosθmax,1]`，再均匀取方位角，构造局部方向后变换到发射朝向。

**易错点：** “角度均匀”“投影面积均匀”和“立体角均匀”是不同需求，散射手感要先确定目标分布。

### Q155. IEEE 754 binary32 怎样表示浮点数？比较时注意什么？

**定位：** P0 · 补充题。

**参考答案：** binary32 使用 1 位符号、8 位指数、23 位显式小数，正规数含隐含首位，共 24 位有效二进制位。最大有限值约 `3.4×10^38`，最小正规正数为 `2^-126`，最小正次正规数为 `2^-149`，还编码零、无穷和 NaN。计算会舍入，比较测量或计算结果时可结合绝对与相对误差。

**易错点：** 数值范围不等于精度，NaN 不等于自身；C++ 的 float 是否采用该格式仍属于目标平台条件。

## 八、计算机图形学与渲染（25 题）

### Q156. 一个三角形如何从顶点数据变成屏幕像素？

**定位：** P0 · 面经题意 [M02]、[M07]。

**参考答案：** CPU 准备可见对象、状态与绘制命令，GPU 读取顶点和索引，经顶点处理变换到裁剪空间，进行图元组装、裁剪、透视除法和视口变换，再光栅化生成片元。片元着色与深度、模板、混合等操作共同产生渲染目标结果，最后可能经过后处理与显示转换。部分测试可被硬件提前执行。

**易错点：** 片元不是最终像素，可能被丢弃或与其他片元合成；也不是所有现代管线都必须经过完全相同的可选阶段。

### Q157. 一个有 2000 个顶点的模型，顶点和片元着色器各运行多少次？

**定位：** P1 · 面经题意 [M10]。

**参考答案：** 无法只根据模型顶点数确定。顶点调用受索引重用、顶点缓存、实例数、Pass 数以及具体管线影响，阴影等额外 Pass 还会重复处理。片元调用受投影覆盖、分辨率、遮挡、Overdraw、MSAA 与采样频率、辅助执行等影响。应先明确“一次绘制还是整帧”和具体统计指标。

**易错点：** 回答“顶点恰好 2000 次，片元恰好屏幕像素数”忽略了绘制次数和实际覆盖。

### Q158. 深度测试、深度写入与 Early-Z 有什么区别？

**定位：** P0 · 面经题意 [M08]。

**参考答案：** 深度测试决定片元是否通过遮挡比较，深度写入决定通过后是否更新深度缓冲，两者可以分别配置。Early-Z 在片元着色前排除确定不可见的工作。片元修改深度、丢弃或产生副作用时，会限制某些提前测试或提前写入优化，实际行为与 API、Shader 声明和硬件有关。参见 [Early Fragment Test][T27]。

**易错点：** 不要绝对声称“用了 discard，所有 GPU 就完全不能 Early-Z”，应区分提前测试、写入与具体规则。

### Q159. Z-fighting 为什么产生？Reversed-Z 为什么有帮助？

**定位：** P1 · 补充题。

**参考答案：** 深度精度有限，几何深度过近或几乎共面时，比较结果可能随像素和帧波动。透视深度分布与距离相关，过近的近裁剪面会加重精度分配问题。可合理设置裁剪范围、消除共面几何、适度偏移，并使用匹配 API 约定的浮点 Reversed-Z，把近处映射到 1、远处映射到 0，改善精度分布。参见 [深度精度分析][T28]。

**易错点：** 仅反转比较函数不够，投影、清屏深度和相关采样公式必须一致。

### Q160. 前向渲染与延迟渲染如何选择？

**定位：** P0 · 面经题意 [M06]。

**参考答案：** 前向路径绘制物体时直接计算光照，处理透明与多种材质较直观；延迟路径先记录法线、材质等 G-buffer，再对可见表面做光照，有利于管理大量光源，但增加缓冲带宽、材质表达和抗锯齿方面的约束。Forward+、Clustered 等又改变了光源筛选成本，实际引擎常采用混合方案。

**易错点：** “光多必用延迟”忽略移动端带宽、分辨率、光源覆盖、透明比例和硬件架构。

### Q161. 半透明物体为什么要排序？如何处理相互交叉？

**定位：** P0 · 面经题意 [M06]。

**参考答案：** 常规透明混合如 `Cout=Cs*αs+Cd*(1-αs)` 与顺序有关，通常先画不透明，再将透明对象从远到近绘制，保留深度测试但常关闭深度写入。按物体中心排序不能正确处理所有交叉面，可考虑拆分几何、深度剥离或逐像素片元存储等顺序无关方法，代价是额外带宽、存储和 Pass。

**易错点：** 加权混合 OIT 等是近似方案；预乘 Alpha 必须配套正确混合因子，不能与直通 Alpha 随意混用。

### Q162. 法线为什么要用逆转置矩阵？法线贴图怎样起作用？

**定位：** P0 · 面经题意 [M02] 的法线贴图主题，补充变换推导。

**参考答案：** 法线需要在变换后继续垂直于表面切向量，因此对可逆线性变换 M，使用 `(M⁻¹)ᵀ` 变换法线并归一化；纯旋转时可简化，非均匀缩放时不能直接套位置矩阵。切线空间法线贴图解码局部法线，再通过 TBN 基变到光照计算空间。它改变光照方向，不直接增加轮廓几何。

**易错点：** 法线贴图是数据纹理，通常不能做 sRGB 解码；切线手性和镜像 UV 也需正确处理。

### Q163. 双线性、三线性、各向异性过滤与 Mipmap 有什么关系？

**定位：** P0 · 面经题意 [M02] 的纹理采样主题。

**参考答案：** 双线性在同一级纹理中混合邻近 texel；三线性再混合相邻 Mip 层，减少层级切换突变；各向异性过滤针对倾斜表面不对称的采样覆盖做更合理的取样。Mipmap 用逐级低分辨率版本改善缩小采样与缓存访问，完整二维方形链在理想情况下约增加基础层三分之一存储。

**易错点：** Mipmap 主要解决缩小采样，不能代替放大时真正缺失的纹理细节。

### Q164. 纹理显存怎样估算？PNG 压缩能直接减少 GPU 采样内存吗？

**定位：** P0 · 面经题意 [M02] 的移动纹理格式主题，补充计算。

**参考答案：** 未压缩 RGBA8 基础层约占 `宽×高×4` 字节，例如 2048² 约 16 MiB，完整常规 Mip 链约 21.3 MiB。GPU 块压缩按块数乘块字节计算，并逐级计入 Mip；例如 ASTC 6×6 每块 16 字节，边缘不足一块也需计入。PNG 是文件编码，运行时通常要解码或转换，不能直接当作 GPU 纹理存储大小。

**易错点：** ASTC、ETC2、BC 系列是否可用取决于设备与图形 API；还要考虑平台对齐、CPU 副本和资源元数据。

### Q165. Lambert、Phong 与 Blinn-Phong 怎样区分？

**定位：** P0 · 面经题意 [M08]。

**参考答案：** Lambert 漫反射依赖 `max(N·L,0)`，理想漫反射 BRDF 常含反照率除以 π；Phong 高光常用反射方向 R 与观察方向 V 的点积幂；Blinn-Phong 改用半程向量 `H=normalize(L+V)` 与法线的点积幂。传统经验模型便于实现，但参数未必自然满足能量守恒或真实材质规律。

**易错点：** Phong 光照模型与 Phong 插值着色不是同一概念，前者描述光照，后者描述插值方式。

### Q166. PBR 与 Cook-Torrance 模型的核心是什么？

**定位：** P1 · 面经题意 [M06]。

**参考答案：** PBR 用物理一致的材质与光照模型提高不同环境下的稳定性。常用微表面镜面项为 `D*F*G/[4(N·L)(N·V)]`：D 描述微表面法线分布，F 描述 Fresnel 反射，G 描述遮蔽与阴影。粗糙度改变高光分布；常见金属度工作流区分导体与电介质响应，并需要处理能量分配。参见 [Filament PBR 文档][T29]。

**易错点：** BRDF 不是最终像素颜色，还要结合入射光、余弦、可见性及积分或其近似。

### Q167. 线性空间、sRGB 与 Gamma 校正为什么重要？

**定位：** P0 · 面经题意 [M08]。

**参考答案：** 光照叠加和许多混合应在与光强相对应的线性空间进行。颜色贴图常以 sRGB 编码存储，采样时解码到线性空间，运算后再按目标格式和显示链路编码。法线、深度、粗糙度等数据纹理不应按颜色解码。sRGB 的精确定义是分段传递函数，简单 2.2 次幂只是常见近似。

**易错点：** 引擎和硬件已做颜色转换时，Shader 再手动转换会造成重复校正。

### Q168. Shadow Mapping 如何生成阴影？常见伪影是什么？

**定位：** P0 · 面经题意 [M02]、[M10]。

**参考答案：** 先从光源视角渲染深度，再把可见表面投到光源空间，与保存的最近深度比较，判断光源到该点是否被遮挡。分辨率和投影分配造成锯齿，数值误差造成自阴影条纹，适度深度或法线偏移可缓解，但偏移过大会让阴影脱离物体。方向光可用级联在相机近处分配更多精度。

**易错点：** 增加分辨率不能消除所有偏移和级联切换问题；光源、深度约定与采样坐标必须一致。

### Q169. PCF 与 PCSS 有什么区别？

**定位：** P1 · 面经题意 [M06]。

**参考答案：** PCF 对多个采样点先做深度比较，再平均可见性，主要平滑边缘。PCSS 先搜索遮挡物估计平均距离，再根据光源大小、遮挡物和接收面的关系估算半影，最后使用对应核进行过滤，近接触处更硬、远离处更软。它是一种有限采样的近似，仍受偏移与采样预算影响。参见 [NVIDIA PCSS 说明][T30]。

**易错点：** 先平均深度再只比较一次，不等于 PCF；PCSS 也不是完整的面积光源可见性积分。

### Q170. IBL 怎样近似环境光？有哪些限制？

**定位：** P1 · 面经题意 [M06]。

**参考答案：** IBL 用环境图描述各方向入射光，再与材质响应积分。实时方法常预计算漫反射辐照度、按粗糙度预过滤镜面环境图，并用 BRDF 查找表组合近似结果。探针数量与位置有限时会出现局部视差和动态变化误差，遮挡也需额外处理。实现例子见 [Filament 环境光章节][T29]。

**易错点：** 从一张环境图采样反射方向不等于准确重建周围所有几何、遮挡和动态物体。

### Q171. AO、SSAO 分别是什么？屏幕空间方法有什么缺陷？

**定位：** P1 · 面经题意 [M07]。

**参考答案：** AO 近似描述表面周围方向受到几何遮挡的程度，常用来调制间接光的接触感；SSAO 由屏幕深度与法线等信息估计附近遮挡，因此成本相对可控。它缺少屏幕外和被遮住的完整几何，可能产生边缘光晕、薄物体错误与噪点，需要合理的采样半径、深度判定、滤波与时域稳定。

**易错点：** AO 不是所有光源阴影的替代品，把 AO 无差别乘在所有直接光上可能过度变暗。

### Q172. SSR、反射探针、平面反射和光追反射怎样比较？

**定位：** P1 · 面经题意 [M06] 的倒影追问。

**参考答案：** SSR 沿反射方向在屏幕深度中寻找命中，能利用当前画面却缺少屏幕外信息；探针用环境图近似反射，便宜但局部视差和动态更新有限；平面反射从镜像相机再渲染场景，对理想平面较准确但增加绘制成本；光追可查询更完整场景，却需要加速结构、采样和降噪预算。

**易错点：** 实际项目常组合多种方法，不能仅凭看到反射就判断用了哪一种技术。

### Q173. MSAA、FXAA、TAA、SSAA 各解决什么问题？

**定位：** P0 · 补充题。

**参考答案：** MSAA 对覆盖和深度等使用多样本，主要改善几何边缘，默认并非每个样本完整着色；FXAA 在最终图像上检测和平滑边缘，便宜但会模糊；TAA 累积重投影后的历史样本，可改善时间闪烁但需处理拖影与新暴露区域；SSAA 以更高采样分辨率渲染后降采样，质量直接但成本高。

**易错点：** MSAA 不能自动消除所有纹理、高光和 Shader 内部走样；抗锯齿还需与材质与采样配合。

### Q174. 高斯模糊和 Bloom 怎样实现？

**定位：** P1 · 面经题意 [M02] 的高斯模糊主题，补充 Bloom。

**参考答案：** 二维高斯核可分离为横向与纵向一维卷积，对 K×K 核可把每像素采样量从约 K² 降到约 2K，再结合降采样降低成本。Bloom 通常从 HDR 画面提取或加权明亮部分，在多级尺度模糊后加回，最后与色调映射等阶段协调。需处理纹理边界、归一化权重和颜色空间。

**易错点：** 直接对整幅画面做一次模糊不等于 Bloom，也不能随意交换所有后处理的顺序。

### Q175. 视锥剔除、背面剔除和遮挡剔除有什么区别？

**定位：** P0 · 补充题。

**参考答案：** 视锥剔除排除相机视野外的对象，常用包围体与六个平面测试；背面剔除根据绕序排除不朝向观察者的图元；遮挡剔除排除被前方几何挡住的对象，可以利用层次深度或其他可见性结构。剔除本身也有成本，包围体更新和测试粒度应与场景规模匹配。

**易错点：** 半透明遮挡物通常不能简单当作完全遮挡；等待 GPU 查询结果还可能造成 CPU/GPU 同步停顿。

### Q176. BVH、四叉树和八叉树如何选择？

**定位：** P1 · 面经题意 [M06]。

**参考答案：** BVH 将对象分组并用层次包围体包裹，子包围体可重叠，常用于射线与碰撞查询；四叉树和八叉树按空间区域递归划分，分别适合二维与三维空间组织。选择依据包括对象分布、尺度差异、动态更新和查询类型。动态 BVH 可 refit 或重建，空间树则要处理跨格对象与空区域。

**易错点：** 八叉树每节点最多八个子节点，不代表它在任何场景都比二叉 BVH 更浅或更快。

### Q177. CPU 与 GPU 怎样协作？为什么读回容易卡？

**定位：** P1 · 面经题意 [M10]。

**参考答案：** CPU 准备资源和命令，GPU 异步执行，二者通过命令队列、缓冲区与同步原语协调。CPU 立即读取尚未完成的 GPU 结果，可能等待 GPU 排空相关工作；可以使用异步读回、环形缓冲和延后消费降低等待。统一内存减少某些复制需求，也仍有缓存一致性、资源状态与执行顺序问题。

**易错点：** 提交绘制返回只表示命令已进入处理流程，不能据此立即覆写或释放 GPU 仍在使用的资源。

### Q178. Shader 中的 if 一定慢吗？如何优化 Shader？

**定位：** P1 · 面经题意 [M08]。

**参考答案：** 若执行组内分支条件一致，分支可跳过昂贵工作；若线程走不同路径，可能出现分歧和掩码执行。编译器也可能改用条件选择，因此不能只数 if。应根据 GPU 数据判断瓶颈是纹理带宽、算术、寄存器压力、覆盖或同步，再减少冗余采样、昂贵计算和无用变体，并验证精度。

**易错点：** 用 lerp 强制计算两个昂贵分支可能更慢；降低精度也不能牺牲必要的坐标范围和稳定性。

### Q179. 骨骼动画与 GPU Skinning 的原理是什么？

**定位：** P0 · 面经题意 [M10]。

**参考答案：** 顶点保存影响骨骼索引与权重，根据当前骨骼变换与逆绑定姿态构造蒙皮矩阵，在一致空间下将各骨骼变换结果加权混合。GPU Skinning 将这部分顶点计算移到 GPU，减少某些 CPU 变形与顶点上传工作，但骨骼姿态更新、矩阵传输和多 Pass 计算仍有成本。可配合动画 LOD 与姿态更新降频。

**易错点：** 权重、绑定空间和法线处理错误会导致拉伸或错误光照；线性蒙皮还存在扭曲塌陷问题。

### Q180. 移动端图形优化为什么特别关注带宽和 Overdraw？

**定位：** P1 · 补充题。

**参考答案：** 移动设备常受功耗、带宽和散热限制，许多 GPU 采用分块架构以在片上处理局部像素；过多渲染目标读写、全屏 Pass、透明叠加和不合理附件保存会增加负担。可降低无效覆盖与目标精度，使用合适纹理格式、分辨率和渲染 Pass 组织，并在目标芯片上看持续运行表现。

**易错点：** 不是所有移动 GPU 都有完全相同架构；单次冷机 FPS 不能代表发热后的稳定帧率。

## 九、客户端系统设计（12 题）

### Q181. FSM、行为树如何选择？怎样处理长按射击？

**定位：** P0 · 面经题意 [M04]。

**参考答案：** FSM 明确表达状态和转移，适合有限且清晰的模式；行为树用组合节点组织决策，叶子通常返回成功、失败或运行中，适合可复用的层次行为。长按射击应区分按下事件、持续输入和松开事件，进入状态做一次性初始化，状态内按射速调度发射，退出时取消后续任务。复杂情况下可将层次状态与行为树组合。

**易错点：** 行为树不是二叉树；每帧重新进入射击状态可能重复创建任务或绕过冷却。

### Q182. 事件系统怎样解耦，又不变成难以追踪的全局消息网？

**定位：** P1 · 面经题意 [M09] 的事件系统主题，补充工程约束。

**参考答案：** 明确事件类型、发布者、有效载荷与订阅生命周期，按模块或场景限定作用域。同步派发需处理重入和监听列表被修改，异步派发需规定线程、顺序、延迟与背压。关键请求应有明确返回通道，日志记录事件 ID 与来源以便追踪。用订阅令牌或作用域绑定解除监听。

**易错点：** 事件传裸对象引用却延迟到下一帧处理，可能遇到对象销毁或复用，宜传稳定 ID 或受控所有权。

### Q183. 技能与 Buff 系统如何支持扩展？

**定位：** P1 · 补充题。

**参考答案：** 将静态配置、施放状态、目标选择、效果执行与表现分离。技能明确消耗、前摇、生效、后摇、打断和冷却；Buff 明确叠层、刷新、互斥、周期触发和移除原因。属性计算规定基础值、加法、乘法与覆盖的顺序，服务器裁定关键结果，客户端预测和展示通过事件对应。

**易错点：** 移除 Buff 时直接“减回当时加的数”可能被叠层和乘算破坏，最好从可追踪修改项重新计算。

### Q184. 大量计时器应该怎样管理？

**定位：** P1 · 补充题。

**参考答案：** 小规模可直接扫描，规模增加时按到期时间用最小堆，若精度与时间范围适合可考虑时间轮。计时器保存 ID、目标时间、重复策略与取消状态；每帧执行设预算，暂停区分逻辑时间与真实时间。重复任务可基于原计划时间推进以减少漂移，并明确错过多个周期时补执行还是合并。

**易错点：** 回调内删除或新建计时器可能使容器失效；到期一万个任务也不能无预算地全部压进一帧。

### Q185. 资源热更新与代码热更新有什么区别？完整更新流程怎样设计？

**定位：** P1 · 补充题。

**参考答案：** 资源热更新替换资产和配置，代码热更新改变执行逻辑，需要目标运行时支持相应机制，不能把资源包视为通用代码加载器。流程包括获取版本清单、校验兼容性、下载到临时区域、验证完整性与真实性、原子切换版本，并保留失败回退。要处理断点续传、空间不足和旧进程仍在使用资源。

**易错点：** 普通哈希能检测损坏，但若清单本身不可信就不能证明来源；运行时代码能力也受 AOT 与平台约束。

### Q186. 一个可靠的异步资源管理器要具备什么？

**定位：** P1 · 补充题。

**参考答案：** 按资源标识合并重复请求，维护加载中、成功、失败与释放状态，明确句柄所有权、依赖和缓存预算。多个调用方共享一次加载时，某一方取消不应直接取消其他人仍需要的操作。回调执行前检查场景或请求代次，释放时等待消费者与依赖关系都满足条件，并记录加载链路供诊断。

**易错点：** 请求返回后界面已关闭、同一格子已改绑，是不同于“资源加载失败”的生命周期问题。

### Q187. 大世界与无缝切换如何控制加载和内存？

**定位：** P1 · 面经题意 [M10] 的演出无缝切换主题，补充分区加载。

**参考答案：** 按空间或场景逻辑划分加载单元，结合玩家位置、速度和相机预测预取；采用加载与卸载不同阈值的迟滞，避免边界抖动。限制每帧实例化和上传预算，按距离切换 LOD，并以过渡演出覆盖必要等待。叙事演出与操作切换还需衔接相机、角色姿态、输入权限和当前世界状态。

**易错点：** 无缝不代表全部常驻，旧新区同时存在时的内存峰值往往比稳定状态更危险。

### Q188. 数据驱动、配置表和序列化协议怎样设计？

**定位：** P1 · 补充题。

**参考答案：** 将易变的数值、资源映射和规则参数外置，用稳定 ID 建立引用，并在构建期检查类型、范围、重复键和依赖。运行时使用适合访问模式的紧凑数据，协议明确版本、可选字段、默认值和未知字段策略。JSON 易读，二进制格式通常更紧凑，但选择应依据工具链、兼容与实测成本。

**易错点：** 不能以表格行号代替稳定 ID，也不能把 C++ 结构体原始内存直接视为跨版本网络协议。

### Q189. AoS 与 SoA 为什么会影响角色批量更新性能？

**定位：** P1 · 补充题。

**参考答案：** AoS 把一个对象的各字段放在一起，适合一起访问某个对象的完整数据；SoA 把同一字段集中成数组，适合系统只遍历速度、位置等少量热字段，可减少无关数据加载并促进 SIMD。实际可采用混合布局，将名字、配置和调试信息等冷数据分离，再根据访问频率与对象规模评估。

**易错点：** SoA 不保证所有操作更快，随机访问完整对象和频繁结构变化也有代价。

### Q190. 为什么实体 ID 往往要带 generation？

**定位：** P1 · 补充题。

**参考答案：** 对象池或槽位表会复用索引，旧回调只保存索引时可能误命中新对象。句柄用“索引＋代次”组成，释放槽位后更新代次，访问时同时验证范围、存活和代次，便可识别大量过期引用。对外使用句柄，对内可以紧凑存储并迁移对象，而不用暴露不稳定地址。

**易错点：** 代次位宽有限会回绕，还需考虑使用寿命与复用速率；验证成功到使用之间若存在并发销毁也仍需同步。

### Q191. 移动端发热、内存紧张时，画质怎样动态调整？

**定位：** P1 · 补充题。

**参考答案：** 先建立目标帧预算与各档质量配置，监控持续帧时间、内存压力及可获得的热状态。优先调整已证实的瓶颈，如 GPU 紧张时降低分辨率、阴影和特效，CPU 紧张时降低远处动画或 AI 更新频率。升降档采用迟滞和冷却时间，并保护输入、网络和关键玩法反馈。

**易错点：** CPU 瓶颈时只降分辨率可能没有收益；过于频繁切档会造成画面闪变和资源反复加载。

### Q192. 如何建立资源与构建管线的质量检查？

**定位：** P1 · 补充题。

**参考答案：** 在导入与构建阶段自动检查纹理尺寸和格式、材质变体、网格与骨骼预算、重复依赖、资源命名和丢失引用。构建产物包含版本、依赖清单、符号与资源哈希，记录体积和耗时变化，并做目标平台的启动、加载和关键流程验证。可重复构建需要固定工具版本和关键输入。

**易错点：** 只验证编辑器能打开场景，会遗漏构建裁剪、平台格式和资源包依赖错误。

## 十、UE 与项目面试（8 题）

### Q193. Actor、Pawn、Character、Controller、GameMode、GameState 怎样分工？

**定位：** P0 · 补充题，UE 方向优先。

**参考答案：** Actor 是可存在于世界中的基础对象；Pawn 是可被控制的实体；Character 在 Pawn 上提供常见角色移动等支持；Controller 表达玩家或 AI 控制关系。多人场景中 GameMode 负责权威规则且存在于服务器，GameState 保存需要向客户端复制的公共比赛状态，PlayerState 表达玩家相关复制状态。框架说明见 [Epic Gameplay Framework][T35]。

**易错点：** 不能把所有客户端都需要读取的比赛信息只放进 GameMode。

### Q194. UObject 怎样被 GC 跟踪？几种对象指针如何选择？

**定位：** P0 · 补充题，UE 方向优先。

**参考答案：** UObject 由引擎创建与回收体系管理，GC 沿可识别的引用关系判断可达性。UObject 成员中需要保活的引用常用带 UPROPERTY 的 TObjectPtr，观察引用可用 TWeakObjectPtr，延迟加载的资产引用可用 TSoftObjectPtr；非 UObject 所有者需要强持有时按场景使用相应引擎机制。参见 [Epic 对象指针][T31]。

**易错点：** 单独声明未被正确跟踪的 TObjectPtr 不等于自动保活；也不要用普通 shared_ptr 管理 UObject 的删除。

### Q195. UCLASS、UPROPERTY、UFUNCTION 与 UHT 有什么关系？

**定位：** P1 · 补充题。

**参考答案：** UE 用标记与 Unreal Header Tool 生成支持类型、字段和函数元数据的代码，再与 C++ 编译配合，为编辑器、蓝图、序列化、GC 和网络等系统提供信息。各说明符声明具体能力，标记属性并不意味着自动实现所有功能。需要遵守引擎支持的类型与声明规则，普通 C++ 类型仍可用于不需要这些系统的模块。

**易错点：** UHT 不是在运行时扫描任意 C++ 源码；反射也不意味着所有 C++ 特性都能暴露给蓝图。

### Q196. 属性复制、RepNotify、RPC 与网络所有权怎样配合？

**定位：** P1 · 补充题。

**参考答案：** 属性复制传播当前状态，RepNotify 在相关复制更新时通知接收端处理表现；RPC 表达远端调用或事件。客户端向服务器发 Server RPC 通常要求对象归该连接所有，并满足复制条件；服务器 Multicast 面向该对象相关的客户端，而非无条件全部玩家。持续状态还要支持晚加入客户端恢复。参见 [Epic RPC 规则][T32]。

**易错点：** 不要用每帧 Reliable RPC 同步所有状态，也不能让客户端单方面调用就越过服务器权威校验。

### Q197. Nanite 与 Lumen 各解决什么问题？

**定位：** P1 · 面经题意 [M06]。

**参考答案：** Nanite 主要处理高细节几何的虚拟化、层次细节选择、流送与可见性，减轻部分传统几何 LOD 管理；Lumen 面向动态全局光照与反射，结合屏幕和场景表示上的追踪等机制求近似结果。它们是不同子系统，可分别产生几何、材质、带宽和追踪成本，支持范围随版本变化。参见 [Nanite][T33]、[Lumen][T34]。

**易错点：** 不应回答“开了 Nanite 就不用优化”或“Lumen 就是一次普通屏幕空间反射”。

### Q198. 怎样介绍自己的项目，才能经得住继续追问？

**定位：** P0 · 面经题意 [M03]、[M06]。

**参考答案：** 按“业务目标与约束—本人负责范围—核心方案—关键难点—验证结果—当前不足”组织。选一个能展开到数据结构、生命周期与性能证据的模块，讲清为何选择该方案，以及规模增长或需求变化时如何改进。区分本人实现、团队已有能力和计划中的功能，技术细节要能与实际代码或记录对应。

**易错点：** 不要把教程步骤、同伴贡献或设想描述为自己的已完成成果，也不要只罗列用了哪些框架。

### Q199. 怎样证明一次性能优化有效？

**定位：** P0 · 补充题。

**参考答案：** 固定设备、构建配置、场景路径、输入与网络条件，记录优化前后的 CPU/GPU 帧时间、分配、内存峰值及相关质量指标。除平均值外看 P95/P99、长帧数量和持续运行趋势，解释测量窗口与采样方式。先用证据确认瓶颈，再比较方案，并报告画质、内存或维护成本的变化。

**易错点：** 编辑器一次 FPS 上升不能证明稳定收益；不要捏造优化数据，没有测量就说明尚未量化。

### Q200. 为什么做游戏客户端？遇到不会的问题和反问环节怎样回答？

**定位：** P0 · 面经题意 [M06]、[M07] 的动机与交流主题，补充回答方法。

**参考答案：** 动机应连接真实经历与客户端工作，例如对即时反馈、交互系统、渲染或性能的兴趣，并用做过的事情支撑。不会的问题先确认条件，明确已知与不确定部分，再从机制推理或提出验证办法。反问可围绕团队当前技术问题、岗位职责、项目阶段和新人交付预期，判断双方是否匹配。

**易错点：** 只说“喜欢玩游戏”不足以解释职业选择，也不要将猜测说成确定实现。

## 复习路线与自测方法

### 按方向分配精力

| 方向 | 第一优先级 | 第二优先级 |
| --- | --- | --- |
| C++ / UE 客户端 | Q001—040、Q066—110、Q193—199 | 数学、图形学与客户端系统设计 |
| Unity 玩法 / 系统 | Q041—065、Q111—145、Q181—192 | C++ 基础、网络同步与算法 |
| 图形 / 引擎 | Q001—040、Q146—180 | 并发、资源管线与性能验证 |
| 校招尚未定细分方向 | 各章 P0、一个能深讲的项目、算法现场实现 | 按投递岗位补 P1，最后补 P2 |

### 两周复习示例

| 时间 | 学习内容 | 当天产出 |
| --- | --- | --- |
| 第 1—2 天 | C++ 40 题 | 口述对象模型、所有权、容器；画出两种生命周期图 |
| 第 3 天 | C# 25 题 | 解释 GC、装箱、闭包、异步，并举项目中的例子 |
| 第 4—5 天 | 操作系统与网络 30 题 | 推演一个线程通信流程和一个预测校正流程 |
| 第 6—7 天 | 算法 15 题 | 每题先独立写，再补空输入、重复值和极值用例 |
| 第 8—9 天 | Unity 35 题 | 整理一个 UI、资源或性能问题的真实定位记录 |
| 第 10—11 天 | 数学与图形学 35 题 | 手推几何题，画管线，解释一个实际画面缺陷 |
| 第 12 天 | 客户端设计 12 题 | 给一个技能或资源系统画出状态与所有权关系 |
| 第 13 天 | UE 与项目 8 题 | 准备 2 分钟项目介绍和 10 分钟深挖版本 |
| 第 14 天 | 模拟面试与复盘 | 记录答错原因，按概念、实现、表达三类补缺口 |

每题可标记为 **0：不会；1：能解释概念；2：能说明机制与边界；3：能举例、推导或实现**。P0 尽量达到 2，自己简历上的知识点争取达到 3。题量是覆盖范围，不能替代项目理解与手写能力。

### 一次 60 分钟的模拟安排

- 5 分钟：自我介绍与项目目标。
- 15 分钟：从语言与计算机基础中随机选题，并连续追问。
- 15 分钟：沿项目系统讨论数据流、所有权、规模和失败场景。
- 20 分钟：完成一道算法题，解释复杂度并验证边界。
- 5 分钟：岗位交流与反问。

该安排是练习建议，不是腾讯官方面试时长或流程。
