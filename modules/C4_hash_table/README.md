# C4 · 手写 unordered_map（哈希表 · 链地址法）

难度 ⭐⭐⭐⭐ · 预计 3h

## 为什么大厂爱考
`unordered_map` 是除 `vector`/`string` 外用得最多的容器，而它的底层——**哈希表**——是面试里"算法 + 工程"双重高频题。面试官借它考查一整套硬核知识：哈希表怎么解决冲突、什么是负载因子、为什么以及何时要 rehash、rehash 时下标为什么必须重算、`operator[]` 为什么会"凭空"插入元素、平均 O(1) 是怎么来的、最坏情况又为什么退化成 O(n)。把这道题写明白，等于把哈希表的工程实现彻底吃透。

## 背景知识

### 1) 哈希表与"链地址法"解决冲突
哈希表用一个数组（**桶数组** `buckets_`）存数据，key 通过哈希函数映射到某个桶下标：`idx = hash(key) % bucket_count`。不同 key 可能算出同一个 idx（**哈希冲突**）。最经典的解法是**链地址法**：每个桶挂一条链表，冲突的元素都串在同一条链上。

```
buckets_[idx] -> (k1,v1) -> (k2,v2) -> (k3,v3)
```

- **查找**：定位桶 → 在桶链里线性比对 key。
- **插入**：定位桶 → 链尾追加。
- **删除**：定位桶 → 链中摘除结点。

只要哈希均匀、每条链都很短，三种操作都接近常数时间。

### 2) 负载因子与 rehash（扩容再散列）
桶数固定，元素越来越多，链就越来越长，查找退化为 O(链长)。用**负载因子**衡量拥挤度：

```
load_factor = size / bucket_count   ≈ 平均每条桶链的长度
```

一旦它超过阈值 `max_load_factor`（本模块取 1.0），就把桶数**翻倍**并 **rehash**：新建一个更大的桶数组，把所有元素按"新桶数"重新分配一遍。链重新变短，查询回到平均 O(1)。这就是"用一次 O(n) 的整体搬迁，换后续大量操作的 O(1)"。

### 3) rehash 最大的坑：桶数变了，下标必须重算
桶下标 `idx = hash(key) % bucket_count` **依赖桶数**。rehash 把桶数从 8 变 16，同一个 key 的 idx 往往也变。所以在 `operator[]` 里插入新 key 的正确顺序是：

1. 先判断"再插一个会不会超阈值"，超了就 `rehash(buckets_.size() * 2)`；
2. **rehash 之后再重新算 `idx`**，然后插入。

如果你用扩容前算好的旧 idx 去插新桶数组，元素就插错位置、以后永远查不到——这是最经典的 rehash bug。

### 4) `operator[]` 的"副作用"：访问即插入
`m[key]` 的语义是"返回该 key 的 value 引用；若不存在，**先插入一个默认值 `V{}` 再返回**"。这正是 `m["x"] = 1;` 能工作的原因：先 `operator[]` 插入 `("x", 0)`，再把返回的引用赋成 1。副作用是：哪怕只是 `int v = m["k"];` 读一下，不存在的 `k` 也会被插进去。

### 5) 平均 O(1) vs 最坏 O(n)
哈希均匀时平均 O(1)；但若所有 key 都撞进同一个桶（哈希极差或被恶意构造），就退化成一条长链，操作变 O(n)。这也是为什么真实库（和高安全场景）关心哈希质量、甚至引入随机化种子防 hash-flooding 攻击。

| C4-4 | `rehash(n)` | 新建 n 桶数组，按新桶数重新分配全部元素 |

## 关键坑
- **rehash 后必须重算 `idx`**——别用扩容前的旧下标插入。
- **扩容时机**：判断的是"插入这一个**之后**"会不会超阈值，所以用 `size_ + 1`。
- **`operator[]` 访问即插入**——不存在的 key 会被插入 `V{}`，`size_` 要 `++`。
- **`erase` 用迭代器摘除**：`chain.erase(it)` 后立刻 `return`，别继续用失效的 `it`。
- **删除/未命中也要返回正确的 bool / nullptr**，调用方依赖它判断。

## 面试追问

1. 哈希表怎么解决冲突？链地址法 vs 开放寻址（线性探测/二次探测/双重哈希）各有何优劣？

   **答**：**链地址法**：每个桶挂一条链表（或树），冲突的 key 都进同一桶的链；优点是实现简单、删除容易、负载因子可>1、对高冲突鲁棒；缺点是链表节点各自堆分配、缓存不友好、有指针开销。**开放寻址**：冲突时按探测序列在数组里另找空槽，所有元素都在一块连续数组里；优点缓存友好、无指针无额外分配；缺点删除麻烦（要墓碑标记）、负载因子必须<1 且高负载时探测变长、聚集。探测方式：**线性探测**（+1，最缓存友好但易一次聚集）、**二次探测**（+1,+4,+9…，缓解一次聚集但有二次聚集）、**双重哈希**（步长由第二个哈希决定，分散最好但缓存稍差）。

2. 负载因子是什么？为什么超过阈值要 rehash？rehash 的代价是多少，为什么"摊还"后仍是 O(1)？

   **答**：**负载因子** = 元素数 / 桶数，衡量拥挤程度。超过阈值（`std::unordered_map` 默认 1.0）冲突链变长、查找退化，所以要 **rehash**：分配更多桶（通常翻倍）、把所有元素按新桶数重新分配。单次 rehash 是 O(n)（搬全部元素），看似昂贵；但因桶数**几何增长**，n 次插入只触发 O(log n) 次 rehash、搬迁总量 1+2+4+…+n≈2n=O(n)，**摊还到每次插入仍是 O(1)**——和 vector 扩容同理。

3. rehash 时为什么下标要重算？如果不重算会发生什么？

   **答**：因为元素落在哪个桶由 `hash(key) % 桶数` 决定，rehash 后**桶数变了**，同一 key 的 `% 桶数` 结果随之改变，必须按新桶数**重算下标**把元素放到新位置。若不重算、沿用旧下标，查找时用新桶数算出的下标和元素实际所在的旧下标对不上→**查不到本来存在的数据**，哈希表失去正确性。所以 rehash 本质就是"用新桶数把每个元素重新归位"。

4. `unordered_map::operator[]` 和 `at()`、`find()` 有什么区别？为什么 `operator[]` 会插入元素？

   **答**：`find(k)` 返回**迭代器**，未命中返回 `end()`，**只查不改**，最安全；`at(k)` 返回值引用，**key 不存在就抛 `std::out_of_range`**，适合"应当存在"的访问；`operator[](k)` 在 **key 不存在时插入一个默认构造的值**并返回其引用，所以它**可能改变容器**（size+1）。`operator[]` 会插入是因其语义是"拿到该 key 对应的可写槽位"，不存在就先建一个——这也是为什么对 const map 不能用 `[]`、且只读查询应用 `find`/`at` 而非 `[]`。

5. 哈希表最坏情况为什么是 O(n)？什么是 hash-flooding 攻击，标准库怎么防？

   **答**：哈希表 O(1) 是**平均**情况，前提是哈希把 key 均匀散开。**最坏情况**是所有 key 都哈希到同一个桶（哈希函数差、或被恶意构造），链地址法退化成长度 n 的链表、查找变 O(n)。**hash-flooding 攻击**：攻击者预先算出大量会**碰撞到同一桶**的 key（如 HTTP 参数、JSON 字段）发给服务器，把哈希表打成 O(n) 链，单请求耗尽 CPU→拒绝服务。防御：用**带随机种子的哈希**（SipHash 等），每进程/每表种子不同，攻击者无法离线构造碰撞；有的实现还在链过长时把桶**转成红黑树**（Java HashMap）把最坏降到 O(log n)。

6. 为什么 `unordered_map` 的迭代器在 rehash 后会失效，而指向元素的指针/引用却不会（链地址法下）？

   **答**：rehash 要分配新桶数组、把元素重新分配到新桶，**迭代器**通常实现为"指向桶+桶内位置"或依赖桶遍历顺序，桶结构一变、遍历顺序和内部指针全乱，所以**迭代器失效**。但在**链地址法**下，元素是独立堆分配的节点，rehash 只是把这些节点从旧桶链摘下挂到新桶链——**节点本身没被移动或重建**，所以指向元素（`pair<const K,V>`）的**指针/引用依旧有效**。这是链地址法相对开放寻址的一个优势（开放寻址 rehash 会搬移元素本体，指针也失效）。

7. `std::unordered_map` 用链地址法，那 Google 的 `absl::flat_hash_map` 为什么用开放寻址？缓存友好性如何影响性能？

   **答**：`std::unordered_map` 标准要求"指向元素的指针/引用 rehash 后不失效"、且有特定 `operator[]` 语义，**逼得实现只能用链地址法**（节点稳定），于是每元素一次堆分配、缓存不友好。`absl::flat_hash_map` 不受这些约束，用**开放寻址**把所有 `pair` **平铺在一块连续数组**里（flat），查找时顺着探测序列扫——内存连续、一次缓存行能带进多个槽，**缓存命中率远高**，且省掉每节点分配。现代 CPU 上访存是主要瓶颈，缓存友好带来的加速往往盖过"开放寻址删除要墓碑、扩容要搬元素、指针会失效"的代价，所以追求性能时常选 flat_hash_map；需要"指针稳定"或存超大/不可移动 value 时仍用链地址法（或 `node_hash_map`）。
