# D6 · 对象生命周期与内存布局（lifetime / padding / alignment / EBO）

难度 ⭐⭐⭐⭐ · 预计 3h

## 为什么大厂爱考

“成员按初始化列表还是声明顺序构造？”“为什么两个字段相同的结构体 `sizeof` 不同？”“空类为什么也占 1 字节？”这些题表面像背诵，实际在检查你是否建立了完整的 **C++ 对象模型**：一个对象何时开始/结束生命周期、子对象按什么顺序存在、编译器为何插入 padding、优化空策略对象时哪些地址仍必须唯一。

这些知识直接影响 RAII 资源依赖、崩溃现场还原、二进制协议、SIMD、缓存布局和 ABI。D4 讲“虚函数如何分派”，本模块补上“对象本身如何出生、排布和消亡”。

## 背景知识

### 1) 构造顺序由对象结构决定

对一个派生对象，构造顺序固定为：

1. 虚基类（由最派生类负责）；
2. 直接基类，按基类列表顺序；
3. 非静态数据成员，按**类内声明顺序**；
4. 构造函数体。

析构顺序完全相反。初始化列表只是写“怎么初始化”，不能改变“谁先初始化”。若 `Socket socket_; Logger logger_;` 的 socket 初始化表达式依赖 logger，即使列表先写 logger 也救不了；正确做法是调整成员声明顺序。

### 2) 临时对象的生命周期延长

通常完整表达式结束，临时对象就析构：

```cpp
consume(Token{}); // 调用结束后临时量销毁
```

把临时直接绑定给局部 `const T&`（或合适的右值引用）时，它的生命周期会延长到该引用的作用域结束：

```cpp
const Token& token = Token{}; // token 所在作用域内临时对象仍活着
```

这条规则**不会层层传递**：返回一个绑定临时的引用、把临时绑定到函数形参再保存、从局部引用返回，都可能悬垂。本模块只用存活计数观察安全的局部绑定，不返回引用。

### 3) 对齐与 padding

对象地址必须满足 `alignof(T)`；成员也要从满足自身对齐的位置开始。编译器会在成员之间插入内部 padding，并在末尾加入尾部 padding，保证数组中下一个元素仍正确对齐。

```cpp
struct Poor    { char a; double d; char b; };
struct Compact { double d; char a; char b; };
```

两者有效数据相同，但常见 ABI 下 `Poor` 需要更多填充。具体数值属于编译器/ABI，不能把“24 字节”当语言定律。本实验始终用 `sizeof`、`alignof`、`offsetof` 读取当前实现。

### 4) `alignas` 与向上对齐

实现支持该扩展对齐时，`alignas(64)` 可以提高对象/缓冲区的对齐要求；跨平台测试应优先使用 `alignof(T)` 或 `alignof(std::max_align_t)` 这类标准保证支持的基本对齐。分配器常把地址 `p` 向上取整到 2 的幂 `a`：

```cpp
(p + a - 1) & ~(a - 1)
```

前置条件必须明确：`a` 非零且是 2 的幂、`a` 自身能由整数地址类型表示，并且 `p + a - 1` 不得超出该类型的可表示范围。仅让缓冲区起点对齐不够，每次切块后的地址也必须重新对齐；生产接口通常应以错误返回显式处理非法参数和溢出。

### 5) 空类、EBO 与 `[[no_unique_address]]`

独立空对象大小至少为 1，才能让同类型的两个完整对象拥有不同地址。但空基类子对象通常可以不额外占空间，这叫 **Empty Base Optimization**。策略类、删除器、allocator 常利用它。

C++20 的 `[[no_unique_address]]` 让空成员也可以与别的成员共享地址/尾部 padding，组合优于继承时尤其有用。属性允许优化但不承诺某个固定 `sizeof`；应观测当前 ABI，不把布局细节当跨编译器协议。

## 关键坑

- **初始化列表顺序不生效**：真正顺序是成员声明顺序；开启警告通常会提示 `-Wreorder`。
- **析构依赖要反向设计**：后构造者先析构。成员 A 的析构若要使用 B，B 必须比 A 更早构造。
- **不要返回绑定临时的引用**：局部生命周期延长不会让引用安全地逃出作用域。
- **不要读取 padding 字节作业务判断**：padding 值未指定，逐字节比较结构体也可能因 padding 得到假差异。
- **不要写死对象大小**：字段大小、ABI、编译器选项和继承模型都会影响结果。
- **`align_up` 有前置条件**：位运算公式只适合非零的 2 的幂对齐，且向上取整结果必须可表示；否则无符号回绕会得到错误地址。
- **`[[no_unique_address]]` 会影响地址直觉**：两个不同子对象可能同址，不能用成员地址唯一标识逻辑对象。

## 面试追问

1. **派生类的完整构造/析构顺序是什么？**

   **答**：构造依次为虚基类、直接基类、成员（按声明顺序）、派生构造函数体；析构严格反向，先派生析构体，再成员逆序、基类逆序、最后虚基。这样任一层构造时，它依赖的基础子对象已存在；析构时基础子对象活得更久。

2. **为什么初始化列表顺序不能改变成员构造顺序？**

   **答**：析构必须只有一个静态确定的逆序，否则编译器需要为每个构造函数记录不同顺序，对异常回滚和对象模型都极复杂。语言因此以类内声明顺序作为唯一顺序。初始化列表只提供初始化表达式，建议按声明顺序书写以避免误导和警告。

3. **临时对象绑定到 `const T&` 后总能安全返回这个引用吗？**

   **答**：不能。局部变量声明中直接绑定可延长到局部引用作用域；函数形参所绑定的临时通常只活到包含调用的完整表达式结束；返回引用不会再次延长。`const T& bad(){ return T{}; }` 返回立即悬垂的引用。

4. **为什么空类 `sizeof` 至少为 1，空基类却可能不占空间？**

   **答**：两个同类型完整对象必须有不同地址，数组步长也不能为 0，所以空完整对象至少占一个字节。空基类只是更大对象的子对象，ABI 可让它与派生对象其他存储重合且仍满足地址规则，这就是 EBO。

5. **padding 从何而来？如何减小？**

   **答**：成员起始地址需满足各自对齐，数组元素步长还需满足整个类型对齐，因此编译器插入内部和尾部 padding。常见策略是把高对齐/大成员放前面，把相同对齐成员聚类；但改变公有类型成员顺序会改变 ABI，不能在已发布二进制接口中随意做。

6. **`alignof`、`alignas` 和 `std::max_align_t` 分别是什么？**

   **答**：`alignof(T)` 查询类型要求；`alignas(N/T)` 提高声明实体的对齐；`max_align_t` 代表实现支持的基本类型中最严格的基础对齐。过度对齐类型可能超过普通分配器保证，需要相应 aligned new/allocator。

7. **`[[no_unique_address]]` 与 union 有何不同？**

   **答**：union 在任一时刻通常只有一个活动成员，用共享存储表达互斥状态；`no_unique_address` 不改变成员生命周期，多个成员可同时存在，只允许实现复用空成员或尾 padding 的地址空间。它是布局优化提示，不是手动生命周期工具。

8. **能否用 `memcmp` 判断两个普通结构体相等？**

   **答**：通常不能。padding 字节可能未初始化或值不同，浮点还存在多个位表示语义问题；即使逐字段相等，对象表示也未必相等。应逐字段比较，只有在明确满足 `has_unique_object_representations` 等严格条件并定义好语义时才考虑字节比较。
