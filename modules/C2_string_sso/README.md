# C2 · 手写 string（小字符串优化 SSO）

难度 ⭐⭐⭐ · 预计 2.5h

## 为什么大厂爱考
`std::string` 几乎无处不在，而它最精妙的实现技巧就是 **SSO（Small String Optimization）**：短字符串直接存在对象内部，零堆分配。面试官借它考查：SSO 是什么、为什么能加速、对象布局怎么设计、为什么短串拷贝/移动不能直接复制指针、移动一个短串和移动一个长串有何本质区别。理解 SSO，就理解了"用空间换时间 + 分支特判"这种工业级优化思路。

## 背景知识

### 1) 什么是 SSO，为什么快
程序里大量字符串其实很短（`"id"`、`"name"`、`"GET"`）。如果每个都去堆上 `new`，开销巨大（堆分配慢、还伤缓存）。SSO 让对象**自带一个小缓冲区**（通常 15 字符），短串直接住在里面——**零堆分配、零间接寻址**，极快。只有超过内联容量才搬到堆上。

### 2) 对象布局（本模块写法）
```cpp
char  buf_[16];     // 内联缓冲：短串住这里（15 字符 + 1 个 '\0'）
char* data_;        // 短串时指向 buf_；长串时指向堆
size_t size_;       // 长度
size_t capacity_;   // 容量（短串恒为 15）
```
判断模式只需一句：`bool is_small() const { return data_ == buf_; }`。

> 真正的标准库用 **union** 把 `buf_` 和「堆指针+容量」叠在同一块空间以省内存（`sizeof(std::string)` 通常 32 字节）。这里用独立字段，牺牲一点空间换代码清晰——原理一致。

### 3) SSO 最大的坑：拷贝/移动要重新指向「自己的」buf_
`buf_` 是对象**内部**的数组，每个对象各有一份。短串拷贝时若直接复制 `data_` 指针，新对象的 `data_` 就指向了**旧对象**的 `buf_`；旧对象一析构，新对象立刻变野指针。所以：

- **短串拷贝/移动**：必须把内容 `memcpy` 进**自己的** `buf_`，再令 `data_ = buf_`。
- **短串无法「偷指针」式移动**：因为指针指向源对象内部，移动短串本质上还是一次小拷贝。
- **长串移动**：才能真正 O(1) 接管堆指针，并把源复位成空短串（否则源析构会 `delete` 掉你接管的堆）。

### 4) 始终维持 '\0' 收尾
`c_str()` 要能直接喂给 C 接口，所以任何修改后都要保证 `data_[size_] == '\0'`。分配时记得 `new char[n + 1]`，拷贝时 `memcpy(dst, src, size_ + 1)` 把结尾 `'\0'` 一起带上。

### 5) 释放时只 delete 堆，不 delete buf_
析构/重新分配时，**只有 `!is_small()`（数据在堆上）才能 `delete[] data_`**；短串模式下 `data_` 指向内部 `buf_`，对它 `delete` 是灾难。

## 关键坑
- **短串的 `data_` 必须指向自己的 `buf_`**——拷贝/移动后尤其要检查这一点。
- **`delete[]` 前先判 `!is_small()`**，否则会去 `delete` 内部缓冲。
- **移动长串后要把源复位**（`data_=buf_; size_=0; buf_[0]='\0'`），不然双重释放。
- **处处维持 `'\0'` 收尾**，`new`/`memcpy` 都要 `+1`。
- **自赋值**：`s = s` 时别先把自己释放了。

## 面试追问

1. SSO 是什么？为什么能提升性能？`sizeof(std::string)` 一般多大、为什么？

   **答**：SSO（Small String Optimization）是把**短字符串直接存进 string 对象自身的内联缓冲区**、不走堆分配的技术。提升性能因为多数字符串都很短，省掉一次 `new`/`free` 和一次间接寻址，构造/拷贝/析构更快、缓存更友好。`sizeof(std::string)` 一般是 **32 字节**（libstdc++/libc++，64 位）：要同时容纳"长串模式"的 3 个字段（指针、size、capacity 各 8 字节）和"短串模式"的内联缓冲，union 复用空间后总体约 32 字节。

2. 为什么短字符串移动并不比拷贝快？长字符串移动为什么是 O(1)？

   **答**：短字符串走 SSO，内容就在对象内联缓冲里，移动**无外部指针可偷**，只能**逐字节把缓冲复制过去**——和拷贝做的事一样，所以不更快。长字符串内容在堆上，对象里只存指针+size+capacity，移动只需把这几个字段**拷过去并把源置空**（偷指针、不复制内容），是 O(1)，而拷贝要再 `new` 一块并复制全部字符 O(n)。所以"移动比拷贝快"只对走堆的长串成立。

3. 标准库为什么用 union 实现 SSO？内联容量一般多大？

   **答**：因为短串模式和长串模式**永远只用其一**，用 `union` 让"内联字符缓冲"与"{指针,size,capacity} 结构"**复用同一块存储**、省空间；再用一个标志位（或指针是否指向内联区）区分当前模式。这样小对象不浪费、大对象也放得下。内联容量一般：libstdc++ 约 **15 个字符**（+1 个 `'\0'`，共 16 字节缓冲），libc++ 用更紧凑的位布局约 **22 个字符**。

4. `c_str()` 为什么保证 `'\0'` 结尾？`data()` 和 `c_str()` 在 C++11 后有何区别？

   **答**：`c_str()` 保证返回的缓冲以 `'\0'` 结尾，是为兼容 C 字符串 API（它们靠 `'\0'` 判结尾）；string 内部始终在 size 处多留一个 `'\0'`。C++11 起 **`data()` 和 `c_str()` 等价**——都返回同一块、同样以 `'\0'` 结尾的缓冲；区别仅在 C++11 之前 `data()` 不保证有结尾 `'\0'`，且 C++17 起 `data()` 有非 const 重载可返回可写 `char*`，而 `c_str()` 永远是 `const char*`。

5. COW（写时拷贝）字符串是什么？为什么 C++11 后被禁用（多线程问题）？

   **答**：COW（Copy-On-Write）让多个 string 拷贝**共享同一份堆缓冲+引用计数**，只有某副本要**修改**时才真正复制一份，省掉大量只读拷贝开销。C++11 禁用它主要因**多线程不安全/性能陷阱**：共享缓冲的引用计数增减需原子操作，且 `operator[]`、`begin()` 这类返回非 const 引用/迭代器的操作必须**悲观地预先分裂**（无法知道是否会写），反而频繁拷贝；加上线程间共享同一缓冲使"看似独立的两个 string 在不同线程读写"出现数据竞争。C++11 收紧了迭代器失效与并发要求，实际上禁止了 COW，标准库转向 SSO。

6. `reserve` 后再 `append` 还会重新分配吗？字符串扩容策略是怎样的？

   **答**：`reserve(n)` 后 capacity≥n，只要后续 `append` 的总长度**不超过这个 capacity 就不会重新分配**；一旦超过才扩容。扩容策略和 vector 类似是**几何增长**（通常约 2 倍并按对齐取整），保证 n 次追加摊还 O(1)；扩容时分配新缓冲、把旧内容拷/移过去、释放旧缓冲，期间指向旧缓冲的指针/迭代器失效。
