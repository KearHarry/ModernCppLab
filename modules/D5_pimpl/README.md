# D5 · Pimpl 编译防火墙（Pointer to Implementation）

难度 ⭐⭐⭐ · 预计 2h

## 为什么大厂爱考
Pimpl 是 C++ **工程化**的招牌技巧：库作者用它把私有实现藏进 `.cpp`，换来**编译解耦**与 **ABI 稳定**——Qt、很多基础库的对外类都是这么写的。它一道题同时考三层功力：① 你懂不懂"头文件即编译依赖的传染源"；② 你知不知道**为什么 `~Widget()` 必须声明在头、定义在 `.cpp`**（不完整类型 + `unique_ptr` 的经典坑，几乎是 Pimpl 面试的必杀追问）；③ 你能不能把代价（堆分配、间接寻址、不可内联）讲清楚，知道什么时候**不**该用。能把这三点串起来，就是"写过真实工程"的硬信号。

## 背景知识

### 1) 问题：头文件是"编译依赖"的传染源
普通类把私有成员摊在头文件里：
```cpp
// widget.hpp（反例）
#include <vector>
#include "heavy_third_party.h"   // 私有依赖被迫暴露给所有调用方
class Widget {
    std::vector<int>   data_;    // 私有实现细节，写在头里
    HeavyThing         thing_;
};
```
后果：**①** 任何 `#include "widget.hpp"` 的 `.cpp` 都要解析 `heavy_third_party.h`，编译变慢；**②** 你改一个私有成员（哪怕只加一个 `int`），所有包含本头的文件**全部重编**；**③** 私有依赖泄漏成了公开依赖，调用方被迫也能看见 `HeavyThing`。

### 2) Pimpl 的思路：把实现搬进 .cpp
头文件只留「一个指向**不完整类型** `Impl` 的指针 + 公开方法声明」，`Impl` 的真身只在 `.cpp` 里：
```
widget.hpp（公开、稳定）          widget.cpp（私有、可随意改）
┌───────────────────────┐        ┌──────────────────────────────┐
│ struct Impl;  // 前置   │        │ struct Widget::Impl {        │
│ unique_ptr<Impl> p_;   │  ───▶  │     std::string name;        │
│ void push(int);        │        │     std::vector<int> data;   │
│ int  sum() const;      │        │ };  // 真身 + 私有依赖都在这   │
└───────────────────────┘        └──────────────────────────────┘
```
于是：**改实现只重编一个 `.cpp`**；**私有依赖不外泄**；类的大小恒为「一个指针」，加减私有成员**不动头、不破 ABI**。

### 3) 经典坑：析构 / 移动**必须定义在 .cpp**
`std::unique_ptr<Impl>` 销毁时要 `delete` 一个 `Impl`。而 `delete` 一个**不完整类型**是未定义行为——标准库还会用 `static_assert`（"invalid application of `sizeof` to incomplete type"）直接把你拦在编译期。

如果你**不写** `~Widget()`，编译器会在**头文件**里替你默认生成它；而那一刻 `Impl` 只有前置声明、**还不完整** → 报错。移动操作同理（它们也可能要销毁旧的 `Impl`）。

> 解法：在头里只**声明** `~Widget();` / 移动操作，把**定义**放到 `.cpp`（写 `= default` 也行）。`.cpp` 里 `Impl` 已完整，`delete` 合法。**定义点的位置**才是关键，不是写不写 `= default`。

### 4) 为什么用 `unique_ptr` 而不是裸指针
`unique_ptr` 自带 RAII（析构自动释放）与移动语义，省去手写 `delete`、防泄漏。代价：它**不可拷贝**，于是 `Widget` 默认也不可拷贝。想要深拷贝就得**自己**写拷贝构造/赋值——在 `.cpp` 里 `new` 一个 `Impl` 的副本（因为头里拷贝不了不完整类型）。本模块**简化为「禁拷贝、只支持移动」**，把精力聚焦在防火墙与析构坑上。

### 5) Pimpl 的代价（什么时候别用）
- **一次堆分配**：每个对象多一次 `new`/`delete`。
- **一次间接寻址**：每次访问成员都要先解引用 `p_`。
- **跨 .cpp 不可内联**：方法体在 `.cpp`，调用方看不到、内联不了。

所以**小而热**的值类型（如 `Point`、迭代器）用 Pimpl 往往得不偿失——它换的是「编译解耦 + ABI 稳定」，不是性能。适合**重量级、对外暴露、迭代频繁**的类。

### 6) 和「抽象基类接口」的关系
信息隐藏还有另一条路：纯虚基类 + 工厂返回 `unique_ptr<Interface>`。区别：抽象接口靠 **vtable 动态分派**（每次调用一次虚跳转）、对象由工厂在堆上造、天然支持多实现/多态；Pimpl 是**同一个具体类型**、方法是普通（非虚）调用、只是把数据藏起来。要"多态/可替换实现"用接口；只想"藏实现、稳 ABI、保持值语义"用 Pimpl。

## 你要实现什么

## 关键坑
- **`~Widget()` / 移动操作要定义在 `.cpp`**：放任编译器在头里默认生成 = 在 `Impl` 不完整处 `delete` = 编译报错。本模块已示范"头里声明、`.cpp` 里 `= default`"。
- **头文件不要 `#include` 私有依赖**：`Impl` 用到的 `<vector>` 等只在 `.cpp` 里包含——这正是"防火墙"的意义，别又把它们漏回头里。
- **移动后的对象内部指针为空**：被 `std::move` 掏空的 `Widget`，除了析构或重新赋值，别再调它的 `sum()/name()`（会解引用空指针）。这是 `unique_ptr` 移动语义的正常表现。
- **禁拷贝是有意为之**：`unique_ptr` 不可拷贝导致 `Widget` 不可拷贝；想要拷贝必须自己在 `.cpp` 里实现深拷贝，别指望默认。
- **`name()` 返回引用**：返回的是 `p_->name` 的引用，注意别在对象已析构后还持有它。

## 面试追问

1. Pimpl 解决什么问题？"编译防火墙"具体防的是哪几种重编译/依赖泄漏？

   **答**：Pimpl（pointer to implementation）把类的**所有私有成员和实现细节**挪进一个只在 `.cpp` 里定义的 `struct Impl`，头文件里只留一个 `unique_ptr<Impl>` 和公有接口。它解决"**头文件泄漏实现细节导致客户端被迫重编译**"。"编译防火墙"具体防：①**私有成员变化**——给 Impl 增删私有字段/改类型，**头文件不变**，所有 `#include` 该头的客户端**无需重编译**（普通类改私有成员会改 `sizeof`/布局，逼全员重编）；②**依赖泄漏**——实现用到的重型第三方头只在 `.cpp` 里 `#include`，**不传染**给客户端，缩小包含图、降低耦合；③**ABI 隐藏**——对外只暴露稳定的指针大小和接口签名。

2. 为什么 `~Widget()` 必须**声明在头、定义在 `.cpp`**？放任编译器默认生成会报什么错、根因是什么？

   **答**：因为头文件里 `Widget` 只**前置声明** `struct Impl;`（不完整类型），而 `~Widget()` 若由编译器在头文件**默认生成/内联**，它要销毁 `unique_ptr<Impl>`，就会在**Impl 还不完整的地方**实例化 `delete impl_ptr`——`delete` 一个**不完整类型**是被 `static_assert` 拦截的错误（编译器无法知道 Impl 的析构与大小）。报错通常是 `invalid application of 'sizeof' to incomplete type 'Impl'` 或 `static_assert ... incomplete type`。解法：在**头里声明** `~Widget();`，在 **`.cpp` 里定义**（哪怕 `= default`）——`.cpp` 中 `Impl` 已完整，`delete` 合法。移动构造/移动赋值同理（也要销毁旧 Impl），都必须挪到 `.cpp`。

3. `unique_ptr<Impl>` 析构不完整类型为什么编译失败，而 `shared_ptr<Impl>` "看起来"不用？（提示：`shared_ptr` 在**构造点**就把删除器类型擦除存好了，那时类型完整。）

   **答**：`unique_ptr<Impl>` 的删除器是其**类型的一部分**（`default_delete<Impl>`），`delete` 调用在**析构 `unique_ptr` 的那个点**实例化，要求那里 `Impl` **完整**——若析构被内联进头文件而 Impl 不完整，就编译失败。`shared_ptr<Impl>` 不同：它的删除器是**类型擦除**的，存在控制块里；这个删除器在 **`shared_ptr` 构造的那一刻**（如 `make_shared<Impl>()`）就被**绑定存好**，而那个构造点通常在 `.cpp` 里、**Impl 完整**。之后 `shared_ptr` 析构调用的是已存好的擦除删除器、**不再需要 Impl 完整**，所以"看起来"不用手动在 .cpp 定义析构。代价是 `shared_ptr` 多一个控制块/原子计数。注意：即便用 shared_ptr，**构造点仍必须见到完整 Impl**。

4. Pimpl 的运行时代价有哪些？为什么说"小而热"的类型不该用？

   **答**：运行时代价：①**一次额外堆分配/释放**（创建/销毁 Impl）；②**一次额外指针间接**——每次访问成员都要 `p_->member`，多一跳、**缓存局部性变差**（对象本体和 Impl 分处两块内存）；③**阻止内联与某些优化**——成员函数实现在 .cpp、跨翻译单元，调用难内联；④移动可以但**拷贝需手写深拷贝**。所以"**小而热**"的类型不该用：像 2D 点、向量、迭代器这种**小、海量、在内循环里频繁访问**的类型，多一次堆分配 + 每次访问多一跳 + 不可内联，性能损失显著，而它们实现很少变、享受不到"编译防火墙"的好处。Pimpl 适合**大、少、接口稳定、实现常变**的边界类型。

5. 用 Pimpl 做信息隐藏 vs 用纯虚抽象基类做，各自的机制、开销与适用场景？

   **答**：两者都隐藏实现，但机制不同。**Pimpl**：同一个**具体类**，私有细节藏到 `.cpp` 的 Impl；客户端**按普通方式**用 `Widget`，**编译期**就知道它是什么、可放栈上、可拷贝（手写）；开销是一次堆分配 + 一跳间接、**无虚调用**；适合"对外是普通值类型、只想隐藏细节/稳定 ABI/降编译依赖"。**纯虚抽象基类**：接口做成抽象基类、实现做成派生类，客户端**只持基类指针、经虚函数调用**，实现可在**运行期多态替换**（工厂返回不同派生）；开销是 **vptr + 每次虚调用间接**，且对象**必须堆分配 + 经指针用**、不能按值；适合"需要运行期多态/插件式替换/多种实现并存"。一句话：只隐藏细节用 Pimpl，要运行期换实现用抽象基类。

6. 想让 `Widget` 支持**拷贝**该怎么做？深拷贝代码写在哪、为什么不能放头文件？

   **答**：`Widget` 默认只能移动（`unique_ptr` 不可拷贝），要支持**拷贝**得**手写拷贝构造和拷贝赋值**做 Impl 的**深拷贝**：`Widget(const Widget& o) : p_(o.p_ ? std::make_unique<Impl>(*o.p_) : nullptr) {}`，拷贝赋值用 copy-and-swap 或同样 new 一份。这些代码**必须写在 `.cpp` 里**，原因同析构：拷贝构造要 `new Impl(*o.p_)`，需要 **Impl 是完整类型**才能调它的拷贝构造和取 `sizeof`；而头里 Impl 只是前置声明（不完整），在头里定义/默认生成拷贝就会在不完整类型上实例化构造→编译失败。放 `.cpp`（Impl 已完整）才合法。也因此 Pimpl 类要么显式 `=delete` 拷贝（保持 move-only），要么在 .cpp 手写深拷贝。

7. ABI 稳定：为什么库作者偏爱 Pimpl？给类**新增一个私有成员**，普通类和 Pimpl 类分别会不会破坏已编译客户端的 ABI？

   **答**：库作者偏爱 Pimpl 正因它**稳定 ABI**：客户端编译时只依赖 `Widget` 的**公有接口**和"内部是一个指针"这一事实，对象大小恒为 `sizeof(void*)`、布局不随实现变。**新增一个私有成员**：**普通类**——私有成员也写在头里，新增会**改变 `sizeof` 和成员偏移**，所有已编译的客户端（内联了旧的大小/偏移）与新版库**ABI 不兼容**，必须**全部重新编译**，否则链接/运行期错乱。**Pimpl 类**——新私有成员加进 `.cpp` 的 `Impl`，头文件和 `Widget` 的大小/布局**完全不变**，已编译客户端**无需重编译、ABI 不破**，库可独立升级（换 .so/.dll 即可）。这对要长期维护二进制兼容的库（系统库、SDK、Qt 等）至关重要。

8. Pimpl 对**编译时间**的实际收益从何而来？大型项目里如何度量这个收益（增量编译 / 包含图）？

   **答**：编译时间收益来自**砍断包含依赖图**：实现所需的重型头（STL 容器、第三方大库）只在 `.cpp` 里 `#include`，**不再出现在公有头**里；于是 `#include "widget.hpp"` 的成千上万个客户端 TU **不必再解析那些被隐藏的头**，单 TU 解析量下降，**改动实现（.cpp 或 Impl）只重编那一个 .cpp**、不触发依赖该头的全量重编。**度量方法**：①比较改一处私有实现后的**增量编译**——受影响 TU 数量与总耗时（Pimpl 应只重编 1 个 .cpp）；②用编译器的**包含图工具**（`-H`/`-MM`、clang `-ftime-trace`、`include-what-you-use`）统计公有头的**传递包含数量**和被多少 TU 包含；③用 `ClangBuildAnalyzer`/ccache 命中率、构建系统的 build graph 看"扇出"。大型项目里"一个常改的核心类不做 Pimpl"往往是增量构建慢的元凶，量化前后包含数与重编 TU 数即可看出收益。
