# C6 · 跳表 SkipList（有序映射，O(log n) 不用平衡树）

难度 ⭐⭐⭐⭐⭐ · 预计 3h

## 为什么大厂爱考

"不用红黑树，怎么实现一个 O(log n) 的有序 map？"——能答出 **跳表（SkipList）** 并讲清它的随机化层高、查找/插入/删除套路、以及为什么 Redis/LevelDB 选它而非平衡树，是数据结构功底 + 工程视野的双重信号。它比红黑树**好写得多**（无旋转、无变色），却同样高效，是高频考点。

## 背景知识

### 1) 从有序链表说起

一条排好序的单链表，查找只能逐个走，O(n)。怎么加速？给它叠加几层"快速通道"。

### 2) 跳表 = 多层快速通道

```
L3: head ----------------------------> 50 --------> nil
L2: head -------> 20 ----------------> 50 --------> nil
L1: head -> 10 -> 20 -> 30 ----------> 50 -> 70 --> nil
L0: head -> 10 -> 20 -> 30 -> 40 -> 45 -> 50 -> 70 -> nil   ← 最底层含全部元素，升序
```

查 45：从最高层往右走，**走过头就下降一层**，继续。高层一步跨过很多节点，平均只看 O(log n) 个。

### 3) 随机层高：跳表的灵魂

每个节点插入时**抛硬币**决定高度：至少 1 层，之后每多一层约 1/2 概率（封顶 `kMaxLevel`）。统计上自然形成上图那种"越高层越稀疏"的塔状分布——**不需要旋转、不需要再平衡**。这就是它比 AVL/红黑树好写的根本原因：平衡靠概率，不靠精巧的结构调整。

### 4) 节点与哨兵

```cpp
struct Node { int key, value; std::vector<Node*> forward; };  // forward[i]=第 i 层后继
```

`forward` 长度 = 节点高度。`head_` 是哨兵，高度拉满 `kMaxLevel`、不存数据，作为每层的起点。

### 5) 三个操作的统一套路：顶层往下"逼近"

```cpp
Node* x = head_;
for (int i = level_-1; i >= 0; --i)                    // 从当前最高层往下
    while (x->forward[i] && x->forward[i]->key < key)  // 同层能往右就往右（不越过 key）
        x = x->forward[i];
// x = "最后一个 key 小于目标的节点"；x->forward[0] 是候选
```

- **find**：看 `x->forward[0]` 是不是目标。
- **insert / erase**：下降时把每层"即将下降处的 x"记进 `update[i]`，事后在这些位置改指针。`update[i]` 即"第 i 层中，新节点要插在谁后面 / 待删节点在第 i 层的前驱"。

### 6) 和平衡树(std::map)的对照


| 维度  | 跳表                          | 红黑树(std::map)     |
| --- | --------------------------- | ----------------- |
| 复杂度 | O(log n) **期望**             | O(log n) **最坏**保证 |
| 实现  | 改指针、无旋转，**易写对**             | 旋转+变色，极易写错        |
| 并发  | 改动局部化，**易做无锁/细锁**           | 旋转牵动大范围，难并发       |
| 用途  | Redis zset、LevelDB memtable | STL 关联容器、需最坏界场景   |

## 关键坑

- `**update[]` 初值设为 `head_`**：高于当前 `level_` 的层，新节点的前驱就是哨兵。`std::vector<Node*> update(kMaxLevel, head_)` 一步到位，省去对新层的特判。
- **比较用严格 `<`**：`while (... && forward[i]->key < key)`。用 `<=` 会走过头、定位错。
- **insert 接指针的两行有顺序**：先 `n->forward[i] = update[i]->forward[i]`，再 `update[i]->forward[i] = n`。反了会把后继丢掉。
- **erase 的 `break` 优化**：从底层往上，一旦某层 `update[i]->forward[i] != c`，说明 c 在这层及更高层都不存在，可直接停。
- **删除后收缩 `level_`**：若最高层变空（`head_->forward[level_-1]==nullptr`）要把 `level_` 降下来，否则后续查找空跑高层、变慢。
- **重复 key 是更新不是新增**：插入前先判候选是否同 key，是则改 `value` 直接返回，`size_` 不变。
- **随机不影响正确性**：层高是性能旋钮；无论怎么抛硬币，逻辑结果都要正确。本模块固定种子，结果可复现。

## 面试追问

1. 跳表为什么平均 O(log n)？随机层高的期望分析（每层约 1/2，期望层数 O(log n)、每层期望走常数步）。
  **答**：跳表是多层有序链表，上层是下层的"快速通道"。每个节点以概率 p（常 1/2）独立决定是否"长高一层"，于是第 k 层期望有 n·p^k 个节点，层数期望约 log_{1/p} n = O(log n)。查找从最高层开始，每层**向右走到不能再走就下降一层**：因为每层节点是下层的约 p 比例抽样，每层期望只走**常数步**（约 1/p）就会下降，总步数 ≈ 层数×每层步数 = O(log n)×O(1) = **O(log n)**。插入/删除先 O(log n) 查到位置再改指针，也是 O(log n)。
2. 跳表 vs 红黑树/AVL：复杂度是期望还是最坏？实现难度、并发友好度、内存开销各如何取舍？
  **答**：跳表的 O(log n) 是**期望/概率**（依赖随机层高，极小概率退化），红黑树/AVL 是**最坏 O(log n)**（确定性平衡）。取舍：**实现难度**——跳表显著简单（无旋转、无复杂再平衡，插删就是改指针），红黑树的旋转和染色规则繁琐易错；**并发友好**——跳表局部改指针、易做细粒度锁/无锁，树的旋转牵动大范围、并发难；**内存开销**——跳表每节点平均约 1/(1-p) 个指针（p=1/2 时约 2 个），通常与红黑树（2 子指针+父指针+颜色）相当或略省；**顺序遍历**——跳表底层就是有序链表，天然友好。
3. Redis 的 zset 为什么用跳表而不是平衡树？（实现简单、范围查询友好、并发/持久化考量）
  **答**：Redis 的 zset（有序集合）选跳表而非平衡树，官方理由有三：①**实现简单**——跳表代码远比红黑树短、易维护调试，作者明确看重这点；②**范围查询友好**——zset 大量用 `ZRANGE`/`ZRANGEBYSCORE` 取区间，跳表底层有序链表顺序遍历天然 O(log n + k)，还能给节点加 span 支持按排名查；③**并发/内存可控**——跳表不需旋转、改动局部，且节点指针数可由概率 p 调节来平衡内存。此外平衡树范围遍历要中序、实现更绕。所以"简单 + 范围操作 + 可调"让跳表更契合 zset。
4. `update[]` 数组是干什么的？insert 和 erase 为什么都需要它？
  **答**：`update[i]` 记录"在第 i 层，**最后一个 key 小于目标**的节点"——即查找路径上每一层的**前驱节点**。插入时新节点要在它**可能存在的每一层**被链进去，而链入第 i 层需知道该层前驱（`new->next=update[i]->next; update[i]->next=new`），所以先用 update[] 把各层前驱一次性记下；删除同理，要在每一层把"前驱的 next 跳过被删节点"（`update[i]->next=victim->next`），也需各层前驱。没有 update[] 就得为每层重新从头找前驱，繁琐且慢。它本质是"查找下降路径"的快照。
5. 层高概率 p 取 1/2 vs 1/4 有何影响？（p 小→层少省内存但每层走更多；时间-空间权衡）
  **答**：p 是"节点每升高一层的概率"，控制时间-空间权衡。**p 小（如 1/4）**：升层难→总层数少、每节点平均指针少（约 1/(1-p)≈1.33 个）→**省内存**，但每层节点更稀疏，查找在每层**期望要多走几步**（约 1/p=4 步）才下降→常数变大。**p 大（如 1/2）**：层多、指针多（平均约 2 个）→**更费内存**，但每层只走约 2 步、查找常数小。两者都是 O(log n)，只差常数。工程上 Redis 用 **p=1/4** 偏向省内存，教学/通用实现常用 1/2。
6. 怎么把这个跳表做成**并发**的（无锁跳表 / 每节点锁 / RCU）？为什么跳表比树容易并发？
  **答**：并发跳表常见三法：①**每节点锁（lazy/optimistic）**——插删时只锁住涉及的少数前驱节点（按层从低到高加锁），验证未被改动后改指针，粒度细、可高并发；②**无锁跳表**——每层指针用 CAS 原子改，配合标记位做逻辑删除（先标记再物理摘除），需处理 ABA 和回收（hazard pointer/epoch），Java `ConcurrentSkipListMap`、folly 都有；③**RCU**——读者无锁读旧版、写者改后延迟回收。跳表比树容易并发，根本原因是**改动是局部的**：插删只动目标位置每层的几个相邻指针，不像平衡树的旋转/再平衡会牵动从叶到根一大片节点、锁范围大、CAS 难界定，所以跳表天然适合细粒度/无锁并发。
7. 如何扩展支持范围查询 `[lo, hi)`、按排名查第 k 个（给节点加 span/跨度计数）？
  **答**：**范围查询 `[lo,hi)`**：先 O(log n) 定位到第一个 ≥ lo 的节点，再沿**底层有序链表**顺序向后收集直到 ≥ hi，复杂度 O(log n + k)（k 为命中数）——跳表底层即有序链表，这正是它的强项。**按排名查第 k 个**：给每个**前进指针附带一个 span（跨度）**，记录"这一跳跨过了底层多少个节点"；查找时把走过的 span **累加**，就能把"位置/排名"转成可跳跃的计数——`select(k)` 沿高层前进、累计 span 不超过 k 地下降，O(log n) 找到第 k 个；同理可 O(log n) 求某 key 的排名（rank）。Redis zset 正是用 span 支持 `ZRANK`/`ZRANGE`。
8. 最坏情况下跳表会退化成 O(n) 吗？概率多大？和哈希表(C4)相比，什么时候选有序的跳表、什么时候选 O(1) 的哈希表？
  **答**：会，但概率极低。跳表退化成 O(n) 需要"随机层高极端不走运"（如几乎所有节点都没升层、退化成单条链），其概率随 n 增大**指数衰减**——对合理的 n 实际几乎不发生，且无法被输入数据诱发（层高是内部随机、与 key 无关，所以也不怕 C4 那种 hash-flooding 式攻击）。与哈希表对比：**哈希表** O(1) 但**无序**，适合纯按 key 查/增/删、不关心顺序的场景；**跳表** O(log n) 但**有序**，当你需要**范围查询、按排名取、顺序遍历、求前驱后继**时选它。一句话：要顺序就跳表/平衡树，只要点查就哈希表。
