# E2 · 线性 / 竞技场 / 帧分配器 LinearAllocator（bump allocator）

难度 ⭐⭐⭐ · 预计 2h

## 为什么大厂爱考
游戏/高性能服务器岗的高频题："每帧产生海量临时数据，你怎么分配？"——能答出 **线性(bump)分配器 + 按帧 reset** 并讲清它为什么比 `new/delete` 快几个数量级、和定长池(C3)如何分工，是"懂引擎内存模型"的硬指标。它是**数据导向设计（DOD）**里"按生命周期分配"的代表作，几乎每个商业引擎都有一个 frame/scratch allocator。

## 背景知识

### 1) 核心思想：分配就是"推一个游标"
线性分配器预先持有一整片缓冲区，维护一个游标 `offset_`（已用到哪）。分配 = 对齐游标 + 往前推：
```
buffer_: [#############------------------------]
                      ↑ offset_
allocate(size, align): 对齐游标 → 检查不越界 → offset_ 推到末尾 → 返回对齐地址
```
一次分配就是"对齐 + 加法"几条指令，没有查找、没有空闲链表、没有锁。**这是能做到的最快的分配**。

### 2) 代价：不能单独释放，只能整片回收
它**故意**不支持 `free(单个对象)`。回收方式是：
- `reset()`：游标归零，整片作废——典型在**每帧帧末**调用，O(1) 丢弃这一帧所有临时分配。
- `rewind(marker)`：回退到历史游标，**栈式（LIFO）**回收一段临时作用域（见下）。

### 3) 为什么这个"缺点"恰恰适合游戏
游戏每帧产生大量**生命周期=一帧**的临时数据：可见物剔除列表、粒子、绘制指令、临时字符串……它们根本不需要逐个释放。用线性分配器：分配快到飞起，帧末 `reset()` 一次性全收回，**零碎片、零遗漏、cache 友好**。长生命周期对象才用别的分配器。

### 4) marker / rewind：栈式作用域
```
m = marker();          // 存档当前游标
... 一堆临时分配 ...
rewind(m);             // 读档：把这段内存一次性吐回（后进先出）
```
这让同一片 arena 支持嵌套的临时作用域（像函数栈帧的 push/pop），不必等帧末。

### 5) 对齐（alignment）必须正确
返回地址要满足请求的对齐，否则在其上放 `double`/SIMD 向量会变慢甚至崩。关键：对齐的是**绝对地址** `base + offset_`，不是单纯对齐 `offset_`（虽然 `new byte[]` 给的 base 已最大对齐，但请求超对齐时仍需按地址算）。`align_up` 已给好。

### 6) 只给生内存，对象生命周期靠你
`allocate()` 返回**未构造**的生内存，用 placement new 造对象（`create<T>` 已给好示范）。⚠️ `reset/rewind` **不调析构**！在 arena 上放了需要析构的非平凡对象（持有资源），你得在回收前自己 `p->~T()`；纯数据(POD)则可直接丢弃。

## 关键坑
- **对齐"地址"不是对齐"偏移"**：`aligned = align_up(base + offset_, align)`，再用 `aligned - base + size` 算新游标。直接对齐 `offset_` 在 base 本身不够对齐时会出错。
- **失败时游标绝不能动**：容量不足返回 `nullptr` 时，`offset_` 必须保持原值，否则后续分配错乱（测试专门验证这点）。
- **`reset/rewind` 不析构**：这是线性分配器的语义，不是 bug。非平凡对象需手动析构，面试爱追问"在 arena 上放了 `std::string` 不管会怎样"。
- **越界判断用 `>` 还是 `>=`**：`needed > capacity_` 才算失败（正好用满 `needed==capacity_` 是允许的）。
- **不要 memset/清零**：bump 分配不负责清零，返回的是脏内存；需要零初始化由调用方负责（placement new 会负责构造）。

## 面试追问

1. 线性分配器为什么比 `new/delete` 快这么多？它省掉了通用分配器的哪些工作（查找、合并、加锁）？

   **答**：线性（bump/arena）分配器的 `allocate` 本质就是"**把游标按对齐推进 size、返回旧游标**"——几条指令、无分支、O(1)。它省掉了通用 `new/delete` 几乎所有重活：①**空闲块查找**——不需在空闲链表/红黑树里找合适大小的块；②**分裂/合并**——释放时不需把相邻空闲块合并、避免碎片；③**元数据维护**——每次分配不需记块头、大小、边界标记；④**加锁**——单线程下无锁（通用 malloc 要应对多线程，常有锁/线程缓存）。代价是只能整体回收。所以它快在"分配是一次指针加法、释放是一次游标复位"。

2. 它最大的限制是什么（不能单独释放）？为什么这个限制在游戏每帧临时数据场景下反而是优点？

   **答**：最大限制是**不能单独释放某一块**——只能整体 `reset`（或回退到某 marker），因为它不记录每块的边界和大小，没法把中间一块还回空闲表。这个限制在**游戏每帧临时数据**场景反而是优点：每帧产生大量短命临时分配（渲染指令、碰撞对、字符串拼接……），它们生命周期**完全一致**——都活到帧末。于是"逐个 free"既无必要又是纯开销，用 arena **每帧开头 `reset` 一把全收**，O(1) 释放全部、零碎片、零 free 调用，正好契合"同生共死"的批量生命周期。限制变成了零成本的批量回收。

3. `reset` vs `rewind(marker)` 有什么区别？marker 机制为什么是后进先出（栈式）的？

   **答**：`reset` 把游标**整个归零**，丢弃 arena 里**所有**分配、从头复用；`rewind(marker)` 只把游标**回退到之前用 `marker = current()` 记下的某个位置**，释放"该 marker 之后"的分配、保留之前的。marker 机制是**后进先出（栈式）**的，因为游标只能单调前进或回退到更早的点：进入临时作用域时 `mark`、离开时 `rewind` 回去，嵌套作用域的 mark/rewind 必须像函数调用栈一样**严格后进先出**——内层先 rewind、外层后 rewind；若想"释放中间某段却保留它之后的"就破坏了连续性、做不到。所以 marker 实现了**栈式的子作用域回收**，是 reset（全清）和"逐块释放"（做不到）之间的中间档。

4. 为什么要对齐"绝对地址"而不是"偏移量"？什么时候两者等价、什么时候不等价？

   **答**：因为对齐约束针对**对象的真实内存地址**——硬件要求 `T` 的地址是 `alignof(T)` 的整数倍。所以分配时要把**游标对应的绝对地址**向上取整到对齐边界（`aligned = (addr + a-1) & ~(a-1)`）再返回。**何时等价**：当 arena 的**基地址本身**已按最大对齐（如 `max_align_t`）对齐时，"地址对齐"和"偏移量对齐"结果相同——`基址(已对齐) + 对齐的偏移` 仍对齐。**何时不等价**：当基地址**未对齐**（来自随意的 buffer、或 `char buf[]` 没 alignas）时，只把偏移量对齐、忽略基址错位，算出的绝对地址仍可能不满足对齐→ARM 上崩溃、x86 上变慢。稳妥做法是对齐绝对地址，或保证基址按 max_align 对齐后再对齐偏移。

5. 在 arena 上构造了 `std::vector`/`std::string` 然后只 `reset` 不析构会怎样？（资源泄漏、UB）

   **答**：会**资源泄漏**，并可能是 **UB**。`std::vector`/`std::string` 对象**本体**虽建在 arena 上，但它们内部持有的**真正数据缓冲是各自向堆（`new`）申请的**。`reset` 只是把游标归零、**不调用这些对象的析构函数**，于是它们的析构永不执行、`new` 的堆缓冲**永不被 `free`**→内存泄漏；若对象还持有文件/锁等资源同理泄漏。正确做法：在 arena 上构造非平凡析构的对象后，`reset` 前必须**显式析构**（`p->~T()`）；arena 最适合放**平凡可析构**（trivially destructible）的 POD/简单结构，它们不 reset 也无资源泄漏。

6. 这个分配器线程安全吗？多线程每帧并发分配怎么改（每线程一个 arena / 原子游标 CAS）？

   **答**：不安全。单个 arena 的 `allocate` 要读改同一个**游标**，并发 bump 会竞争——两个线程可能拿到**重叠**内存、或游标更新丢失。改造：①**每线程一个 arena**（thread-local）——各线程在自己的 arena 上无锁 bump，最快最常用（帧分配天然可按线程切分），代价是内存按线程预留、跨线程引用要小心；②**原子游标 CAS**——把游标设为 `atomic`，用 `fetch_add(size)`（带对齐处理）原子推进并拿回旧值，无锁但高并发下游标是争用热点、且对齐让 fetch_add 不够直接（需 CAS 循环算对齐后的新值）；③**加锁**——一把锁包 allocate，最简单但串行化。引擎里通常选①每线程 arena，配合任务系统按 worker 分配。

7. 和 C3 定长内存池比，各自适合什么对象？真实引擎里会怎么搭配使用这两类分配器？

   **答**：**C3 定长池**适合**大量同型、生命周期各异、需逐个 new/delete** 的对象——子弹、粒子、链表节点：支持单独释放、复用空闲块、无碎片，但只能一种大小。**E2 arena** 适合**任意大小、生命周期一致（同生共死）、批量回收**的临时数据——每帧渲染队列、临时字符串、计算中间结果：分配极快、整体 reset，但不能单独释放。**搭配**：引擎常分层——用 **arena 管"每帧/每作用域瞬时数据"**（帧末 reset），用**定长池管"持续存活、需独立增删的同型对象"**（实体组件、节点），持久 arena 管关卡级资源（切关卡才 reset）。即按**生命周期模式**选：同生共死→arena；独立增删→对象池；通用长寿→标准堆。

8. double-ended（两端各一个游标）arena、ring/环形帧分配器（N 帧延迟回收）分别解决什么问题？

   **答**：**double-ended arena（双端）**：一块缓冲，**两个游标从两端相向推进**，分别分配生命周期/用途不同的两类数据——如低端放"本帧临时"、高端放"较持久"，二者独立 reset 互不干扰；好处是**一块内存按两种生命周期共用、互相挤占剩余空间**，比切成两块固定区更灵活、利用率更高。**ring/环形帧分配器（N 帧延迟回收）**：游标在固定缓冲里**环形前进**，分配的内存**延迟 N 帧才复用**——解决"GPU/异步系统还在读上一帧（或前几帧）数据，不能立刻 reset 覆盖"的问题：CPU 写第 k 帧数据，GPU 可能落后 1~2 帧才消费，环形 + N 帧延迟保证一块内存在所有消费者用完前不被覆写，实现 CPU-GPU 的**多帧流水线**无需每帧同步等待。
