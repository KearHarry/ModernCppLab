# D8 · 编译、链接与 ABI（translation unit / ODR / linkage）

难度 ⭐⭐⭐⭐ · 预计 3.5h

## 为什么大厂爱考

“头文件里定义普通函数为什么会 multiple definition？”“`inline` 只是建议内联吗？”“`static` 全局变量和 `extern` 有何区别？”这些问题决定一个工程能否从单文件 demo 长成库。很多 C++ 故障并非语法错，而是在预处理、编译、符号生成、链接的边界上出错。

本模块是仓库中第一个刻意由多个 `.cpp` 组成的实验，并额外包含一个真正由 C 编译器处理的 `.c` 调用方。只有真正跨越翻译单元与语言边界，ODR、内部/外部链接、inline 实体身份与 C ABI 才不是纸上谈兵。

## 背景知识

### 1) 从源文件到程序

简化流程为：预处理展开 include/宏 → 每个翻译单元独立编译成目标文件 → 链接器解析符号、重定位并产出可执行文件/库。一个 `.cpp` 加它递归包含的头，经预处理后构成一个翻译单元（TU）。不同 TU 在编译阶段通常互相不可见。

“编译错误”多是当前 TU 类型/语法不成立；“未定义引用”表示声明让编译通过，但链接时找不到定义；“重复定义”表示链接器看见不允许并存的多个外部定义。

### 2) 声明、定义与 ODR

`extern int counter;` 是声明，告诉当前 TU 有这样一个对象；`int counter = 0;` 是定义，真正提供存储。One Definition Rule 简化理解：普通外部链接函数/对象在整个程序中只能有一个定义；类、模板、inline 实体可在多个 TU 出现相同定义，但每个 TU 中仍只有一个定义且定义必须满足 ODR 等价要求。

因此头文件通常放声明、类/模板/inline 定义；普通非 inline 函数定义放一个 `.cpp`。

### 3) linkage：名字指向哪一份实体

- **外部链接**：不同 TU 中的声明可指向同一实体，本实验的 `shared_counter` 就是一份。
- **内部链接**：实体只在当前 TU 可见。命名空间作用域 `static` 或匿名 namespace 常用于此目的。
- **无链接**：局部自动变量等只能在自身作用域引用。

头中定义 `static` 函数会让每个包含它的 TU 得到独立副本；函数内 local static 也随这些独立函数各有一份。

### 4) `inline` 的 ODR 含义

现代 C++ 中 `inline` 最重要的含义是：允许实体在多个 TU 中具有满足规则的相同定义，并代表一个程序级实体。是否真的机器码内联由优化器决定，与关键字没有保证关系。

本实验把 `inline_counter()` 定义在头中。alpha/beta 两个 TU 取到的函数内 static 地址相同，证明它不是“每个 TU 一份”。计数器使用无符号整数，极端情况下的回绕也有语言定义，不会引入有符号溢出 UB。

### 5) 名字修饰、C linkage 与 ABI

C++ 为重载、namespace 等把类型信息编码到符号名中（name mangling），规则属于 ABI。`extern "C"` 指定 C 语言链接，通常得到未修饰的稳定符号名，便于 C/其他语言查找；它不把函数体变成 C，也不自动让复杂 C++ 类型跨边界安全。

ABI 还包括参数如何进寄存器/栈、对象布局、异常、标准库类型布局等。稳定边界优先使用固定宽度整数、字节缓冲、opaque handle 和显式资源释放函数，避免跨编译器直接传 `std::string`、异常或含虚函数对象。

## 关键坑

- **不要把普通外部函数定义放头中**：多个 TU 包含后通常重复定义；改成声明 + 单一 `.cpp` 定义，或确属 header-only 时用 inline。
- **`extern` 声明不提供存储**：必须有且仅有一个匹配定义。
- **不要以为 inline 保证性能内联**：它主要是 ODR/linkage 属性。
- **头文件 `static` 会复制状态**：若你本想全程序共享，结果会出现“不同 cpp 看见不同配置”的隐蔽 bug。
- **ODR 违反不一定有诊断**：两个 TU 因宏得到不同 inline/template 定义，链接器可能合并其中一份，运行结果取决于构建细节。
- **C linkage 不等于稳定全部 ABI**：复杂 C++ 对象、allocator、异常仍可能不兼容。
- **声明签名必须一致**：不同 TU 对同一外部函数的类型理解不一致会破坏调用约定，可能链接成功却运行崩溃。
- **跨语言头必须真能由 C 解析**：用 include guard、`stdint.h` 和 `#ifdef __cplusplus` 包住 `extern "C"`；不要把 namespace、引用、模板、`noexcept` 或 STL 类型暴露给 C。
- **固定宽度不自动阻止算术溢出**：本实验把两个 `int32_t` 输入提升后以 `int64_t` 返回；若仍在 32 位类型中先相加，转换结果前就已经发生 UB。

## 面试追问

1. **什么是翻译单元？头文件会单独编译吗？**

   **答**：一个源文件加预处理后递归展开的头/宏形成 TU，通常独立编译成目标文件。普通头不会单独编译，只是文本进入每个包含它的 TU；因此头中的定义可能被复制很多次。

2. **编译错误、未定义引用、重复定义分别在哪一阶段？**

   **答**：语法/类型问题通常在编译当前 TU 时发现；未定义引用在链接时表示已有符号引用但无定义；重复定义在链接时表示多个强外部定义冲突。LTO 会模糊实现阶段，但概念边界仍成立。

3. **ODR 的工程化理解是什么？**

   **答**：普通外部实体全程序一个定义；模板、类和 inline 实体可在多个 TU 有等价定义。违反 ODR 有些能被链接器报出，有些属于 ill-formed no diagnostic required，尤其危险。公有头受宏影响生成不同定义是典型雷区。

4. **`inline` 与优化器内联有什么关系？**

   **答**：关键字允许多 TU 等价定义并约束实体身份；优化器是否消除调用独立决定，可以内联未标 inline 的函数，也可拒绝标了 inline 的函数。跨 TU 优化通常依赖 LTO 或函数体在当前 TU 可见。

5. **namespace 作用域 `static`、匿名 namespace 与函数内 static 有何区别？**

   **答**：前两者让命名空间作用域实体具有内部链接，现代 C++ 通常偏好匿名 namespace；函数内 static 是静态存储期但名字只在块内，其 linkage/实体身份还受外层函数影响。inline 外层函数的 local static 是程序共享，内部链接外层函数则每 TU 一份。

6. **`extern "C"` 解决了什么、没解决什么？**

   **答**：它指定 C language linkage，主要解决符号命名与 C 调用边界查找，禁止按 C++ 方式重载同一 C 名。它不保证 STL 类型布局、编译器运行库、异常、内存分配器兼容。稳定 ABI 仍应使用 C 风格简单数据与显式所有权。

7. **静态库和动态库的核心区别？**

   **答**：静态库目标代码在最终链接时复制进可执行文件，部署简单但每个程序各带一份、升级需重新链接；动态库在装载/运行时解析，共享代码、可独立替换，但涉及导出可见性、版本、搜索路径和 ABI 兼容。

8. **为什么不能轻易跨 DLL 边界传 `std::string` 并由另一侧释放？**

   **答**：两侧可能使用不同编译器/标准库布局、Debug ABI、CRT heap 或 allocator；一侧创建另一侧析构会跨堆释放，成员布局也可能不一致。更稳的是 caller-provided buffer、opaque handle，加上“谁创建谁销毁”的同模块释放函数。
