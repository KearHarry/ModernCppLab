# D3 · 线程安全的单例（Meyers / call_once / 双重检查锁）

难度 ⭐⭐⭐ · 预计 2h

## 为什么大厂爱考
单例几乎人人会写，但"**多线程下保证只构造一次**"才是面试真正的考点。它把并发的精髓浓缩在一行初始化里：竞态、内存序、双重检查锁的历史血泪、C++11 之后到底变了什么……能把 Meyers / `call_once` / DCLP 三种写法的取舍讲透，等于展示了你对 C++ 内存模型的真实理解。

## 背景知识

### 1) 朴素懒汉式为什么在多线程下错
```cpp
if (instance_ == nullptr)     // ① 检查
    instance_ = new T();      // ② 构造并赋值
return instance_;
```
两个线程可能**同时**通过 ① 的检查，于是各自 `new` 一次：构造了两个对象、泄漏、甚至不同调用拿到不同实例。这类「检查-再-执行（check-then-act）」竞态，是并发 bug 的经典模板。

### 2) Meyers 单例：函数内 `static` 局部变量（首选）
```cpp
static T& instance() {
    static T inst;   // C++11 起：标准保证它的初始化是线程安全的
    return inst;
}
```
**C++11 标准明确规定**：函数内静态局部变量的初始化，在并发首次进入时，只有一个线程执行构造，其余线程阻塞等待其完成（俗称 "magic statics"）。编译器替你插入了同步。代码最短、性能最好（初始化后是无锁快路径）、最不易错——现代 C++ 的默认选择。

### 3) `std::call_once` + `std::once_flag`
```cpp
std::call_once(once_, []{ instance_ = new T(); });
return *instance_;
```
标准库保证：传给 `call_once` 的可调用物，在多线程并发下也**恰好执行一次**（且若它抛异常，会让下一个线程重试）。适合初始化逻辑不止一行、或想显式表达"这段只跑一次"的场景。本质上和 Meyers 一样依赖底层同步原语。

### 4) 双重检查锁 DCLP：理解原理，少用
```cpp
T* p = instance_.load(std::memory_order_acquire);   // 第一次检查：无锁快路径
if (!p) {
    std::lock_guard<std::mutex> lk(mtx_);
    p = instance_.load(std::memory_order_relaxed);  // 第二次检查：持锁，防重复构造
    if (!p) {
        p = new T();
        instance_.store(p, std::memory_order_release);  // release 发布
    }
}
return *p;
```
两次检查的用意：第一次无锁，让"已初始化"的常见情况走最快路径；只有为空时才加锁，加锁后**再查一次**，防止两个线程都过了第一次检查后重复构造。

### 5) DCLP 的历史血泪与 acquire/release
C++11 之前没有标准内存模型，DCLP **著名地不可靠**：`instance_ = new T()` 可能被编译器/CPU 重排为"先发布指针、后跑完构造"，于是别的线程看到非空指针、却访问到**尚未构造完成**的对象。
C++11 用 `std::atomic` + 内存序修好了它：
- 写线程 `store(p, release)`：保证 `new T()` 的所有写入**先于**指针的发布；
- 读线程 `load(acquire)`：保证一旦读到非空指针，就能看到指针之前的全部写入（即构造完成的对象）。

这对 **release→acquire 同步**正是 DCLP 正确性的关键。也正因为 Meyers / `call_once` 把这些细节都封装好了，日常更该用它们，而不是手写 DCLP。

## 你要实现什么
打开 [include/singleton.hpp](include/singleton.hpp)。三个类各有一个静态 `ctor_count`（构造计数）和 `set/get`，已给出；你实现 3 个 `instance()`：

| 编号 | 函数 | 任务 |
|------|------|------|
| D3-1 | `MeyersSingleton::instance()` | 一行 `static T inst;` + 返回引用 |
| D3-2 | `CallOnceSingleton::instance()` | `std::call_once` 内 `new`，返回 `*instance_` |
| D3-3 | `DclpSingleton::instance()` | 原子指针 + 双重检查 + acquire/release |

## 关键坑
- **Meyers 必须是函数内 `static` 局部变量**——写成类的 `static` 成员就失去了"首次进入时线程安全初始化"的保证。
- **DCLP 的两次 load 内存序**：第一次 `acquire`、store 用 `release`；持锁后的第二次 load 可用 `relaxed`（已被 mutex 保护）。
- **DCLP 第二次检查不能省**——否则两个线程都过第一次检查后会各 `new` 一次。
- **构造计数用原子**，`++` 要用原子操作；本模块读取计数发生在所有线程 `join()` 之后，是安全的同步点。
- 别忘了**禁用拷贝/赋值**，单例不该被复制。

## 如何验证
```powershell
ctest --test-dir build -R D3 --output-on-failure
```
测试对三种单例各做一次"**16 线程并发首次访问**"：断言所有线程拿到的指针**完全相同**（同一对象），且 `ctor_count == 1`（构造恰好一次）；Meyers 还额外验证 `set/get` 的状态在多次访问间共享（证明确是同一对象）。

> 提示：骨架里 `instance()` 每次都 `new` 一个新对象 → 指针各不相同、计数远大于 1，所以一开始变红；但每个指针都有效，不会崩溃。

## 面试追问

1. 朴素懒汉式单例的竞态出在哪？画出两个线程的时序。

   **答**：朴素懒汉 `if (!inst) inst = new T;` 的竞态在"**检查**和**赋值**之间非原子"。时序：线程 A 执行 `if(!inst)` 为真，进入；CPU 切到线程 B，B 也执行 `if(!inst)` 仍为真（A 还没赋值），也进入；于是 **A、B 各 `new` 一个对象**——要么两个实例（违反单例、计数=2），要么一个指针覆盖另一个（泄漏 + 两线程拿到不同对象）。根因是"读-判断-写"这串复合操作在多线程下没有互斥/原子保护。

2. Meyers 单例为什么 C++11 后才线程安全？C++11 对函数内 static 局部变量的初始化做了什么规定？

   **答**：**Meyers 单例**是 `static T& instance(){ static T inst; return inst; }`——用**函数内静态局部变量**，首次执行到该行时构造、整个程序只构造一次。C++11 之前标准没规定它的初始化线程安全，多线程首次同时进入可能重复构造或读到半构造对象。**C++11 [stmt.dcl]/4 规定**：函数内静态局部变量的初始化是**线程安全**的——多线程同时首次到达时，**恰好一个**线程执行初始化、其余**阻塞等待**它完成（编译器自动插入一次性保护，如 `__cxa_guard_acquire`）。所以 C++11 起 Meyers 单例天生线程安全且最简洁，是首选写法。

3. DCLP 在 C++11 之前为什么不可靠？"指针已发布但对象未构造完"是怎么发生的？

   **答**：DCLP（双重检查锁定）`if(!inst){ lock; if(!inst) inst=new T; }` 在 C++11 前不可靠，根源是 `inst = new T` **不是原子**、且**编译器/CPU 可重排**。`new T` 分三步：①分配内存、②构造对象、③把地址写给 `inst`。重排后可能变成 ①③②——**先把指针发布给 `inst`，再构造对象**。此时另一线程在外层 `if(!inst)` 看到非空，**跳过锁直接返回并使用这个"指针已发布但对象还没构造完"的半成品**→读到未初始化数据、崩溃。C++11 前的内存模型无法禁止这种重排，所以 DCLP 当时被认为是坏的。

4. DCLP 里两次检查分别防什么？第二次检查能不能去掉？两次 load 的内存序为什么不同？

   **答**：**第一次检查**（无锁）：快路径，对象已存在时**避免每次都加锁**，绝大多数访问走这里、省锁开销。**第二次检查**（持锁内）：防竞态——多个线程可能都过了第一次检查、排队拿锁，后进来的必须**再确认对象还没被前一个建好**，否则重复构造。**第二次不能去掉**，去掉就退化成"多个线程各 new 一次"的竞态。**内存序不同**：第一次 `load(acquire)`——读到非空指针时，acquire 保证能看到构造者对对象的全部写（与构造者 `release store` 配对）；持锁内第二次检查已被 mutex 保护、可用较弱序。发布时 `store(release)` 确保对象构造完成后指针才可见。

5. `release`/`acquire` 在这里各保证了什么？换成 `relaxed` 会怎样？

   **答**：发布单例指针时 `store(release)`：保证**对象的构造（所有成员写）一定"先于"指针发布**，不会被重排到指针赋值之后——即"别人看到指针非空时，对象必已构造完整"。读取时 `load(acquire)`：保证**读到非空指针后，后续对对象的访问能看到构造者写入的所有内容**，不读到旧/未初始化值。二者**配对**建立 happens-before。换成 `relaxed`：失去顺序保证，可能出现"指针非空但对象成员还是垃圾"（正是上一题的 bug 重现）——relaxed 只保证指针这个**单一变量**的原子可见性，**不约束它与对象内容之间的顺序**。所以 DCLP 必须用 release/acquire（或干脆用 Meyers）。

6. 饿汉式（程序启动即构造）vs 懒汉式（首次用时构造）各有何优劣？单例的销毁顺序（static destruction order fiasco）怎么处理？

   **答**：**饿汉式**（启动即构造）：优点是**首次访问无竞态、无锁**、实现简单；缺点是**无条件付出构造代价**（即使没用到），且多个翻译单元的全局对象**构造顺序不确定**（static init order fiasco）。**懒汉式**（首次用时构造）：优点是**按需构造、不用不付费**、构造顺序由"首次访问"自然定序；缺点是首次访问要处理线程安全（Meyers/DCLP）。**销毁顺序问题**：不同 TU 的静态对象析构逆于构造、跨 TU 不确定，若单例 A 析构时用了已被析构的单例 B 就 UB。处理：用 **Meyers 局部静态**（析构按构造逆序、相对可控）；或 **Nifty Counter** 惯用法；或**故意泄漏**（`new` 了不 delete，进程退出由 OS 回收，彻底回避析构顺序），后者在"单例需活到程序最后"时常用。

7. 单例的常见弊端是什么（全局状态、可测试性差、隐藏依赖）？有哪些替代方案（依赖注入）？

   **答**：弊端：①**全局可变状态**——任何地方都能改，数据流难追踪、易引入隐藏耦合；②**可测试性差**——单例把依赖**硬编码**进调用点，测试时无法替换成 mock/stub，且单例状态在测试间残留、相互污染；③**隐藏依赖**——函数签名看不出它依赖了某单例，破坏"依赖显式化"；④并发下还要自己保证线程安全；⑤生命周期/销毁顺序难管。**替代方案**：**依赖注入（DI）**——把依赖**作为参数/构造函数显式传入**，调用方决定用哪个实例，测试时注入假实现；配合**接口抽象**（传 `ILogger&` 而非全局 `Logger::instance()`）、**服务定位器**（折中）、或由 **DI 容器/组合根**在程序入口统一装配。核心是"把全局单例换成显式传递的协作对象"，换回可测试性与解耦。
