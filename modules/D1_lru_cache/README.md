# D1 · 手写 LRU 缓存（哈希表 + 双向链表）

难度 ⭐⭐⭐⭐ · 预计 2.5h

## 为什么大厂爱考
LRU 缓存是**最经典的"手撕代码"题之一**（LeetCode 146），几乎所有大厂面试都可能让你白板写。它的精彩之处在于：单一数据结构都做不到 O(1)，必须把**哈希表**和**双向链表**组合起来，各取所长。能写对它，说明你真正理解了"为不同操作选择不同数据结构、再把它们粘合在一起"的工程思维——这正是面试官想看的。

## 背景知识

### 1) 什么是 LRU
缓存容量有限，装满后再插入新数据，就得淘汰一个旧的。**LRU 策略：淘汰"最久没被访问过"的那个**（Least Recently Used）。直觉是"最近用过的，将来更可能再用"。每次 `get`/`put` 命中，都把该元素标记为"最新"；淘汰时挑"最旧"的扔掉。

### 2) 为什么需要两个数据结构
要同时做到两件事，且都 O(1)：

| 需求 | 单独用它行不行 | 谁能 O(1) 做到 |
|------|----------------|----------------|
| 按 key 查 value | 链表查找是 O(n) ✗ | **哈希表** ✓ |
| 维护使用顺序、把元素提到最前/从最后删 | 哈希表无序 ✗ | **双向链表** ✓ |

所以组合：**双向链表**记录顺序（表头=最近用 MRU，表尾=最久未用 LRU），**哈希表** `key -> 链表结点` 让查找跳过遍历。

```
index_:  key ───────────┐  (哈希表：key 直接定位到结点)
                         ▼
items_:  front [MRU] (k,v) <-> (k,v) <-> (k,v) [LRU] back
              最近用过 ←───────────────→ 最久没用，下一个被淘汰
```

### 3) get / put 的流程
- **get(key)**：哈希表查；命中就把结点**挪到表头**（标记最新）并返回 value，未命中返回空。
- **put(key,value)**：
  - key 已存在 → 更新 value，并挪到表头；
  - key 不存在 → 表头插入新结点、哈希表登记；若**超出容量**，删掉**表尾**（LRU）那个，并从哈希表抹掉它的 key。

### 4) 关键魔法：`std::list::splice` + 在哈希表里存「迭代器」
把结点"提到表头"如果用"删一个、再插一个"会破坏迭代器。正确做法是 `list::splice`：它把结点从原位置 O(1) 地**剪切**到表头，**不会让任何迭代器/指针失效**——所以哈希表里存的那个迭代器，splice 之后依然指向同一个结点、继续可用。这是本题能 O(1) 的技术核心。

> 反例：若用 `std::vector` 存结点，一旦中间插入/删除，所有迭代器和指针全部失效，哈希表里存的"位置"立刻作废。`std::list` 的稳定迭代器特性是这套设计的前提。

### 5) 淘汰时的顺序坑
删表尾结点要"先抹哈希表，再删链表"：先用表尾结点的 key 把 `index_` 里的项 `erase` 掉，**再** `items_.pop_back()`。反过来先 `pop_back`，结点没了，就拿不到 key 去删哈希表项，留下悬挂的索引。

## 你要实现什么
打开 [include/lru_cache.hpp](include/lru_cache.hpp)。`contains`（只读、不刷新顺序）、`size`/`capacity`/`empty`、构造函数已给出。你实现 3 个 `TODO`：

| 编号 | 函数 | 任务 |
|------|------|------|
| D1-1 | `get(key)` | 命中 → `splice` 提到表头、返回 `&value`；未命中 → `nullptr` |
| D1-2 | `put(key,value)` | 已存在 → 更新 + 提头；不存在 → 表头插入，超容则 `evict_lru_()` |
| D1-3 | `evict_lru_()` | 删表尾：先 `index_.erase(key)`，再 `items_.pop_back()` |

## 关键坑
- **提到表头用 `splice`**，别"删了再插"——splice 保持迭代器有效，哈希表里存的迭代器才不会失效。
- **淘汰顺序**：先从哈希表 `erase(key)`，再 `pop_back()`。
- **put 已存在的 key 也要刷新顺序**（提到表头），不能只改值。
- **超容判断**：插入后 `items_.size() > capacity_` 才淘汰；正常只会多 1 个，淘汰一次即可。
- **get 命中必须刷新顺序**——否则热点数据会被误淘汰，LRU 形同虚设。

## 面试追问

1. 为什么 LRU 要"哈希表 + 双向链表"两个结构配合？只用其一分别卡在哪？

   **答**：LRU 要 O(1) 完成两件事：①**按 key 查值**，②**把某节点移到"最近使用"端并淘汰"最久未用"端**。**哈希表**给①O(1)，但它无序、说不出谁最久没用；**双向链表**按访问新旧排序、能 O(1) 在表头/表尾增删，但按 key 查要 O(n) 遍历。单用哈希表→淘汰时找不到最久者（要遍历）；单用链表→查值 O(n)。两者配合：哈希表存 `key→链表节点指针`，查值走哈希 O(1)，拿到节点后在链表里 O(1) 挪动/删除——互补凑齐 O(1)。

2. 为什么链表必须是**双向**的？单链表删除结点的复杂度是多少？

   **答**：因为 LRU 命中后要把**任意位置**的节点 O(1) 摘下移到表头，摘除需改它的**前驱和后继**指针，而只有**双向链表**能从节点直接拿到前驱（`node->prev`）。**单链表**删一个节点必须先找到它的前驱——从头遍历 O(n)，所以单链表删中间节点是 O(n)，无法满足 LRU 的 O(1)。双向链表 + 哈希表存节点指针，才能直接定位并 O(1) 摘除。

3. 为什么能用 `std::list` 而不能用 `std::vector` 存结点？迭代器失效规则讲一下。

   **答**：LRU 把哈希表的 value 存成**指向链表节点的迭代器/指针**，要求它在其它元素增删时**保持有效**。`std::list` 是节点式链表，**插入/删除只影响被操作节点，其它节点的迭代器/指针永不失效**，完美满足。`std::vector` 连续存储，`push_back` 扩容或中间 insert/erase 会**搬移元素、使大量迭代器和指针失效**，哈希表里存的位置全部作废、且中间删是 O(n)。迭代器失效规则简记：`vector` 扩容/插删使后续失效；`list`/`map` 等节点容器只失效被删元素；`unordered_map` rehash 失效迭代器但不失效元素指针。

4. `get` 为什么要改变数据结构（提到表头）？这对"读操作不应有副作用"的直觉有何冲突？

   **答**：因为 LRU 的"最近使用"必须把**读命中**也算作一次使用——`get` 到一个 key 说明它刚被用过，应刷新成最新、推迟淘汰，所以要把对应节点**移到表头**，这就改了链表结构。这确实和"读不应有副作用"的直觉冲突：`get` 逻辑上是读，却修改了内部结构（且因此**多线程下 `get` 也需写锁**）。但这是 LRU 语义的必然——"使用"包含读；可理解为"读的是缓存值、写的是使用记录"，副作用作用于元数据而非用户数据。

5. LRU、LFU、FIFO 淘汰策略有何区别？各适合什么场景？

   **答**：三者都按"淘汰谁"区分：**FIFO**——按**进入顺序**淘汰最早进来的，不管近期是否在用，实现最简但会误删高频老数据。**LRU**（最近最少使用）——淘汰**最久未被访问**的，假设"近期用过的还会再用"（时间局部性），适合大多数有热点的访问模式。**LFU**（最不经常使用）——淘汰**访问频次最低**的，适合频次比新近度更能反映重要性的场景，但要计数、对突发流量反应慢、老数据靠高计数赖着不走（需老化）。选择：通用缓存用 LRU；有稳定长期热点用 LFU；只需简单顺序淘汰用 FIFO。

6. 高并发下这个 LRU 怎么加锁？为什么 `get` 也要写锁？有没有分段锁/无锁的优化思路？

   **答**：最简单是**整把互斥锁**包住 `get`/`put`。注意 **`get` 也要写锁（独占锁）**，因为它会把节点移到表头、修改链表，是写操作，不能用共享读锁并发跑（会破坏链表）。这把全局锁在高并发下是瓶颈。优化：**分段锁（sharding）**——按 key 哈希分成 N 个独立小 LRU、各自一把锁，并发度提升 N 倍（Java `ConcurrentHashMap`、Guava Cache 思路），代价是淘汰变成"每段独立 LRU"的近似；**无锁/近似**——放宽精确性，用 CLOCK/采样近似 LRU 减少写竞争。工程上分段锁最常用。

7. Redis 的近似 LRU 是怎么做的？为什么不用精确 LRU（采样 + 时钟近似）？

   **答**：Redis 不维护精确 LRU 链表（每次访问都移动节点，在百万级 key 上开销和锁竞争太大、且给每个 key 存链表指针很费内存）。它用**近似 LRU**：每个对象存一个 24 位的**最后访问时间戳**，淘汰时**随机采样**若干 key（默认 5 个，`maxmemory-samples` 可调），从样本里挑时间戳最旧的淘汰，并用一个池保留候选——用"随机采样 + 比时间戳"近似全局最旧，省掉链表维护和指针内存。Redis 4.0 还提供近似 **LFU**（访问计数 + 衰减）。核心权衡：牺牲一点精确性，换 O(1) 无链表的低内存、低开销，对命中率影响很小。
