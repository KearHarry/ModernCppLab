# E5 · 数据导向设计（AoS / SoA / cache locality）

难度 ⭐⭐⭐⭐ · 预计 3h

## 为什么大厂爱考

高性能岗位问“为什么连续数组快”“AoS 和 SoA 怎么选”，考的不是会不会背 cache 友好，而是能否从**访问模式**反推数据布局。引擎一帧更新百万组件、服务器扫描状态位、图形管线批量变换顶点时，算法常只碰对象的少数字段；把冷字段一起拖进工作集会浪费带宽。

本模块延续 E1/E2 的数据导向主题，但特别强调测量纪律：普通单元测试环境噪声极大，绝不以“耗时必须更短”判断正确。我们验证结果等价、内存步长、标量读写数、模型化工作集和 buffer 增长事件；真实硬件性能需另用 Release benchmark 和 profiler 验证。

## 背景知识

### 1) AoS：实体完整记录连续

```cpp
struct Particle { float x,y,z,vx,vy,vz; uint32_t flags; };
vector<Particle> particles;
```

访问某个粒子的全部字段很方便，相邻完整实体连续，API 也自然。但只扫描 `x` 时，相邻 x 的地址步长是 `sizeof(Particle)`，中间夹着当前算法不需要的字段。

### 2) SoA：同类字段形成连续列

```cpp
struct Particles {
    vector<float> xs, ys, zs;
    vector<float> vxs, vys, vzs;
    vector<uint32_t> flags;
};
```

只扫 x 时，连续读取 float；更新位置时只遍历位置/速度六列，不触碰 flags。代价是完整实体访问要拼装多列，列长度一致性需要维护，容器管理和增删更复杂。

### 3) cache line、预取与 SIMD

CPU 按 cache line（常见但不保证为 64 字节）搬运内存。顺序访问容易被硬件预取；连续同类型数据还利于编译器自动向量化。指针追逐、随机索引和大步长会降低空间局部性。不过“连续”不自动等于“快”：算法强度、分支、数据规模、NUMA、编译选项都会影响结果。

### 4) 热/冷分离

实际工程往往不是纯 AoS 或纯 SoA，而是按系统拆出热数据：位置/速度放紧凑数组，调试名、脚本句柄等冷数据放另一侧；或采用 AoSoA，把固定小块内做 SoA，兼顾 SIMD 与块级实体管理。

### 5) 为什么单元测试不用耗时断言

CI 机器负载、频率调节、Debug/Release、分配器缓存都能让微基准波动。`EXPECT_LT(soa_time, aos_time)` 会变成随机红。正确分层：

- 单元测试验证值、布局不变量与确定性计数；
- benchmark 预热、重复、批量运行并报告分布；
- profiler/hardware counters 观察 cache miss、branch miss、带宽和指令数；
- 用真实数据集验证端到端收益。

本模块的 `modeled_bytes` 是教学模型：AoS 热扫描跨过每条完整记录，SoA 只跨热列；它不是硬件 cache miss 计数，README 和命名都不夸大结论。

## 关键坑

- **不要宣称 SoA 永远更快**：完整实体访问、数据量很小或索引同步成本高时 AoS 可能更好。
- **所有列必须同长度**：任一异常/提前返回造成部分追加，会破坏实体索引不变量；工业实现需事务式追加或统一 storage。不要假定不同列的 `capacity` 或增长策略必然相同。
- **reserve 不是 resize**：预留容量不创建实体。
- **引用/指针会因 vector 增长失效**：跨 push 保存某列地址同样危险。
- **分配次数不是性能全部**：SoA 有更多 buffer，却可能大幅改善热扫描；指标必须结合访问模式解释。
- **模型字节不是硬件计数器**：它是确定性教学指标，不可写成“证明 cache miss 减少 N 倍”。
- **基准必须优化构建**：Debug 下边界检查、未内联与测试框架开销会淹没布局差异。

## 如何验证

```powershell
ctest --test-dir build -R E5 --output-on-failure
```

测试覆盖：AoS/SoA 值等价；预留、重复预留与未预留 push 的逐 buffer 增长计数；相邻 x 的真实地址步长；位置更新的独立期望值、读写计数与模型字节；仅扫描 x 时的模型工作集；空容器边界。没有任何 wall-clock 断言。

> 骨架不追加、不更新并返回 0，所以测试安全预期红；访问元素前都有 `ASSERT_EQ(size, ...)` 防护，不会因空容器越界。

## 面试追问

1. **AoS 与 SoA 各适合什么访问模式？**

   **答**：经常一次读取/修改一个实体大部分字段时 AoS 自然且局部；跨大量实体只处理少数字段时 SoA 让热列连续、减少无关数据带宽并利于 SIMD。选择依据是最热循环，不是面向对象审美。

2. **为什么连续存储通常比链表快，即使二者遍历都是 O(n)？**

   **答**：复杂度忽略常数和存储层次。连续数组空间局部性好、cache line 利用率高、硬件易预取、少指针加载；链表节点分散，每步依赖上一步指针，容易 cache/TLB miss 且难并行预取。

3. **SoA 的主要工程代价是什么？**

   **答**：多列长度/索引必须严格同步；增删、排序、压缩要同时作用所有列；返回“实体引用”通常需代理对象；列各自分配；异常安全更复杂。可用 zip view、生成代码、tuple-of-vectors 或 ECS storage 封装这些不变量。

4. **什么是 AoSoA？**

   **答**：把实体按固定宽度分块，每块内部按字段数组存储，例如每 8 个粒子的 x 连续、再存 8 个 y。它让块宽匹配 SIMD，同时保留块级局部性和较易管理的记录组，是图形/HPC 常见折中。

5. **如何正确证明布局优化有效？**

   **答**：先以单测证明语义等价；再用优化构建、真实规模和稳定 benchmark 比吞吐/延迟分布；用 perf/VTune 等看 cache miss、IPC、带宽、向量化；最后做端到端负载验证。只看一次 `chrono` 或只看理论字节都不足以证明。

6. **为什么 SoA 有七次 reserve，却仍可能更快？**

   **答**：构建阶段多几个大块分配往往可摊薄，热循环可能执行数百万次。性能取决于生命周期总成本：若 SoA 让每帧扫描少读大量冷字段，长期节省远大于初始化的几次分配。提前 reserve 还能把增长成本集中到初始化。

7. **热/冷分离是什么？**

   **答**：把高频访问的小字段放紧凑热结构，把罕用的大字段放冷结构，通过 ID/索引关联。例如实体更新只需 transform/velocity，名字、调试信息和脚本状态另存。它避免热循环把冷数据带进 cache，是比全量 SoA 更务实的做法。

8. **数据导向设计是否意味着不用类和封装？**

   **答**：不是。它要求存储和算法围绕数据流设计，仍应通过类维护列长度、生命周期和并发不变量。封装边界可以是“组件块/查询/系统”，而非“每个实体一个拥有全部行为的对象”。DOD 反对的是忽视访问模式，不是反对抽象。
