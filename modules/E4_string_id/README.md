# E4 · 编译期字符串哈希 ID（constexpr FNV-1a string id）

难度 ⭐⭐⭐ · 预计 1.5h

## 为什么大厂爱考
"游戏里成千上万个资源名/状态名/事件名，运行时怎么高效标识与比较？"——能答出 **编译期哈希成整数 ID（constexpr）** 并讲清它为何能当 `switch` 标签、零运行时开销，是 C++20 `constexpr` 功力 + 引擎工程嗅觉的双重体现。UE 的 `FName`、各引擎资源系统、序列化 tag 都用这套"名字→编译期整数"的把戏。

## 背景知识

### 1) 问题：运行时玩字符串又慢又费
资源路径、动画状态、事件名……到处是字符串。运行时拿字符串做比较（逐字符）、做 map 键（哈希整串）既慢又占内存，还无法用于 `switch`。

### 2) 解法：编译期把名字哈希成一个整数
用 **FNV-1a** 把字符串算成 32 位整数。比较整数飞快，可作 map 键，还能当 `switch` 标签：
```cpp
switch (anim_id) {            // anim_id 是个 HashId（整数）
    case "idle"_id: ...;      // "idle"_id 在编译期就是常数 → 合法的 case 标签
    case "run"_id:  ...;      // 字符串永远做不到这点（switch 只接整型常量）
}
```
关键是 `"idle"_id` 在**编译期**就折叠成一个立即数，运行时零开销。

### 3) FNV-1a 算法（两行）
```
h = 2166136261 (offset basis)
对每个字节 b:  h = (h XOR b) * 16777619 (prime)     // 1a = 先异或、后乘
return h                                            // 32 位无符号乘法自然回绕 = 对 2^32 取模
```
"1a" 指异或在前、乘法在后（分散性比 FNV-1 好）。无符号溢出在 C++ 是**良定义**回绕，正是所需。

### 4) constexpr 的双重身份
函数标 `constexpr`：喂常量时编译期算（结果是立即数），喂运行时变量时退化为普通运行期函数。**同一份代码两用**。用户自定义字面量 `operator""_id` 让 `"name"_id` 这种最顺手的写法触发编译期哈希。

### 5) 和哈希表(C4)的配合
C4 是运行时哈希桶；这里把字符串压成整数 key。常配合：先 `_id` 把名字变 32 位整数，再拿它去 `unordered_map` 查——key 比较从"逐字符比串"降为"比一个 int"。

## 关键坑
- **顺序是"异或在前、乘在后"**（FNV-**1a**）。写反就成了 FNV-1，结果不同、分散性差，过不了测试向量。
- **字节要先转 `unsigned char`**：`char` 可能有符号，负值直接异或会污染高位。先 `static_cast<unsigned char>` 取 0..255 再升到 `HashId`。
- **依赖无符号回绕**：`h *= kFnvPrime32` 故意溢出，这是 FNV 的定义，不是 bug（无符号溢出良定义，无 UB、无告警）。
- **本模块测试用运行期断言、不用 `static_assert`**：因为骨架返回 0，若用 `static_assert(fnv1a_32(...)==X)` 骨架会**编译失败**（而非"变红"）。理解这个取舍——你自己加 `static_assert` 验证编译期性时，要在实现**之后**加。
- **`operator""_id` 的参数形式固定**：字符串字面量的 UDL 只接 `(const char*, std::size_t)` 这一种签名；后缀必须以下划线开头（`_id`），否则占用保留命名。

## 面试追问

1. 为什么要把字符串名编译期哈希成整数？解决了运行时的什么开销（比较、内存、`switch` 不可用）？

   **答**：游戏/引擎里资源路径、动画状态、事件名是海量字符串，**运行时直接用字符串**有三重开销：①**比较慢**——字符串相等要**逐字符**比较，最坏 O(len)，而整数比较是**一条指令** O(1)；②**内存/cache 差**——字符串本体散落堆上、长度不一，做 `map` 键还要哈希整串、存指针，cache 不友好；③**不能当 `switch` 标签**——`switch` 只接**整型编译期常量**，字符串永远进不了 `case`，只能写一长串 `if-else if` 逐个 `strcmp`。把名字**编译期**用 FNV-1a 哈希成一个 32 位整数后：比较降为比一个 `int`、可作紧凑的 map 键、`"idle"_id` 折叠成立即数能直接当 `case` 标签，**运行时零哈希开销**（哈希在编译期已算完）。这正是 UE `FName`、资源系统、序列化 tag 的核心把戏：对外用可读字符串，对内用整数 ID。代价：丢失可读性（需反查表 debug）、有极小碰撞概率（见追问 4）。

2. FNV-1a 和 FNV-1 的区别（异或/乘法顺序）？为什么 1a 分散性更好？还有哪些常见非加密哈希（MurmurHash、xxHash、CityHash）？

   **答**：二者只差**每字节里异或与乘法的先后**：**FNV-1** 是 `h = (h * prime) XOR byte`（**先乘后异或**）；**FNV-1a** 是 `h = (h XOR byte) * prime`（**先异或后乘**）。**为什么 1a 分散性更好**：1a 让当前字节**先**和累加值异或、**再**经乘法在整个字宽上扩散——异或改动的低位会被随后的乘法"搅拌"到高位，使**输入字节的微小差异更快更均匀地影响所有输出位**（雪崩效应更好）；FNV-1 先乘后异或，异或发生在乘法**之后**，本字节的影响来不及再被乘法扩散就直接落到结果，低位区分度差。所以实践中一律用 1a。**其它常见非加密哈希**：**MurmurHash**（MurmurHash3，快、分布好，广用于哈希表）、**xxHash**（极快、吞吐高，适合大数据/校验）、**CityHash/FarmHash**（Google，针对短串和现代 CPU 优化）。它们比 FNV 更快更均匀，但 FNV-1a **实现仅两行、极易 `constexpr` 化**，做编译期短字符串 ID 最顺手，所以引擎里短名哈希仍爱用它。

3. `constexpr` 函数是怎么做到"编译期能算、运行期也能算"的？什么情况下它**必须**在编译期求值？

   **答**：`constexpr` 函数是**"具备在编译期求值的资格"**，而非"总在编译期求值"。编译器对它**一份代码、按上下文两用**：①当**所有实参都是常量表达式**、且结果用在**需要常量的语境**（数组维度、`case` 标签、模板实参、`constexpr`/`static_assert` 初始化）时，编译器在**编译期执行**这个函数（在内部常量求值器里跑完循环），把结果折叠成**立即数**，运行时零开销；②当实参是**运行期变量**（如 `fnv1a_32(user_input.c_str())`）时，它**退化为普通运行期函数**，照常生成机器码在运行时算。这就是"同一份 `fnv1a_32` 既能 `"idle"_id` 编译期出常数、又能哈希运行时读入的字符串"。**何时必须编译期求值**：当结果用在**只接受常量表达式的位置**——`case "run"_id:`、`static_assert(hash("x")==…)`、模板非类型参数 `Foo<hash("x")>`、`constexpr T v = "x"_id;`、数组大小等；此时若函数某路径不满足 constexpr 规则会**编译报错**。补充：`consteval` 更强——**强制**每次调用都在编译期，杜绝意外退化到运行期。

4. 哈希冲突怎么办？32 位 ID 在几万资源下碰撞概率多大（生日悖论）？工程上如何缓解（升 64 位 / 编译期查重 / 保留反查表 debug 用）？

   **答**：哈希把任意字符串压到 32 位，**鸽巢原理**决定必然存在不同串映射到同一 ID 的**碰撞**。**概率（生日悖论）**：N 个随机串至少一对碰撞 ≈ `1 - exp(-N²/(2·2³²))`。代入：N=1 万 → ≈ **1.16%**；N=2 万 → ≈ **4.5%**；N≈7.7 万时达 **50%**。即几万量级资源下碰撞**并非罕见**，必须正视。**工程缓解**：①**升到 64 位哈希**——碰撞概率降到天文数字级（同 N 下约为 32 位的 1/2³²），UE 的 `FName` 索引、多数引擎都用 64 位；②**编译期/构建期查重**——把所有已知名字塞进一张 `constexpr` 表两两比对，**一发现碰撞就编译报错**（见追问 8），逼开发者改名，从源头杜绝；③**保留反查表（debug）**——运行时维护 `id → 原字符串` 映射，碰撞或调试时能查回是哪个名字；④**换更均匀的哈希**（Murmur/xxHash）或加盐，降低实际分布上的聚集。生产里常用"64 位哈希 + 构建期查重 + debug 反查表"三件套。

5. 为什么字节要先转 `unsigned char`？有符号 `char` 异或会出什么问题？

   **答**：因为 `char` 在多数平台上**默认有符号**，取值 -128..127，而 FNV 要把每个字节当**无符号的 0..255** 喂进去。若直接拿有符号 `char`（如某字节是 `0x80`，作为 `signed char` 是 **-128**）参与 `h ^ b`：表达式会先做**整型提升**，负的 `char` 提升为 `int` 时**符号扩展**成 `0xFFFFFF80`，于是异或污染了**高 24 位**——本该只翻动低 8 位的一个字节，结果把高位全搅了，得到的哈希与"按无符号字节"算的标准 FNV **不一致**，过不了标准测试向量，且不同符号性平台结果还不一样（破坏可移植性）。正确做法：`static_cast<unsigned char>(c)` 先把字节**截到 0..255** 再升到 `HashId`（`std::uint32_t`），保证只有低 8 位携带信息、跨平台一致。这是处理**字节级**算法（哈希、CRC、编解码）的通用纪律：一律用 `unsigned char` 看字节。

6. 用户自定义字面量（UDL）的规则：合法的参数签名有哪些？后缀命名为何必须下划线开头？

   **答**：**字符串字面量的 UDL** 形参签名**固定唯一**：`operator"" _id(const char* str, std::size_t len)`——编译器把 `"name"_id` 解析为以**字面量内容指针 + 长度**调用它（长度已知，无需再 `strlen`，且能含内嵌 `\0`）。整个 UDL 家族的合法签名还有：**整型** `operator""(unsigned long long)`、**浮点** `operator""(long double)`、**字符** `operator""(char)`，以及"**原始字面量**"形式 `operator""(const char*)`（拿到未解析的字符序列）和**模板** `operator""<char...>()`（编译期逐字符，常用于编译期数字解析）。对字符串而言只有 `(const char*, size_t)` 这一种。**后缀为何必须下划线开头**：C++ 标准**保留了"不以下划线开头的后缀"给标准库**（如 `s`/`sv`/`if`/`h` 分别是 `std::string`、`string_view`、`std::complex`、`std::chrono` 的官方字面量）。用户后缀若不加下划线，可能与现有或未来的标准后缀**冲突**，属保留/未定义行为；强制 `_` 开头（`_id`）划出**用户专属命名空间**，与标准后缀互不打架。所以自定义一律写 `_xxx`。

7. 这种"名字→整数 ID"和 UE 的 `FName`（字符串池 + 索引）相比，各自取舍？什么时候需要能反查回字符串？

   **答**：**纯哈希 ID（本模块）**：名字→FNV 整数，**单向**、无需任何全局表、**编译期即得常数**、可当 `switch` 标签、零运行时状态；缺点是**不可逆**（拿 ID 反查不回原名）、有**碰撞**风险、无法枚举"系统里有哪些名字"。**UE `FName`（字符串池 + 索引）**：维护一个**全局字符串表**，每个不同字符串**首次出现时入池**得到一个**索引（+实例号）**，`FName` 内部存这个索引；好处是**可反查字符串**（debug、UI 显示、序列化为可读名）、**相等比较是比索引** O(1)、**去重省内存**（同名只存一份）、**无哈希碰撞**（不同串必不同索引）；缺点是**需运行时全局池 + 插入时加锁/查表**（非纯编译期常量）、构造 `FName` 有运行时成本、跨进程/序列化要处理池一致性。**取舍**：要"纯编译期常量、当 case 标签、零状态"→哈希 ID；要"能显示/反查名字、保证无碰撞、可枚举"→字符串池索引。**何时需要反查**：日志与调试（打可读名而非数字）、编辑器/工具链展示、序列化成人类可读格式、报错信息、热重载时按名匹配。许多引擎**两者结合**：对外 `FName` 可反查，内部热路径再用其哈希/索引快比。

8. 如何在编译期就**检测哈希冲突**并报错？（把所有已知名字塞进 constexpr 表里两两比较 / consteval）

   **答**：思路是把"**所有已知名字**"集中到一处，在**编译期**两两比较它们的哈希，发现两个**不同字符串却同哈希**就让编译失败。具体做法：①**constexpr 表 + 两两比对**——把名字列成一个 `constexpr` 数组，写一个 `constexpr` 函数遍历所有对 `(i,j)`：若 `hash(name[i])==hash(name[j])` 但字符串本身不同，则返回"有冲突"；再用 `static_assert(!has_collision(table), "FNV collision!")` 钉在编译期——一旦撞了**直接编译报错**，逼开发者改名。②**`consteval` 强制编译期**——把哈希和查重函数标 `consteval`，保证它们**只能**在编译期求值，杜绝意外退化到运行期、确保检查真发生在构建时。③**注册宏/X-macro 集中清单**——用宏把每个名字"登记"进同一张编译期表，集中一次性查重，避免名字散落各处漏检。④进阶可在编译期把名字**排序**后只比较相邻项，把 O(N²) 降到 O(N log N) 应对大表。本质是**用编译期计算把"运行时才暴露的碰撞"提前到构建期拦截**，零运行时成本，是引擎资源/ID 系统保证唯一性的常用手段（配合追问 4 的 64 位与反查表）。
