# A9 · 异常安全与 RAII（强保证 / Scope Guard / 事务式提交）

难度 ⭐⭐⭐⭐ · 预计 3h

## 为什么大厂爱考

“代码能抛异常”不难，难的是抛到任何一行时对象仍然合法、资源不泄漏、外部看不到半成品。异常安全把构造析构、RAII、移动语义和容器实现串在一起，是区分“能写功能”和“能写基础库”的高频考点。

本模块完成两个设施：离开作用域必执行清理的 `ScopeExit`，以及先在副本上操作、成功后一次提交的 `TransactionalVector`。测试用确定性的异常注入验证承诺，不依赖真的耗尽内存。

## 背景知识

### 1) 三档常见异常保证

- **基本保证**：异常后对象仍合法、无泄漏，但值可能已经改变。
- **强保证**：异常后可观察状态与调用前完全一致，像操作从未发生。
- **不抛保证**：操作承诺不会抛，析构、释放资源、`swap` 等提交步骤尤其需要它。

没有任何保证则异常可能留下损坏的不变量、泄漏或重复释放。

### 2) 栈展开与 RAII

异常沿调用栈传播时，已经完整构造的自动对象会逆序析构，这叫栈展开。把锁、文件、内存等资源绑进对象析构，就无需在每条 return/throw 路径重复清理。构造函数自身失败时，对象析构不会运行，但已经构造完成的成员会自动析构。

### 3) Scope Guard 补齐“没有专用 RAII 类型”的清理

有时操作由一组 C API 或状态修改组成，没有现成资源类。`ScopeExit` 捕获一个清理 lambda，在离开作用域时执行；成功提交后调用 `release()` 取消回滚。它仍然是 RAII，只是资源释放策略来自调用方。

### 4) copy-and-commit 实现强保证

直接修改原容器，第三次插入抛出时前两次已经生效，只能给基本保证。事务式方案：

1. 复制当前状态到 `draft`；
2. 只修改 `draft`；
3. 所有可能抛的步骤完成后，用不抛的 `swap` 提交。

任何前两步异常都只销毁局部 draft，原对象未动。这也是 copy-and-swap 的核心思想。

### 5) “提交点”应尽量不抛

强保证依赖最后一步不能失败。标准 `vector` 在分配器满足条件时 `swap` 为 noexcept；真实泛型库必须检查 allocator propagation/equality 等契约，不能盲目假设所有 swap 都不抛。

## 关键坑

- 析构函数在栈展开期间再次抛异常会触发 `std::terminate`；清理动作必须不抛。
- 构造函数抛出时本对象析构不执行，因此裸资源应立即交给已经构造好的 RAII 成员。
- “先清空自己再复制对方”通常破坏强保证；先构造临时副本，再提交更安全。
- ScopeExit 被移动后必须解除源对象，否则两个析构会执行同一清理。
- catch 住异常不等于异常安全；关键是所有不变量和资源所有权是否仍正确。
- 强保证可能需要完整复制，成本较高；可以用日志、双缓冲或预分配换取更低成本的事务语义。

## 面试追问

1. 基本保证与强保证的区别是什么？

   **答**：基本保证只要求对象仍合法且无资源泄漏，值允许部分改变；强保证要求异常后可观察状态与调用前一致，具有 commit-or-rollback 语义。

2. 为什么析构函数通常必须 `noexcept`？

   **答**：异常传播引发栈展开时正在调用析构，若析构再抛出第二个异常，运行库无法同时传播两个异常，只能 `std::terminate`。因此资源释放应吞掉/记录错误或提供显式 `close()` 报错，而析构不传播。

3. 构造函数抛异常会调用这个对象的析构吗？

   **答**：不会，因为对象尚未完整构造；但已经构造完成的基类和成员会按逆序析构。因此资源应随拿随交给 RAII 成员，不能先放裸指针等构造末尾再接管。

4. copy-and-swap 为什么常提供强保证？

   **答**：所有可能失败的复制和修改都发生在局部临时对象上；它们失败只销毁临时对象。最后通过不抛的 swap 一次提交，因此外部要么看到完整新值，要么仍看到旧值。

5. `noexcept` 为什么会影响 `vector` 扩容？

   **答**：扩容搬到一半若移动抛出，旧元素可能已被掏空，难以恢复强保证。若移动不是 noexcept 且类型可拷贝，vector 通常用 `move_if_noexcept` 选择拷贝，保留旧缓冲区作为回滚点。

6. Scope Guard 与 `try/catch` 有什么不同？

   **答**：try/catch 处理异常类型和恢复策略，但不能自动覆盖正常 return、多处分支等所有退出路径；Scope Guard 把清理绑定到作用域，无论正常、return 还是异常都执行，通常与 catch 分工合作。

7. 如何确定一个操作真的满足强保证？

   **答**：列出每个潜在抛出点，检查在该点之前是否只修改了临时状态；确认异常展开会释放全部已取得资源；最后确认提交步骤不抛。测试可用“第 N 次操作抛出”遍历每个失败点并比较调用前后状态。

8. 什么时候不值得提供强保证？

   **答**：复制成本巨大、操作天然不可逆（例如已发送网络包）、或调用方只需要对象合法时，基本保证可能更合理。接口应明确承诺，并通过事务日志、补偿操作等机制处理外部副作用。
