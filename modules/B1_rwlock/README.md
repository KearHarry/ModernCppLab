# B1 · 手写读写锁 RWLock（std::shared_mutex 的核心）

难度 ⭐⭐⭐⭐ · 预计 2.5h

## 为什么大厂爱考
"读多写少的共享数据，怎么提高并发？"——一把普通互斥锁把**读也串行**了，吞吐很差。读写锁让**多个读者并行、写者独占**，是高并发服务的常用件。手写它能同时考查：`condition_variable` 的"按条件等待/唤醒"、临界区的最小化、以及**写者饥饿**这个经典并发陷阱。讲清"为什么用 `cv.wait(lk, 谓词)` 而不是裸 `wait`、怎么避免写者饿死"，是并发功底的硬信号。

## 背景知识

### 1) 读写锁的语义：多读单写
```
读者 lock_shared() ┐
读者 lock_shared() ├─ 可同时持锁（并发读无害）
读者 lock_shared() ┘
写者 lock()         ── 独占：排斥所有读者和其他写者
```
适用：配置表/路由表/缓存元信息——绝大多数访问是读，偶尔更新。比互斥锁吞吐高得多。

### 2) 用一把 mutex + 一个 condition_variable 实现
内部三个计数描述状态，`mtx_` **只短暂保护这些计数**，真正的等待交给 `cv_`：
```cpp
int  readers_;          // 活跃读者数
bool writer_;           // 是否有写者持锁
int  waiting_writers_;  // 排队中的写者数
```

### 3) condition_variable 的正确姿势：`wait(lk, 谓词)`
```cpp
std::unique_lock<std::mutex> lk(mtx_);
cv_.wait(lk, [&]{ return 条件; });   // 等价于 while(!条件) cv_.wait(lk);
```
`wait` 会**原子地"释放锁 + 挂起"**；被唤醒后**重新加锁 + 复查谓词**。带谓词的重载天然防住**虚假唤醒**（spurious wakeup）和**唤醒丢失**。务必用带谓词版本，别裸 `wait`。

### 4) 四个动作怎么写
```cpp
lock_shared():    wait 到「无写者 且 无写者排队」→ ++readers_
unlock_shared():  --readers_；若归零 → notify_all（可能轮到写者）
lock():           ++waiting_writers_；wait 到「无写者 且 readers_==0」→ writer_=true；--waiting
unlock():         writer_=false；notify_all
```

### 5) 写者优先：防写者饿死
若 `lock_shared` 只看 `!writer_`，那么源源不断的读者会一直插队，**写者可能永远等不到** `readers_==0`。解法：让新读者在**有写者排队**时也让路——谓词加上 `&& waiting_writers_ == 0`。这就是"写者优先"，本模块采用。代价是极端读压力下读者要等写者，但避免了写饥饿。

### 6) 和 std::shared_mutex 的关系
你写的就是 `std::shared_mutex` 的核心。配合 RAII：`std::shared_lock`（读）/ `std::unique_lock`（写）。本模块给了 `ReadGuard`/`WriteGuard` 两个等价守卫，构造上锁、析构解锁，异常安全。

## 关键坑
- **必须用带谓词的 `wait(lk, pred)`**：裸 `wait` 会被虚假唤醒坑到，且无法表达"等待某条件"。
- **`notify` 时机**：`unlock_shared` 只在 `readers_` 归零时通知（否则没必要）；`unlock` 总要通知。
- **临界区要短**：`mtx_` 只保护计数的读改，绝不能在持有 `mtx_` 时去做用户的读/写工作——那样就退化成普通互斥锁了。
- **写者饥饿**：不加 `waiting_writers_` 这道让路条件，重读负载下写者可能永远拿不到锁。
- **RAII 配对**：`lock_shared` 必须配 `unlock_shared`、`lock` 配 `unlock`，别交叉；用 `ReadGuard`/`WriteGuard` 自动配对最稳。
- **不可重入**：同一线程已持读锁再去拿写锁（或反之）会死锁——和 `std::shared_mutex` 一样，本模块不支持重入。

## 面试追问

1. 读写锁相比普通互斥锁的收益来自哪？什么负载下才划算（读写比）？

   **答**：收益来自允许**多个读者同时持锁并行**——普通互斥锁把读也串行化，而读操作不改状态、彼此无冲突，本可并发。只有"读多写少"且临界区有一定耗时才划算：读占比越高、临界区越长，并行读的收益越能盖过读写锁更复杂的簿记（维护读者计数、cv 协调）开销。若写很频繁或临界区极短（如只读一个字），读写锁的额外开销反而比普通 mutex 慢，直接用 mutex 或原子更好。

2. `cv.wait(lk, pred)` 内部做了什么？为什么必须带谓词？虚假唤醒是什么？

   **答**：带谓词版等价于 `while (!pred()) cv.wait(lk);`。`cv.wait(lk)` 会**原子地"释放 lk + 把线程挂入等待队列睡眠"**，被唤醒后在返回前重新加锁。必须带谓词是因为"被唤醒"不等于"条件成立"——可能 notify 后条件又被别人改回去了，所以醒来必须重新检查。**虚假唤醒**（spurious wakeup）指线程在没有任何 notify 的情况下也可能自行醒来（标准允许实现这样做以换效率），因此"醒了就盲信条件成立"是错的，必须用循环/谓词复查。

3. 写者饥饿怎么产生、怎么解决？"读者优先 / 写者优先 / 公平"三种策略各有什么取舍？

   **答**：读者源源不断进出、读者计数永不归零，写者就一直等不到"无读者"窗口→写者饥饿。解决靠调度策略：**读者优先**——只要有读者就让后续读者插队，吞吐最高但写者可能饿死；**写者优先**——一旦有写者在等就挡住新读者，写延迟低但读可能饿、写多时退化成串行；**公平**（按到达顺序 FIFO 排队）——不饿死任何一方，但放弃了"无脑放读者进来"的峰值吞吐。工程上常用写者优先或公平来防饥饿。

4. 为什么临界区只保护计数、不能罩住真正的读写工作？罩住了会怎样？

   **答**：读写锁内部那把 mutex+cv 只用来保护"读者数/写者标志"这几个簿记变量，进出时短暂持有；真正的读写工作发生在"已登记成读者/写者"之后、且**不持那把内部 mutex**。若把整段工作都罩在 mutex 里，等于又把所有读写串行化了——读者无法并发，读写锁直接退化成普通互斥锁，白费力气。正确做法是锁内只改计数、锁外干活。

5. `notify_one` vs `notify_all` 在读写锁里怎么选？滥用 `notify_all` 的代价（惊群）？

   **答**：写者释放锁时可能要放进"多个等待的读者"，这种"一对多唤醒"用 `notify_all`；读者全部退出、只需放进一个写者时用 `notify_one` 足够。**惊群**（thundering herd）指 `notify_all` 把所有等待者一次性唤醒，它们争抢同一把锁，结果只一个能继续、其余复查谓词后又睡回去——大量无效的唤醒/上锁/再睡，浪费 CPU 与上下文切换。所以"只可能有一个等待者能前进"时别用 notify_all。

6. 读写锁可重入吗？升级（持读锁→升为写锁）为什么容易死锁？

   **答**：标准的 `std::shared_mutex` **不可重入**——同一线程重复加锁是未定义行为。锁升级（持读锁时直接升为写锁）容易死锁是因为：升级要求"等所有其他读者退出"，但若两个线程都持读锁、又都想升级，各自都在等对方先放掉读锁→相互等待、谁也升不了→死锁。所以标准库不提供原子升级；要改写得先 `unlock_shared` 再 `lock`（中间有窗口，需重新检查状态）。

7. `std::shared_mutex` / `std::shared_lock` 怎么用？C++14/17 各加了什么？

   **答**：写者用 `std::unique_lock<std::shared_mutex>`（或 `lock_guard`）拿**独占锁**，读者用 `std::shared_lock<std::shared_mutex>` 拿**共享锁**，多个读者可同时持有。C++14 先引入 `std::shared_timed_mutex`（带超时的 `try_lock_for/until`）和 `std::shared_lock`；C++17 才加入更轻量、无超时的 `std::shared_mutex`。用法：`shared_lock lk(m);` 读、`unique_lock lk(m);` 写，RAII 自动释放。

8. 无锁或基于原子的读写同步（如 seqlock、RCU）相比 cv 方案适合什么场景？各自代价？

   **答**：**seqlock**——写者改一个序号（写前奇、写后偶），读者读前读后比对序号、不一致就重读，读侧几乎零开销、无需加锁，适合"写极少、读极多、数据小可整体重读"（如时间戳、配置）；代价是读者可能空转重试、数据不能含指针（读到一半被改会读到撕裂值）。**RCU**——读者完全无锁地读旧版本，写者复制改新版后原子换指针、并延迟回收旧版直到所有读者离开，读侧扩展性极佳（Linux 内核大量使用）；代价是写者重、回收延迟、实现复杂。两者都适合"读远多于写"、读侧比 cv 读写锁更快，但放弃了通用性与阻塞等待能力。
