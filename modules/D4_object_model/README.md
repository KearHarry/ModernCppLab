# D4 · 虚函数与对象模型（vtable / 虚析构 / clone / RTTI）

难度 ⭐⭐⭐ · 预计 2.5h

## 为什么大厂爱考
"虚函数是怎么实现的？"几乎是 C++ 面试必问。它背后牵出一整套 **C++ 对象模型**：vptr/vtable、动态分派的代价、为什么基类析构要 virtual、对象切片、抽象类、RTTI……这些不是语法细节，而是理解一切多态框架、排查诡异崩溃（内存泄漏、调错函数）的地基。把这一个 Shape 例子吃透，对象模型的问题就能对答如流。

## 背景知识

### 1) 虚函数的实现：vptr + vtable
一个类只要有虚函数，编译器就为它生成一张 **虚函数表（vtable）**——按槽位存放各虚函数的真实地址。每个对象里埋一个隐藏指针 **vptr**，指向其所属类型的 vtable。

```
Circle 对象            Circle 的 vtable
┌──────────┐          ┌────────────────────┐
│  vptr ───┼────────▶ │ [0] Circle::area   │
│  r_      │          │ [1] Circle::name   │
└──────────┘          │ [2] Circle::clone  │
                      │ [3] ~Circle        │
                      └────────────────────┘
```

调用 `shape->area()` 时，编译器生成"查 vptr → 取 vtable 槽位 → 间接调用"的代码。对象构造时 vptr 被设为其**真实类型**的 vtable，于是运行时调到正确的派生版本——这就是**动态分派**。代价：一次间接跳转 + 无法内联；收益：运行时多态。

### 2) 静态类型 vs 动态类型；动态分派
`Shape* s = new Circle;` 中，`s` 的**静态类型**是 `Shape*`（编译期就定），**动态类型**是 `Circle`（运行期才知道）。**只有虚函数**按动态类型分派；非虚函数、默认参数、`static` 成员都按静态类型。

### 3) 为什么基类析构必须 virtual
通过基类指针 `delete` 派生对象：
- `~Base()` **非 virtual** → 只调 `~Base()`，跳过派生析构 → 资源泄漏，**未定义行为**。
- `~Base()` **virtual** → 经 vtable 找到 `~Derived()`，先派生后基类，顺序正确、全部释放。

口诀：**会被继承、且会通过基类指针删除的类，析构必须 virtual。**

### 4) 抽象类 / 纯虚函数 / 防切片
`virtual double area() const = 0;` 的 `= 0` 是**纯虚函数**：只声明不实现。含纯虚函数的类是**抽象类**，不能实例化，只能被继承。

**对象切片（slicing）**：把派生对象按值赋给基类对象，会"切掉"派生部分，只剩基类（vptr 也变回基类的，多态失效）。而抽象基类**天然防切片**——`Shape` 不能作为值存在，你只能用 `Shape*`/`Shape&` 持有它，逼你走多态。

### 5) 虚拷贝：clone() / 原型模式
普通拷贝构造只认**静态类型**，无法用 `Shape*` 复制出正确的派生对象。解法：每个派生类重写 `clone()` 返回 `make_unique<自己>(*this)`，于是 `base->clone()` 多态地克隆出正确类型——**原型模式（Prototype）**。

### 6) RTTI：dynamic_cast / typeid
运行时类型识别。`dynamic_cast<Circle*>(shape)`：实际是 Circle 返回有效指针，否则 `nullptr`（引用版失败则抛 `std::bad_cast`）。它依赖 vtable 挂的类型信息，**仅对多态类型可用**。`typeid(x).name()` 取动态类型名。注意：大量 `dynamic_cast` 往往是设计有问题的信号（应优先用虚函数表达多态）。

## 关键坑
- **`clone()` 要返回"自己的"类型**：`make_unique<Circle>(*this)`，别返回基类。
- **基类析构已经是 virtual**（本模块给好了）——理解为什么：去掉 virtual 再想想通过 `Shape*` 删除会怎样。
- **`dynamic_cast` 只对多态类型有效**（类里得有虚函数），失败返回 `nullptr`（指针版）。
- **重写要带 `override`**：拼错签名时编译器会报错，而不是悄悄变成"新函数"。
- **不要试图把 `Shape` 按值存进容器**——它是抽象类；多态容器要存 `unique_ptr<Shape>`。

## 面试追问

1. 虚函数怎么实现的？vptr 在对象的什么位置？vtable 存什么、何时建立、vptr 何时被设置？

   **答**：虚函数靠 **vtable（虚函数表）+ vptr（虚表指针）** 实现。每个**有虚函数的类**有一张 vtable——一个**函数指针数组**，按虚函数声明顺序存该类各虚函数的**最终覆盖版本**地址（还含 RTTI、虚基偏移等）。每个**对象**里藏一个 **vptr**，指向其真实类型的 vtable；vptr 通常放在**对象内存的最前面**。vtable 在**编译/链接期为每个类静态生成**（每类一张、同类对象共享）；vptr 在**构造函数中被设置**——基类构造时先指向基类 vtable，进入派生构造体前改指向派生 vtable。调用 `p->f()` 时：取 vptr→在 vtable 里按 f 的固定下标取函数地址→间接调用，运行期分派到真实类型的实现。

2. 有虚函数的类 `sizeof` 为什么变大？多一个指针的开销值不值？

   **答**：因为对象要嵌入一个 **vptr**（64 位上 8 字节），所以一个空的、仅有虚函数的类 `sizeof` 从 1 变成 8。注意 vptr 是**每对象一个**，vtable 是每类一张、不计入对象大小。**值不值**：对绝大多数类，多 8 字节、一次间接跳转换来**运行期多态**这一核心能力，完全值得。但对**海量小对象**（如几百万个 2D 点）或**热路径内循环**，8 字节/个的内存放大和不可内联的间接调用可能成瓶颈——此时考虑 CRTP 静态多态或不用虚函数。一句话：需要运行期多态就值，纯数据/性能极致场景就斟酌。

3. 为什么基类析构要 virtual？不写会怎样？什么时候可以不写（不会被基类指针删除）？

   **答**：因为通过 **基类指针 `delete`** 一个派生对象时，若析构非虚，只调**基类析构**、**派生类析构被跳过**→派生独有的资源（堆内存、句柄）泄漏、对象被**部分销毁**，是 UB。把基类析构声明 `virtual` 后，`delete base_ptr` 会经 vtable 分派到**派生析构**，再依次调基类析构，完整销毁。**何时可以不写虚析构**：当该类**不会被当作基类、或绝不会通过基类指针/引用 delete**（如纯静态多态的 CRTP 基类、值类型、`final` 且自管生命周期的类）。准则：**只要可能 `delete derived via base*`，基类析构就必须 virtual**；纯接口类尤其要写。

4. 什么是对象切片？怎么避免？抽象基类为什么能天然防切片？

   **答**：**对象切片**指把**派生对象按值赋给/拷贝给基类对象**时，只有基类那部分被拷过去、**派生独有的成员和 vptr 被"切掉"**，结果是个纯基类对象、多态丢失。例：`Base b = derived;` 或 `void f(Base b)` 按值传参。**避免**：多态一律用**基类指针或引用**（`Base&`、`Base*`、`unique_ptr<Base>`）传递和持有，绝不按值；容器存 `unique_ptr<Base>` 而非 `Base`。**抽象基类天然防切片**：含纯虚函数的抽象类**不能被实例化**，于是 `Base b;`、按值传 `Base`、`vector<Base>` 统统**编译不过**，逼你必须用指针/引用——从语言层面堵死了切片路径。

5. 构造函数/析构函数里调用虚函数，会分派到派生版本吗？为什么不会（vptr 还没/已不指向派生）？

   **答**：**不会**——构造/析构里调用虚函数，调到的是**当前正在构造/析构的那一层**的版本。原因在 **vptr 的设置时机**：构造时**先构造基类子对象**，那一刻 vptr 还指向**基类 vtable**（派生部分尚未构造，不能让虚调用跳进还没初始化的派生函数），所以基类构造体里的虚调用走基类版本；等基类构造完、进入派生构造体，vptr 才改指向派生 vtable。析构是**逆序**：先析构派生部分并把 vptr 改回基类，再执行基类析构体，所以基类析构里的虚调用也只看到基类版本。这保证"虚调用永远不会落到一个尚未构造或已被析构的对象层"——是安全设计，不是 bug。实践上应避免在构造/析构中依赖虚分派。

6. `dynamic_cast` 的原理和代价？什么场景该用、什么场景说明设计有问题？

   **答**：**原理**：`dynamic_cast` 在**运行期**借对象的 **RTTI**（经 vptr 找到 type_info）沿继承图检查"真实类型能否安全转成目标类型"，可以则返回调整好偏移的指针、不行则**指针返 nullptr / 引用抛 `bad_cast`**。**代价**：要查 RTTI、可能遍历继承层次（多重/虚继承下更慢），比 `static_cast`（编译期、零开销）显著贵；还要求类型**多态（有虚函数）**。**该用的场景**：确实需要运行期"向下/侧向转型"且要安全检查，如插件系统、反序列化、与外部对象交互。**说明设计有问题**：在自己可控代码里**频繁 `dynamic_cast` 然后按类型分支**（`if(dynamic_cast<Cat*>)...else if(dynamic_cast<Dog*>)...`）——这通常意味着**本该用虚函数**把行为多态化，把分支下放到各派生类的虚函数里更干净。

7. `override` 和 `final` 的作用？`final` 对去虚化（devirtualization）优化有何帮助？

   **答**：**`override`**：显式声明"我意在覆盖基类虚函数"，编译器据此**检查签名是否真匹配**某基类虚函数——签名写错（参数/const/返回不符）就**编译报错**，挡住"本想覆盖却因笔误变成新函数"的隐蔽 bug。**`final`**：用在虚函数上禁止派生类再覆盖；用在类上禁止被继承。**对去虚化的帮助**：`final` 给编译器"**此处不可能有更派生的覆盖版本**"的确定信息，于是通过 `final` 类型的指针/引用调用该虚函数时，编译器能**确定唯一目标、把虚调用变成直接调用甚至内联**，省掉 vtable 间接跳转。同理 `final` 类的虚调用、或对象类型编译期已知（如局部对象直接调用）也能去虚化。

8. 多重继承 / 虚继承下对象布局和 vptr 会变成什么样？为什么菱形继承要用虚继承？

   **答**：**多重继承**：对象里**每个有虚函数的基类子对象各带一个 vptr**，按基类顺序拼接，所以多重继承对象可能有**多个 vptr**；通过非首基类指针调用时，编译器借 vtable 里的 **this 偏移调整（thunk）** 把指针修正到正确子对象。**虚继承**：为解决菱形问题共享虚基类子对象，布局里加入**虚基类指针/偏移（vbptr 或 vtable 中的 vbase offset）**，虚基类被放到对象末尾由各路径共享，访问虚基成员要经一次间接偏移，布局更复杂、`sizeof` 更大。**为什么菱形要虚继承**：`B:A, C:A, D:B,C` 若普通继承，`D` 里会有**两份 A 子对象**——数据重复、`A` 成员二义（`d.a` 不知指哪份）、`A*` 向上转型有歧义。**虚继承**让 `B`、`C` **共享同一份 A** 子对象，消除重复与二义，代价是访问虚基多一层间接、构造时由**最派生类 D 直接负责构造虚基 A**。
