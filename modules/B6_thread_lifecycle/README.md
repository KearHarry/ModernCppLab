# B6 · 线程生命周期、协作取消与死锁避免

难度 ⭐⭐⭐ · 预计 3h

## 为什么大厂爱考

会写 `std::thread t(f)` 只是起点。线上事故往往发生在收尾：异常路径漏掉 `join()` 导致 `std::terminate`，对象先析构而后台线程仍访问它，等待线程没有取消通道，或者两个线程按相反顺序拿锁形成 ABBA 死锁。本模块把这些零散问题串成一条主线：**线程必须有明确所有者、明确结束协议、明确的锁顺序**。

## 背景知识

### 1. `std::thread` 的三种状态

默认构造、已经 `join()` 或 `detach()` 的线程对象不可 join；成功启动且尚未收尾的对象 `joinable()==true`。一个仍 joinable 的 `std::thread` 若直接析构，标准规定调用 `std::terminate`。因此每条控制流——正常返回、异常、提前 return——都必须完成 join 或 detach。

`join()` 等线程函数返回，并建立同步关系：子线程结束前的写，对 `join()` 返回后的线程可见。`detach()` 则放弃所有权，线程在后台独立运行；它不会自动延长捕获对象的寿命，所以捕获局部变量、`this` 或所属资源时极易产生悬空访问。

### 2. 用 RAII 管住生命周期

`JoiningThread` 把 `std::thread` 当成资源：构造取得所有权，析构若仍 joinable 就 join。它和 `lock_guard` 的思想完全一致——正确性不依赖调用者记住收尾。真实工程还需考虑移动所有权、析构等待时间以及“不得从被拥有线程中销毁自己”等约束，本实验先实现最小可靠版本。

### 3. `std::jthread` 与协作式取消

C++20 的 `std::jthread` 默认在析构时 `request_stop()` 再 `join()`，并可把 `std::stop_token` 自动传给形如 `f(stop_token, args...)` 的任务。停止是**请求**而不是强杀：任务要在循环、批次边界或阻塞点检查 `stop_requested()`，清理资源后主动返回。

`stop_source` 发请求，`stop_token` 只观察状态；二者共享一个停止状态。多个观察者可以持有同一 token。

### 4. 可取消的条件等待

传统 `condition_variable::wait` 只会因通知或虚假唤醒返回，外部停止请求若没有同时通知它，线程可能永远睡着。C++20 的 `condition_variable_any` 提供：

```cpp
bool ok = cv.wait(lock, token, predicate);
```

谓词成立返回 `true`；停止已请求且谓词仍不成立返回 `false`。它把“注册停止回调、释放锁并睡眠、醒后复查谓词”组成一个不会丢唤醒的协议。

### 5. 死锁与 `std::scoped_lock`

死锁通常需要四个条件：互斥、占有且等待、不可抢占、循环等待。转账要同时锁住 A/B 两个账户；线程 1 若先 A 后 B，线程 2 先 B 后 A，就形成 ABBA。

```cpp
std::scoped_lock lock(a.mtx, b.mtx);
```

多参数 `scoped_lock` 使用与 `std::lock` 等价的死锁避免算法取得全部锁，并在析构时释放其持有的全部锁；代码不应依赖这些锁的具体解锁次序。另一种方案是制定全局锁顺序，但按地址排序要谨慎处理同一对象和可移植比较。

## 关键坑

- 不要让 joinable 的 `std::thread` 析构；“异常很少发生”不是理由。
- 不要把 detach 当作省事版 join。后台线程捕获的每个对象都必须有独立、可证明的寿命。
- `request_stop()` 不会抢占正在执行的代码；长任务必须设计停止检查点。
- 等待必须带谓词，且共享状态要在同一 mutex 下修改；否则有虚假唤醒和丢唤醒。
- 不要持锁执行任意用户代码，也不要在持锁时 `join()` 一个可能需要该锁才能退出的线程。
- 多锁操作要么一次交给 `scoped_lock`，要么全系统遵守同一锁序；局部“看起来一致”不够。
- 同一账户转给自己时不能把同一 mutex 传两次给 `scoped_lock`，应先特判。

## 面试追问

1. **为什么 joinable 的 `std::thread` 析构会终止进程？**

   **答：**标准无法猜测调用者想阻塞等待还是让线程后台运行。静默 detach 可能制造悬空访问，静默 join 又可能让析构意外长时间阻塞，所以把未处理的所有权视为程序错误并 `terminate`，迫使调用者明确选择。

2. **`join()` 建立了什么内存可见性？**

   **答：**线程函数的完成 synchronizes-with 对应 `join()` 的成功返回。因此子线程结束前的操作 happens-before join 返回后的操作；读取普通结果无需再用 atomic，但线程运行期间的并发访问仍需同步。

3. **`jthread` 比 `thread` 多了什么？**

   **答：**析构自动请求停止并 join；内部关联 stop source/token；若可调用物首参接受 `stop_token`，构造时会自动传入。它解决所有权和取消协议，但仍不能强杀不合作的任务。

4. **停止标志用普通 `bool` 行不行？**

   **答：**若一个线程写、另一个线程无锁读普通 bool，就是数据竞争和 UB。可用 atomic bool，但 stop_token 还提供共享状态、回调注册和与 C++20 等待设施的集成，协议更完整。

5. **死锁的四个必要条件是什么，通常破坏哪个？**

   **答：**互斥、占有且等待、不可抢占、循环等待。工程里常通过统一锁序或一次性锁多个 mutex 破坏循环等待；也可用 try-lock 回退破坏占有且等待。

6. **`std::lock` 与 `std::scoped_lock` 的关系？**

   **答：**`std::lock` 只负责以死锁避免算法取得多把锁，之后仍需用 adopt_lock 守卫释放；`scoped_lock(m1,m2)` 把获取与 RAII 释放合在一起，异常安全且更不易漏解锁。

7. **为什么不能持 mutex 调用 `join()`？**

   **答：**被等待线程可能正要取得同一 mutex 才能完成，于是当前线程持锁等它退出，它等锁继续，形成确定性死锁。通常先发布停止状态、解锁并通知，再 join。

8. **可取消等待为什么仍需要谓词？**

   **答：**停止令牌只增加一个唤醒原因，不能消除虚假唤醒，也不能代表业务条件成立。返回后必须区分“队列有数据”和“仅收到停止请求”，谓词重载正是把两者安全组合起来。
