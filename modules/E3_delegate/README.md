# E3 · 多播委托 / 信号-槽 Signal（multicast delegate / event）

难度 ⭐⭐⭐ · 预计 2h

## 为什么大厂爱考
"模块间怎么通信又不互相依赖？"——能答出 **信号-槽 / 多播委托** 并讲清它如何解耦发送方与接收方，是架构能力的体现。它是观察者模式的工业级形态：Qt 的 signals/slots、虚幻引擎(UE)的 `Multicast Delegate`、boost.signals2、C# 的 `event` 全是它。本模块还把 A4（`std::function` 类型擦除）和 E1（唯一 Id 凭证）的思想串起来用。

## 背景知识

### 1) 问题：强耦合的事件分发
"玩家受伤"要通知 UI（更新血条）、音效、成就、AI……若受伤代码直接调这四者：
```cpp
void on_damage(int hp) { ui.update(hp); audio.play(); achievements.check(hp); ai.alert(); }
```
加一个监听者就得改这行、`#include` 它的头、还反向依赖——大型项目里这是灾难。

### 2) 解法：信号把"谁关心"反转过来
```cpp
Signal<int> on_damage;                 // 受伤处只持有一个信号
on_damage.connect([&](int hp){ ui.update(hp); });   // 各模块自己来订阅
on_damage.connect([&](int hp){ audio.play(); });
...
on_damage.emit(current_hp);            // 受伤时一句话广播给所有订阅者
```
发送方**完全不认识**接收方，只管 `emit`；接收方随时 `connect/disconnect`。**彻底解耦**。

### 3) 核心结构：回调列表 + 唯一连接号
内部就是一串 `(Id, 回调)`：
```
connect(fn)    → 分配单调递增的 Id，存 (Id, fn)，返回 Id        // O(1)
emit(args...)  → 遍历列表，逐个 fn(args...)                     // 多播 / fan-out，O(n)
disconnect(id) → 按 Id 找到并移除那一条                          // O(n)
```
`Id` 是你的"连接凭证"，日后凭它精确断开某个监听者。

### 4) 槽用 std::function 装（呼应 A4）
槽类型是 `std::function<void(Args...)>`，lambda、函数指针、`std::bind` 的成员函数、仿函数都能塞进同一列表——这正是 A4 **类型擦除**的应用。`Signal<Args...>` 的 `Args` 就是事件携带的参数类型。

### 5) Id 单调递增、不复用（和 E1 对照）
E1 的槽位下标会复用、靠 generation 区分新旧；这里更简单：Id 只增不减，删了也不回头用，于是天然不会认错，断开一个失效 Id 安全返回 `false`。代价是 Id 一直变大（64 位足够）。两种思路都常见。

## 你要实现什么
打开 [include/signal.hpp](include/signal.hpp)。`Entry`、`std::function` 槽类型、`size/empty/clear` 都已给好。你实现 3 个 `TODO`：

| 编号 | 函数 | 任务 |
|------|------|------|
| E3-1 | `connect(fn)` | 分配新 Id、存入 `(id, fn)`、返回 Id |
| E3-2 | `disconnect(id)` | 按 Id 移除对应条目，返回是否找到 |
| E3-3 | `emit(args...)` | 遍历所有槽，逐个 `fn(args...)` |

## 关键坑
- **Id 用 `next_id_++`，不要复用**：单调递增保证唯一。从 1 起，0 留作"无效连接号"。
- **`connect` 里 `std::move(fn)`**：`std::function` 可能很重（捕获了大对象），按值入参后移动进列表。
- **`emit` 期间不要改 `slots_`（再入坑）**：如果某个回调在被调用时又 `connect/disconnect`，会在遍历中修改 `vector` → 迭代器失效/UB。工业级实现要么"延迟增删"、要么遍历前先拷一份列表。本模块测试不触发再入，但面试常问——见追问 5。
- **悬垂捕获**：回调常按引用捕获外部对象 `[&]`；若该对象先于信号析构，emit 时就访问了野引用。所以真实库提供 RAII `scoped_connection`（对象析构自动断开）——见追问 6。
- **`emit` 是 const**：它不改信号的连接列表，只读地遍历调用。`std::function::operator()` 本身是 const。

## 如何验证
```powershell
ctest --test-dir build -R E3 --output-on-failure
```
测试覆盖：连接一个槽 emit 后被调用且**参数正确**；emit 一次**多播**给全部槽；`disconnect` **精确移除**一个、其余不受影响、重复断开返回 `false`；**多参数**原样转发；空信号 emit **安全**、`clear` 清空；不同连接拿到**互不相同**的 Id。

> 提示：骨架里 `connect` 返回 0 且不挂槽、`disconnect` 恒 `false`、`emit` 为空操作；这里没有裸指针解引用，所以骨架只会变红（断言失败）而不崩溃。

## 面试追问

1. 信号-槽 / 多播委托解决了什么耦合问题？和直接函数调用、和观察者模式接口（`virtual onEvent`）相比优劣？

   **答**：信号-槽把"事件源"和"事件处理者"**解耦**——发送方只持有一个 `Signal`、只管 `emit`，**完全不认识也不依赖**任何接收方；接收方自己 `connect` 订阅。对比：①**直接函数调用**——发送方要 `#include` 并硬编码调用每个接收者，加一个监听者就改一次源码、还引入反向依赖，扇出全焊死；②**观察者模式接口（虚 `onEvent`）**——比直调好，但要求每个监听者**实现同一个接口基类**、注册时传 `Observer*`，耦合在"接口类型"上，一个对象想监听多种事件就得继承多个接口或自己写分发，且回调粒度被锁死成"一个对象一个虚函数"，挂不了 lambda。信号-槽用 `std::function` 槽，**任意可调用物**（lambda、成员函数绑定、自由函数）都能挂、不需继承任何接口，一个类可对不同信号挂不同 lambda，最灵活。代价：`std::function` 有类型擦除开销、`emit` 是间接调用不可内联、连接的生命周期要自己管理。

2. 为什么槽要用 `std::function` 而不是函数指针？（要容纳 lambda 捕获、`bind` 的成员函数——类型擦除）

   **答**：因为要容纳的可调用物远不止"裸函数指针"。**函数指针**只能指向无捕获的自由函数或静态成员，**装不下**：①**带捕获的 lambda**（`[&ui](int hp){ ui.update(hp); }` 携带状态，不是函数指针）；②**绑定了对象的成员函数**（`std::bind(&UI::update,&ui,_1)` 或 `[&]{ obj.f(); }`，需携带 `this`）；③**仿函数**（带 `operator()` 和成员数据的对象）。这些"代码 + 绑定状态"的组合，唯有**类型擦除**容器能统一存放——`std::function<void(Args...)>` 正是标准库的类型擦除包装：内部用小缓冲（SBO）或堆存放任意可调用对象、擦掉其具体类型，只暴露统一的 `operator()(Args...)`。这正是 A4 模块的应用。代价是一次间接调用 + 可能的堆分配 + 不可内联；若热路径上槽都是无捕获函数，可退化用函数指针数组省开销（见追问 4）。

3. `connect` 返回的 Id 有什么用？为什么单调递增不复用？和 E1 的 generation 复用方案各自取舍？

   **答**：**Id 是"连接凭证"**——`connect` 返回它，日后凭它 `disconnect(id)` 精确断开**某一个**特定监听者（而非 `clear` 全部）。**单调递增不复用**（`next_id_++`，从 1 起、0 留作无效）的好处是**实现极简且天然不认错**：每个连接拿到史上唯一的号，删了也不回收，于是绝不会出现"旧凭证恰好撞上新连接"的张冠李戴，`disconnect` 一个已失效 Id 安全返回 `false`。代价：Id 只增不减、会一直变大（用 64 位现实中用不完）；按 Id 线性查找是 O(n)。**对照 E1 的 generation 方案**：E1 的槽位下标**会复用**（free list 回收），靠 `generation` 代数区分"同一下标的新旧占用"，好处是下标紧凑、可直接当数组索引 O(1) 定位，代价是要多存并校验 generation、有回绕边界。两者都是"防凭证失效后被误用"的手段：信号-槽用"**永不复用的大号**"绕开问题，slot map 用"**复用 + 代数校验**"换紧凑索引。事件连接数通常不大、不需要 O(1) 索引，所以"单调 Id"这种更简单的方案够用。

4. `emit` 的复杂度？多播 N 个槽不可避免 O(N)，但每次调用的 `std::function` 间接跳转开销如何？热路径上怎么优化（小缓冲/内联委托/直接函数指针数组）？

   **答**：`emit` 遍历列表逐个调用，**O(N)**（N=槽数），这是多播/fan-out 的本质、省不掉。每次调用 `std::function` 的开销：①一次**类型擦除的间接跳转**（经内部函数指针跳到真实可调用物），**编译器无法内联**；②若目标超过 SBO 大小存在堆上，还有一次**指针解引用导致的 cache miss**。对偶发事件（受伤、按钮点击）这点开销无所谓；**热路径**（每帧对几万对象广播）上可优化：①**小缓冲/内联委托**——自己实现 delegate，把"对象指针 + 成员函数指针"内联存进固定大小结构，避免堆分配（UE delegate、`function_ref` 思路）；②**直接函数指针数组**——若槽都无捕获，用 `void(*)(void*,Args...)` + `void* ctx` 两个裸指针存，调用开销最小、cache 友好；③**数据导向**——把同类回调状态打包成连续数组批量处理，而非逐个间接调用；④**按需 emit**——分桶/分级，只对真正关心的子集广播。核心是用"已知形状的轻量委托"换掉通用 `std::function` 的灵活性。

5. 回调在被 `emit` 调用时又 connect/disconnect 会发生什么？怎么安全支持"再入"（延迟增删队列 / 遍历前快照 / 标记删除）？

   **答**：会**迭代器/引用失效 → UB**。`emit` 正在 `for (auto& e : slots_)` 遍历 `vector`，若某回调内部 `connect`（`push_back` 可能触发**扩容、整片搬迁**，正在用的引用/迭代器全失效）或 `disconnect`（`erase` 移动后续元素、改变 size），轻则漏调/重复调用、重则越界崩溃。安全支持再入的常见做法：①**遍历前快照**——`emit` 先把当前槽列表**拷一份**再遍历，期间的增删只作用于原列表、不影响本次广播（boost.signals2 思路，代价是每次 emit 拷贝）；②**延迟增删队列**——emit 时设"正在遍历"标志，此时的 connect/disconnect 不直接改 `slots_`，而记进 pending 队列，遍历结束后统一应用；③**标记删除（tombstone）**——disconnect 只把条目标记失效（置空 `fn` 或 id=0），遍历时跳过，emit 结束后再压实清理，避免遍历中改动容器结构。工业库通常组合②③，并处理"emit 中 `clear` 整个信号""信号在自己的回调里被销毁"等极端情况。本模块测试不触发再入，但这是面试高频追问。

6. 监听者对象先于信号销毁会怎样（悬垂）？RAII `scoped_connection` 怎么自动断开？和 `weak_ptr` 跟踪生命周期怎么结合？

   **答**：会**悬垂访问 → UB**。回调常按引用/指针捕获监听者（`[&obj]` 或捕获 `this`），若该对象**先于信号析构**，信号里仍挂着指向它的槽，下次 `emit` 就调用了访问**野引用/已析构 this** 的回调——读到垃圾或崩溃。解法：①**RAII `scoped_connection`**——`connect` 返回一个持有 `(Signal*, Id)` 的小对象，它的**析构函数自动调用 `signal->disconnect(id)`**；把它作为监听者的成员变量持有，于是**监听者析构 → 成员 scoped_connection 析构 → 自动断开**，信号里再不会留下指向死对象的槽（类似 `lock_guard` 之于锁）。②**`weak_ptr` 跟踪**——若监听者由 `shared_ptr` 管理，槽里存 `weak_ptr<T>` 而非裸引用；emit 时先 `weak.lock()`，**提升成功**才调用、失败（对象已亡）就跳过甚至顺手移除该槽。这把"对象是否还活着"交给引用计数，天然防悬垂。工业库（boost.signals2 的 `slot::track`、Qt 的 `QObject` 父子 + 信号自动断连）都内建这类生命周期跟踪。本模块为简化没做，但真实系统必须处理。

7. 单播 delegate（只一个回调，可有返回值）和多播 signal（多个回调、通常无返回值）有何区别？UE 为什么区分 `Delegate` 与 `MulticastDelegate`？

   **答**：**单播 delegate**——只绑定**一个**回调，语义是"把这件事**委托**给某一个处理者"，因为只有一个目标，**可以有返回值**（`Ret(Args...)`），调用方拿得到结果；典型用途：异步完成回调、定制策略钩子、"谁来回答这个问题"。**多播 signal**——挂**任意多个**回调，语义是"广播事件给所有关心者"，因为有 N 个回调、返回值无处安放（N 个返回值给谁？），所以**通常无返回值**（`void(Args...)`），要聚合得用 combiner（见追问 8）。**UE 为什么区分**：①**语义不同**——`Delegate`（单播）表达"一对一委托、要结果"（如返回 bool 决定是否拦截）；`MulticastDelegate` 表达"一对多通知、不要结果"（如 `OnHealthChanged` 广播给 UI/音效/成就）；②**开销不同**——单播只存一个委托、调用无需遍历，更轻；多播要存列表、遍历广播；③**反射/蓝图集成**——UE 还有 `Dynamic` 版（可序列化、蓝图可见），单播/多播各有 Dynamic 变体。明确区分让 API 自带意图、各自最优实现。

8. 怎么扩展：带返回值聚合（boost.signals2 的 combiner）、调用顺序/优先级、线程安全的跨线程 emit（排队到目标线程）？

   **答**：①**带返回值聚合**——多播默认丢弃返回值；要收集就引入 **combiner**（boost.signals2 的设计）：emit 时把每个槽的返回值喂给一个聚合器，由它决定最终结果——如"取最后一个""求和""**任一返回 true 就短路停止**（事件是否被消费）""收集成 `vector` 全返回"，combiner 还能控制是否提前终止遍历。②**调用顺序/优先级**——给每个连接附带 priority/group，`connect` 时按优先级**有序插入**（或 emit 前按优先级排序），保证高优先级槽先收到（Qt 的连接顺序、boost 的 group），同优先级按连接先后。③**跨线程 emit 线程安全**——并发 connect/disconnect/emit 要同步：最简单一把锁保护 `slots_`（emit 时先快照再解锁调用，避免持锁执行用户回调导致死锁/长持锁）；更关键的是 GUI/游戏常要求"**回调在目标线程执行**"——emit 不直接调用，而把"(目标槽, 参数拷贝)"**打包成任务投递到目标线程的事件队列/消息循环**，由该线程取出执行（Qt 的 `QueuedConnection`、游戏的"派发到主线程"）。这解决了"工作线程产生事件、但 UI 只能在主线程更新"的问题，代价是参数要可拷贝/可移动地跨线程传递、有排队延迟。
