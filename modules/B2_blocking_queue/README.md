## 为什么大厂爱考

生产者-消费者是并发的「Hello World」，几乎所有线程池、消息队列、日志系统的底层都是它。面试官借它考查：`mutex` 怎么用、`lock_guard` vs `unique_lock`、条件变量为什么必须配 `while`/谓词、什么是虚假唤醒、怎么优雅关闭不死锁。写对一个有界阻塞队列，并发基本功就立住了。

## 背景知识

### 1) `std::mutex` 与 RAII 锁

`mutex` 保护共享数据，同一时刻只允许一个线程进入临界区。**不要手动 `lock()/unlock()`**（异常一抛就忘了解锁 → 死锁），用 RAII 包装：

- `std::lock_guard<std::mutex>`：构造即加锁、析构即解锁，最简单，不能中途解锁。
- `std::unique_lock<std::mutex>`：更灵活，可中途 `unlock()/lock()`、可移动、**可配合条件变量**。

### 2) `std::condition_variable`：等待某个条件成立

当「队列空了，消费者得等有数据」时，不能忙等（空转浪费 CPU）。条件变量让线程**睡眠**直到被唤醒：

```cpp
std::unique_lock<std::mutex> lk(mtx_);
cv.wait(lk, [this]{ return 条件成立; });   // 条件不成立就释放锁并睡眠；被唤醒后重新拿锁再判
// 醒来后这里一定持有锁，且条件成立
```

`wait` 会**原子地「释放锁 + 睡眠」**，被 `notify` 唤醒后再**重新加锁**返回。条件变量必须配 `unique_lock`（因为它要中途解锁/加锁）。

### 3) 为什么必须用「谓词版 wait」/ while 循环 —— 虚假唤醒

条件变量可能在没人 notify 的情况下「莫名醒来」（spurious wakeup），也可能被 notify 后条件又被别的线程抢先改掉。所以**醒来后必须重新检查条件**：

```cpp
// 错误：if (q.empty()) cv.wait(lk);     // 醒来不复查，可能在空队列上 pop → 崩
// 正确：cv.wait(lk, [this]{ return !q.empty() || closed_; });  // 等价于 while(!pred) wait(lk);
```

### 4) 有界队列：两个条件变量

容量有限时有两个等待方向：队列满了**生产者**要等（`not_full_`），队列空了**消费者**要等（`not_empty_`）。push 成功后唤醒 `not_empty_`，pop 成功后唤醒 `not_full_`。

### 5) 优雅关闭 (graceful shutdown)

关闭时要让所有正在 `wait` 的线程醒过来，否则它们永远睡着（线程泄漏/无法 join）。做法：置 `closed_ = true` 后 `notify_all()`。约定关闭后：push 不再入队；pop 把**剩余数据先取完**，队列空了再返回 `false` 表示「没有更多了」。

## 关键坑

- `**cv.wait` 一定要用谓词版**（或 `while` 复查），否则虚假唤醒会让你在空队列上操作。
- **条件变量配 `unique_lock`，不是 `lock_guard`**。
- `**notify` 可以在解锁后再调**（减少「被唤醒线程立刻又抢不到锁」的概率），但在锁内调用也正确。
- **关闭后 pop 要先把残留数据取完再返回 false**，否则数据丢失。
- **谓词里要带上 `|| closed_`**，否则关闭时等待者无法醒来 → 卡死、join 不掉。

## 面试追问

1. `lock_guard` 和 `unique_lock` 有什么区别？各自什么场景？
  **答**：`lock_guard` 是最简 RAII：构造即锁、析构即解，中途不能解锁/重锁，零开销，适合"进作用域锁、出作用域解"的简单临界区。`unique_lock` 更灵活：支持延迟加锁（`defer_lock`）、提前 `unlock()`/再 `lock()`、`try_lock`、所有权移动、以及配合条件变量（`cv.wait` 需在内部解锁再加锁，**必须**用 `unique_lock`）。代价是多一个状态位、略重。普通互斥用 `lock_guard`；要配 cv 或需手动控制加解锁时机时用 `unique_lock`。
2. 条件变量为什么必须配 `while`/谓词？什么是虚假唤醒？
  **答**：因为"被唤醒"不等于"条件已满足"：可能虚假唤醒，也可能醒来拿锁前条件又被别人改掉。所以必须 `while (!pred) wait();` 重新检查，用 `if` 会漏检、在条件不成立时往下跑。**虚假唤醒**指线程没收到任何 notify 也可能自行返回（标准允许实现这样做以换效率），因此谓词复查是强制的、不是可选优化。
3. `notify_one` 和 `notify_all` 怎么选？惊群效应是什么？
  **答**：只需唤醒一个、且任意一个被唤醒都能前进时用 `notify_one`（如队列放进一个元素只够喂一个消费者），开销小、无惊群。当状态变化可能让多个等待者都该前进、或不同等待者共用一个 cv 等不同条件时用 `notify_all`。**惊群效应**指一次唤醒全部等待线程，它们争抢同一把锁，最终只一个能干活、其余复查谓词后又睡，造成大量无谓的上下文切换。能用 notify_one 就别用 notify_all。
4. `wait` 内部是怎么「原子地释放锁并睡眠」的？为什么不能用普通锁？
  **答**：`wait(lk)` 把"解锁 + 进入等待队列睡眠"做成对外不可分割的一步：先把线程登记到 cv 等待队列，再释放 `lk`，使"解锁"与"睡眠"之间不存在可被 notify 漏掉的窗口——否则若先解锁、还没睡时别人 notify，这次唤醒就丢了（lost wakeup），线程永远睡下去。被唤醒后 wait 在返回前重新加锁。必须用 `unique_lock`（不能用 `lock_guard`）正因为 wait 需在内部解锁再加锁，而 lock_guard 不暴露这种能力。
5. 怎么优雅关闭一个阻塞队列而不丢数据、不死锁？
  **答**：设一个 `closed`_ 标志，`close()` 加锁置位后 `notify_all` 唤醒所有阻塞的生产者和消费者。消费者 `pop` 的谓词改成"队列非空 **或** 已关闭"：醒来后若队列还有数据就继续取（保证不丢已入队数据），直到队列空且 closed 才返回失败/退出；生产者在 closed 后拒绝入队。关键点：close 必须 `notify_all`（否则阻塞者永远醒不来→死锁）、消费者要"先排空再退出"。
6. 如果改成「无界队列」，还需要 `not_full_` 吗？有什么风险？（内存暴涨/背压）
  **答**：不需要 `not_full_`——无界队列生产者永不因满而阻塞，可去掉容量上限和对应 cv，只保留 `not_empty_`。风险是**失去背压**：生产持续快于消费时队列无限增长→内存暴涨甚至 OOM，故障从"生产者被自然限速"变成"整个进程被拖垮"。有界队列正是用"满则阻塞生产者"提供背压、把压力反馈给上游。无界队列只适合能确保消费跟得上、或峰值有限的场景。
