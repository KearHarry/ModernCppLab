# C5 · 侵入式双向链表 IntrusiveList（intrusive linked list）

难度 ⭐⭐⭐⭐ · 预计 2h

## 为什么大厂爱考

"`std::list` 慢在哪？内核/引擎为什么自己写链表？"——能答出 **侵入式链表（对象自带指针）** 并讲清它如何做到零分配入链、O(1) 摘除、一对象多链表，是系统/引擎岗的硬核加分项。Linux 内核 `list_head`、boost.intrusive、游戏引擎的对象管理全用它。

## 背景知识

### 1) std::list 的隐藏成本

`std::list<Widget>` 每放一个元素，都在堆上 `new` 一个独立节点 `{prev, next, Widget}`：

- 每个元素**一次堆分配**（高频增删时是大头开销）；
- 节点散落堆各处，遍历**cache 不友好**；
- 想删除某元素必须先拿到它的 `iterator`。

### 2) 侵入式：让对象自己当节点

反过来，把 `prev/next` **塞进对象自身**（继承一个 `ListNode` 钩子）：

```
std::list<Widget>:  额外 [node:prev|next|→Widget]   节点与对象分离、每个一次堆分配
IntrusiveList:      Widget 自己 = [prev|next|...数据...]   对象即节点、零额外分配
```

### 3) 三大超能力

1. **零分配入链**：对象已存在，链接只改几个指针，不 `new`。
2. **O(1) 摘除**：`unlink(对象)` 只用该对象的 `prev/next` 改 4 个指针，**无需遍历查找它在哪**。`std::list::erase` 要先有 iterator；裸数组 `remove` 要先 `find`。
3. **多链表成员**：一个对象带多个钩子，就能**同时**挂在多个链表里（"可见物列表"+"待删除列表"+……各用各的指针）。这是引擎里极常见的需求。

### 4) 带哨兵的环形双向链表

`head_` 是个不放数据的**哨兵**节点，首尾相接成环：

```
head_ <-> A <-> B <-> C <-> head_        空链表时 head_.next==head_.prev==&head_（自环）
```

哨兵让插入/删除**无需特判头尾**（永远有前驱后继），代码干净——工业级链表标配。`front=head_.next`，`back=head_.prev`。

### 5) 从钩子指针找回对象：static_cast 向下转型

`T` 公有继承 `ListNode`，故 `ListNode*` 实际指向某个 `T` 的基类子对象。`static_cast<T*>(node)` 安全转回（对象本就是 `T`，编译器自动算基类偏移）。哨兵 `head_` 是裸 `ListNode`、**永不**转成 `T`——遍历到它就停。（Linux 内核用 `container_of` 宏 + `offsetof` 实现同样的"由成员找回宿主"，见追问。）

## 关键坑

- **改指针的顺序**：`push_back` 要先把新节点的 `prev/next` 设好，再让原尾的 `next` 和哨兵的 `prev` 指向它，4 个指针都要更新，别漏。
- `**unlink` 的精髓**：`n->prev->next = n->next; n->next->prev = n->prev;`——让前驱后继互相直连、跳过自己。因为有哨兵，删头/删尾也走这同一段代码，不用特判。
- `**unlink` 后置空**：把 `n->prev=n->next=nullptr` 标记"已脱链"，避免悬挂指针；前置条件是对象当前确实在某链表里（对没入链的对象 unlink 是 UB）。
- **上/下转型都用 `static_cast`**：`&static_cast<ListNode&>(obj)`（上）、`static_cast<T*>(node)`（下）。**绝不**用 `reinterpret_cast`——当 `ListNode` 不是 `T` 的首个基类时，`reinterpret_cast` 不会调整偏移，会错位。
- **链表不拥有元素**：从不 `new/delete` 对象。元素生命周期由你管（栈对象/对象池/slot map）。链表析构不删元素；元素若先于链表析构，要先把它 `unlink`，否则链表里留下悬挂节点。

测试覆盖：`push_back` **保持顺序**、`front/back` 正确；**只凭对象本身 O(1) 摘除**中间元素、前后自动直连；`pop_front` **依次清空**、空链返回 `nullptr`；同一对象**零分配地从一个链表转移到另一个**；空链表各接口安全。

## 面试追问

1. `std::list` 相比侵入式链表多了哪些开销（每元素堆分配、cache、删除需 iterator）？侵入式分别怎么消除？
  **答**：`std::list` 每插入一个元素都要**堆分配一个独立节点**（含 prev/next 指针 + 元素副本），开销有三：①每元素一次 `new`/`free`（慢、易碎片）；②节点散布堆上、**缓存不友好**；③要删除某元素得先有指向它的**迭代器**（常需先遍历找到）。侵入式链表把 prev/next 指针**直接做成元素自身的成员**：①元素自带钩子、**零额外分配**（节点就是对象本身）；②少一层节点间接；③拿着对象本身就能 O(1) unlink，无需遍历查找。
2. 侵入式链表为什么能 O(1) 摘除一个元素而无需遍历？这对"一个对象在多个容器里"意味着什么？
  **答**：因为元素自带 prev/next 指针，**对象自己就知道它在链表里的前驱和后继**，摘除时只需 `prev->next=next; next->prev=prev` 改四个指针、O(1)，根本不用从头遍历定位它。这意味着只要手里有**对象的指针**就能立刻把它摘掉。对"一个对象同时在多个容器"很有用：对象为每个链表各带一组钩子，可被 O(1) 地从任意一个链表单独摘除而不影响其它链表——这是 `std::list`（节点私有、删除需该链表的迭代器）做不到的。
3. 哨兵节点解决了什么问题？没有哨兵时插入/删除头尾要怎么特判？
  **答**：**哨兵节点**（dummy/sentinel）是一个不存数据、首尾相连的占位节点，让链表**永不为空**、头尾也有"前驱/后继"。它消除了边界特判：插入/删除时被操作节点**总有非空的 prev 和 next**，统一用 `prev->next=…; next->prev=…` 即可。没有哨兵时，头部插入要特判"原链表为空/更新 head"、尾部要更新 tail、删除唯一元素要把 head/tail 都置空——大量 `if(node==head)`/`if(node==tail)`/`if(empty)` 分支，易错。哨兵把这些都变成普通的中间操作。
4. 从成员/基类指针找回宿主对象，C++ 用 `static_cast`（基类）或 Linux 的 `container_of`/`offsetof`（任意成员），两者原理和适用条件？
  **答**：两者都解决"已知子对象地址，反推外层对象地址"。`**static_cast`（基类钩子）**：让对象**继承**链表钩子基类，`static_cast<Derived*>(hook_ptr)` 由编译器按继承布局自动调整偏移，类型安全、最常用，但要求对象继承指定基类。`**container_of`/`offsetof`（任意成员钩子）**：钩子是对象的**普通成员**，用 `offsetof(T,hook)` 算出成员在结构体内的字节偏移，`(T*)((char*)hook_ptr - 偏移)` 反推宿主地址；适用条件是 T 必须是 **standard-layout** 类型（否则 offsetof 未定义），不依赖继承、可多个钩子，Linux 内核链表用此法。
5. 为什么不能用 `reinterpret_cast` 做这个转换？多继承下会出什么错？
  **答**：因为成员/基类子对象到宿主对象的地址转换**可能有非零偏移**，必须按真实布局**加减偏移**，而 `reinterpret_cast` 只是"把这串比特当成另一类型"、**不调整任何偏移**，单继承且钩子在偏移 0 时碰巧对、一旦有偏移就指到错误地址。**多继承**下尤其糟：一个对象有多个基类子对象排在不同偏移上，`static_cast` 会按所转基类正确加减偏移，而 `reinterpret_cast` 直接按原地址解释→指向错误的基类子对象、读写错乱、UB。所以这种"子对象↔宿主"转换要用 `static_cast`（基类）或 offsetof 算偏移（成员），绝不能用 reinterpret_cast。
6. 一个对象同时在多个侵入式链表里怎么实现（多个钩子 + tag 模板参数区分）？
  **答**：给对象**放多组钩子**，每组对应一个链表；为在类型层面区分"这是哪条链表的钩子"，用 **tag 模板参数**：如 `ListHook<TagA>`、`ListHook<TagB>` 是不同类型的成员，链表 `IntrusiveList<T,TagA>` 只操作 TagA 那组钩子。对象同时继承/包含多个不同 tag 的钩子，就能被多个链表各自独立地 O(1) 链入/摘除、互不干扰。tag 既区分钩子、又让"同一对象在同类型多个链表"在编译期类型安全。
7. 侵入式链表不拥有元素，生命周期怎么管？元素先析构而没 unlink 会怎样？怎么用 RAII 自动 unlink（auto-unlink hook）？
  **答**：侵入式链表**只借用对象的钩子、不拥有对象**，对象的创建/销毁由别处负责。危险在于：若对象**先被析构却没先 unlink**，链表里仍留着指向这块已失效内存的指针，下次遍历或别的元素 unlink 时访问它→**悬垂指针、UB**。两种管法：①约定"析构前必须 unlink"，由所有者保证顺序；②**auto-unlink hook**——把 unlink 放进钩子的**析构函数**里（RAII），对象一析构，其钩子自动把自己从所在链表摘除，杜绝悬垂；代价是钩子要存"我在哪个链表"的信息、且这种链表不能再假设 O(1) `size()`。
8. 它的缺点是什么（侵入类型定义、不能存不可改的第三方类型、线程安全需自己加锁）？什么时候宁可用 `std::list`/`std::vector`？
  **答**：缺点：①**侵入性**——必须修改元素类型给它加钩子，**存不了不可改的第三方类型**（如 `int`、别人库里的 class）；②对象被多个链表共享时**生命周期/所有权易混乱**；③**线程安全要自己加锁**；④钩子占用对象空间、API 不如 STL 通用。何时宁用标准容器：元素是**值类型/第三方类型**、不需要 O(1) 跨容器转移、追求**连续存储和遍历速度**时用 `std::vector`；需要稳定节点、频繁中间插删又不想侵入类型时用 `std::list`。侵入式只在**高性能、对象生命周期已被你掌控、要零分配/多容器共享**（游戏引擎、内核、内存分配器）时才划算。
